> **છેલ્લે અપડેટ કરેલું:** 2026-08-29 — v3.8.51 (Video Bridge ટ્રાન્સક્રિપ્ટનું મૂળ કૉલર દ્વારા જાહેર કરવામાં આવે છે,
> હજી સર્વર દ્વારા ચકાસાયેલું નથી — #11661 અનુસાર સ્પષ્ટ કરવામાં આવ્યું)

Guardrails, OmniRoute અને અપસ્ટ્રીમ પ્રદાતાઓ વચ્ચેની સીમા પર સુરક્ષા, નીતિ અને કન્ટેન્ટ રૂપાંતરણો લાગુ કરે છે. દરેક guardrail વિનંતીના payloads (`preCall`) અને અપસ્ટ્રીમ પ્રતિસાદો (`postCall`)નું નિરીક્ષણ કરી શકે છે (અને વૈકલ્પિક રીતે તેમને નકારી, રૂપાંતરિત અથવા ઍનોટેટ કરી શકે છે).

સિસ્ટમ **fail-open** છે: જો કોઈ guardrail કાર્યરત હોય ત્યારે અપવાદ ફેંકે, તો registry ભૂલ નોંધે છે અને વિનંતીને નિષ્ફળ કરવાને બદલે આગામી guardrail સાથે ચાલુ રહે છે. બ્લૉક કરવું હંમેશાં સ્પષ્ટ નિર્ણય (`block: true`) હોય છે, ક્યારેય આકસ્મિક ઘટના નહીં.

### વિઝન બ્રિજ (`visionBridge.ts`) — મોડાલિટી બ્રિજ PR-1

**ગેર-વિઝન મોડેલ્સ** માટે નિશાન બનાવેલ છબી ધરાવતી વિનંતીઓને અટકાવે છે અને અથવા તો
વિઝન-સમર્થ મોડેલ તરફ સમગ્ર વિનંતીને ફરીથી માર્ગદર્શન આપે છે અથવા છબીના ભાગોને
ટેક્સ્ટ વર્ણનોથી બદલે છે જે એક કન્ફિગરેબલ વિઝન મોડેલ દ્વારા ઉત્પાદન કરવામાં આવે છે
ઉપરાંત કૉલ પહેલાં. આ ટેક્સ્ટ-માત્ર પ્રદાતાઓને પારદર્શક રીતે
મલ્ટીમોડલ પેલોડ્સને સંભાળવા દે છે.

પ્રવાહ:

1. જો લક્ષ્ય મોડેલ પહેલેથી જ વિઝનને સપોર્ટ કરે છે તો છોડી દો (જ્યારે તે
   ફરજિયાત-બ્રિજ યાદી `isVisionBridgeForcedModel` માં દેખાય છે).
2. `extractImageParts(messages)` દ્વારા છબીના ભાગોને કાઢી નાખો
   (`visionBridgeHelpers.ts`), જે **એકીકૃત મીડિયા
   ડિટેક્ટર** `detectMediaParts()` ને委托 કરે છે `open-sse/utils/mediaParts.ts` માં — એક જ સત્યનો સ્ત્રોત
   જે કોમ્બો સુસંગતતા ફિલ્ટર સાથે શેર કરવામાં આવે છે.
   કાઢી નાખવું ટોચના સ્તરના ભાગો માટે મંજૂર છે જે આકારો
   `replaceImageParts` પાછા સ્પ્લાઇસ કરી શકે છે (કાઢી નાખવું↔બદલવું કરાર): OpenAI
   `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL
   `source.type:"url"`, અને Responses API `input_image`. નેસ્ટેડ હિટ્સ અને
   સૂચક-માત્ર આકારો કોમ્બો-ફિલ્ટર સામગ્રી છે અને ક્યારેય કાઢી લેવામાં નથી આવતી.
   જો કશું મળતું નથી તો છોડી દો.
3. `resolveVisionBridgeRuntimeSettings()`
   (`src/shared/constants/modalityBridgeDefaults.ts`) દ્વારા રનટાઇમ કન્ફિગરેશનને ઉકેલો:
   નવા `modalityBridge*`
   સેટિંગ્સ કી જીતે છે; વારસાગત `visionBridge*` કી **એક-ચક્ર
   બેકફોલ્બ** (રોલબેક વિન્ડો) રહે છે. બ્રિજ અક્ષમ હોય ત્યારે કોઈ મીડિયા ટ્રાવર્સલ પહેલાં છોડી દો.
4. મોડ પસંદકર્તા (`modalityBridgeVisionMode`, નીચેની કોષ્ટક જુઓ) નક્કી કરે છે
   ફરીથી માર્ગદર્શન આપવું કે વર્ણન કરવું. ફરીથી માર્ગદર્શન આપે છે `modifiedPayload` સાથે ફક્ત `model`
   બદલાયું, ઉપરાંત મેટા `{ rerouted, fromModel, toModel, imagesKept }`.
5. વર્ણન પાથ: છબીઓને `maxImages` પર મર્યાદિત કરો, કાર્ય-જાણકાર પ્રોમ્પ્ટ બનાવો,
   વર્ણન કેશને પરામર્શ કરો, વિઝન મોડેલને **સાથે** કૉલ કરો
   (`Promise.allSettled`), અને `[Image N]: <description>` ટેક્સ્ટ ભાગોને તેમના સ્થાનમાં દાખલ કરો. એક નિષ્ફળ વર્ણન `null` આપે છે અને મૂળ છબીનો ભાગ **સંરક્ષિત** છે (#4012) — સિવાય કોમ્બો વર્ણન પાથ પર જ્યારે દરેક
   વર્ણન નિષ્ફળ જાય છે, જ્યાં એક પુષ્ટિ કરેલ ગેર-વિઝન અપસ્ટ્રીમને
   `(unavailable — no vision-capable provider connected)` સ્ટબ મળે છે (#8430).
6. પાછું આપો `modifiedPayload` + મેટા (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`).

#### મોડ પસંદકર્તા (`modalityBridgeVisionMode`)

| મોડ        | ડિફોલ્ટ | વર્તન                                                                                                                                                                                                                                                                                   |
| ---------- | ------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔       | વારસાગત હ્યુરિસ્ટિક, અચૂક (#6640/#7204): ગેર-કોમ્બો/`auto/` મોડેલો શ્રેષ્ઠ વિઝન મોડેલ તરફ ફરીથી માર્ગદર્શન આપે છે જો કે મૂળ મોડેલ પાસે પહેલેથી જ ઉપયોગી પ્રમાણપત્રો હોય (ત્યારે વર્ણન); કોમ્બો લક્ષ્યો હંમેશા વર્ણન કરે છે.                                                             |
| `describe` |         | હંમેશા વર્ણન કરો — ફરીથી માર્ગદર્શન બ્લોક સંપૂર્ણપણે છોડી દેવામાં આવે છે; વપરાશકર્તાના પસંદ કરેલા મોડેલ હંમેશા જવાબ આપે છે.                                                                                                                                                             |
| `reroute`  |         | ફરજિયાત ફરીથી માર્ગદર્શન: કીપ-પ્રમાણિત-મોડેલ ગાર્ડને બાયપાસ કરવામાં આવે છે. ફરીથી માર્ગદર્શન-**લક્ષ્ય** પ્રમાણપત્ર ગાર્ડ હજુ પણ લાગુ પડે છે — જ્યારે કોઈ ઉપયોગી વિઝન લક્ષ્ય નથી, ત્યારે વિનંતી વર્ણન તરફ જતી હોય છે જેથી કાચી છબીઓ ક્યારેય ટેક્સ્ટ-માત્ર બેકએન્ડ સુધી ન પહોંચે (#8430). |

ફરજિયાત મોડ્સ **પહેલાં** ઓટો હ્યુરિસ્ટિક ચાલે છે; `auto` વર્તન
પ્રિ-PR-1 ગાર્ડરેલ સાથે બાઇટ-આઈડેન્ટિકલ છે.

#### કાર્ય-જાણકાર વર્ણન પ્રોમ્પ્ટ (`modalityBridgeVisionTaskAware`)

ડિફોલ્ટ **સાચું**. `composeVisionPrompt()` (`visionBridgeHelpers.ts`) ઉમેરે છે
**છેલ્લા વપરાશકર્તા સંદેશાનો** ટેક્સ્ટ (500 અક્ષરોમાં કાપી) આધારભૂત
વર્ણન પ્રોમ્પ્ટમાં, વર્ણનને વપરાશકર્તા દ્વારા વાસ્તવમાં પૂછવામાં આવેલા પર દોરી જાય છે
(codex-vision-proxy પેટર્ન) અને વિઝન મોડેલને દૃશ્યમાન
ટેક્સ્ટને લખવા માટે કહે છે. ધ્વજ બંધ હોય ત્યારે — અથવા કોઈ વપરાશકર્તા ટેક્સ્ટ ન હોય — આધારભૂત પ્રોમ્પ્ટને અચૂક ઉપયોગ કરવામાં આવે છે.

વિશેષણ સ્વરૂપનું પોતાનું OpenAI-સંગત વિનંતી (`callVisionModelSingle()`
`visionBridgeHelpers.ts` માં) હંમેશા `image_url.detail: "high"` માટે વિનંતી કરે છે —
બિનશરતી, દરેક caller/provider માટે, કોઈપણ ક્લાયન્ટ સંકેત પર ગેટેડ નથી.
ઓછી વિગતોનું નમૂનાકરણ OCR ચોકસાઈને ખરાબ બનાવે છે તે ચોક્કસ લખાણ-ટ્રાન્સક્રિપ્શન
કાર્ય માટે જે આ પ્રોમ્પ્ટ માટે પૂછવામાં આવ્યું છે, તેથી વર્ણન કૉલ પોતે હંમેશા ઉચ્ચ
વિગત માટે પૂછે છે ભલે જ મૂળ આવક વિનંતી કયા વિગત સ્તરનો ઉપયોગ કરે છે. આ
માત્ર આંતરિક વર્ણન વિનંતી શરીરને અસર કરે છે; તે કેવી રીતે
OmniRoute caller ની પોતાની `image_url.detail` ને મુખ્ય વિનંતી પર આગળ વધારવામાં
ફરક નથી પાડતું — તે ડિફોલ્ટ અલગ રીતે લાગુ થાય છે, અને માત્ર શોધી લેવામાં આવેલા
OpenCode ક્લાયન્ટો માટે, `defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`) માં.
વર્ણન સ્વરૂપની આન્થ્રોપિક વાયર-ફોર્મેટ શાખામાં કોઈ `detail` ક્ષેત્ર નથી
અને તે બંને ડિફોલ્ટથી અસંવેદનશીલ છે.

#### વર્ણન આઉટપુટ કૅપ (`modalityBridgeVisionMaxChars`)

| કી                             | ડિફોલ્ટ | શ્રેણી             |
| ------------------------------ | ------- | ------------------ |
| `modalityBridgeVisionMaxChars` | `0`     | `0` અથવા 100–50000 |

`0` (ડિફોલ્ટ)નો અર્થ છે **કોઈ કૅપ નથી** — `callVisionModel()` દ્વારા પાછો આપેલ વર્ણન
અવિરત રીતે પસાર થાય છે, વર્તમાન વર્તન જાળવી રાખે છે. 100–50000 શ્રેણીમાં કોઈપણ મૂલ્ય
વર્ણનને `…` સોફિક્સ સાથે કાપે છે તે પહેલાં તે `[Image N]: <description>` તરીકે
સ્પ્લાઇસ કરવામાં આવે છે (`VisionBridgeGuardrail.preCall()` `src/lib/guardrails/visionBridge.ts` માં).
વિગત-ભરપૂર OCR કાર્ય માટે આ વધારવું જ્યાં નીચેના મોડેલને સંપૂર્ણ ટ્રાન્સક્રિપ્શનની જરૂર છે;
ચેટી દૃષ્ટિ મોડેલ પર ટોકન વપરાશને બાઉન્ડ કરવા માટે તેને ઘટાડવું.
ડેશબોર્ડ ક્ષેત્ર Vision ટેબના એડવાન્સ્ડ પેનલમાં રહે છે
(`modality-bridge-max-chars` `ModalityBridgeVisionTab.tsx` માં) અને 1 અને 99 વચ્ચેના કોઈપણ
મૂલ્યને 100 ની તળિયે કંપ કરે છે જ્યારે સ્પષ્ટ `0` ને અસ્પષ્ટ રાખે છે — `0` પોતે જ
એક માન્ય Zod મૂલ્ય છે
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`), માત્ર
"unset" ડિફોલ્ટ નથી.

#### વર્ણન કેશ (`modalityBridge/bridgeCache.ts`)

વર્ણન આઉટપુટ માટે મેમરીમાં LRU + TTL કેશ, શેર કરેલ પ્રક્રિયા-વિસ્તૃત.
કી = `sha256(imageRef + composedPrompt + configuredBridgeModel)` સાથે
લંબાઈ-પ્રિફિક્સ ફ્રેમિંગ (કોઈ ક્ષેત્ર-સીમા ટકરાવા નથી). મોડેલ ઘટક છે
**કન્ફિગર કરેલ** બ્રિજ મોડેલ, જે મોડેલ વાસ્તવમાં જવાબ આપ્યો તે નથી —
`callVisionModel` આંતરિક રીતે પાછા પડી શકે છે, અને દરેક પ્રયાસ માટે કી બનાવવાથી
કેશને તૂટે છે. નિષ્ફળ વર્ણનો કેશ કરવામાં નથી આવતાં. સેટિંગ્સ:

| કી                              | ડિફોલ્ટ | શ્રેણી  |
| ------------------------------- | ------- | ------- |
| `modalityBridgeCacheEnabled`    | `true`  | —       |
| `modalityBridgeCacheTtlMinutes` | `60`    | 1–1440  |
| `modalityBridgeCacheMaxEntries` | `200`   | 10–5000 |

#### રિમોટ ઇમેજ નોર્મલાઇઝેશન (સ્વ-લૂપ વર્ણન/base64 ફેચ)

જ્યારે બ્રિજ **રિમોટ** ઇમેજને પોતે ફેચ કરે છે — આન્થ્રોપિક વર્ણન
સ્વ-કૉલ અને ક્લોડ-વાયર-ફોર્મેટ base64 રૂપાંતરણ
(`ensureBase64ImagesForClaudeWire`), બંને દ્વારા
`fetchRemoteImageAsDataUri()` `visionBridgeHelpers.ts` માં — પરિણામે મળેલ ડેટા
URI `normalizeDataUri()` દ્વારા પસાર થાય છે
(`open-sse/utils/imageNormalize.ts`) પહેલાં તે દૃષ્ટિ-મોડેલ
વિનંતીમાં એમ્બેડ કરવામાં આવે છે. ઓવરસાઇઝ્ડ ઇમેજોને **2048px લાંબા કિનારે** (જે
OpenAI/આન્થ્રોપિક પહેલેથી સર્વર-સાઇડ પર લાગુ કરે છે) પર ઘટાડવામાં આવે છે, જે
અપલોડ બાઇટ્સ/લેટન્સી ઘટાડે છે જ્યારે દૃષ્ટિ મોડેલ શું જોવે છે તે બદલતું નથી. પુનઃમાપન
`sharp` નો ઉપયોગ કરે છે, જે ડાયનામિક આયાત દ્વારા લોડ થાય છે: એક પ્લેટફોર્મ પર જ્યાં તેની નેટિવ
બાઇનરી લોડ થવામાં નિષ્ફળ જાય છે, `normalizeDataUri()` **ક્યારેય ફેંકતું નથી** — તે મૂળ બાઇટ્સના
પાસથ્રૂમાં પાછું પડે છે, તેથી વર્ણન/base64-રૂપાંતરણ
માર્ગ હંમેશા કાર્યરત રહે છે. નોન-ઇમેજ બાઇટ્સ (એક ફેચ જે ડિકોડ કરી શકાય તેવી
ઇમેજ પાછું આપતું નથી) પણ અસ્પષ્ટ રીતે પસાર થાય છે. આ નોર્મલાઇઝેશન
બ્રિજ દ્વારા તેના પોતાના સ્વ-કૉલ માટે ફેચ કરેલ ઇમેજો સુધી મર્યાદિત છે — તે ક્યારેય
caller ની કાચી પાસથ્રૂ પેલોડ પર લાગુ નથી થતું, ઓપ્ટ-ઇન-માત્ર મ્યુટેશન સિદ્ધાંત સાથે
સંગત (હાર્ડ રૂલ #20).

નવી `modalityBridge*` કી `updateSettingsSchema` માં Zod-પ્રમાણિત છે

`modalityBridgeVisionMode`, `modalityBridgeVisionModel`,
`modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`,
`modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`,
`modalityBridgeVisionMaxChars`, `modalityBridgeCache*` ત્રિકોણ, અને
`modalityBridgeAudio*` જૂથ જે ઓડિયો બ્રિજ દ્વારા ઉપયોગમાં લેવાય છે. માઇગ્રેશન
`141_modality_bridge_settings.sql` અસ્તિત્વમાં આવેલા વારસાગત
`visionBridge*` મૂલ્યોને મેળ ખાતા નવા કી પર નકલ કરે છે (ઇડેમ્પોટન્ટ, ક્યારેય ઓપરેટર-સેટ
`modalityBridge*` મૂલ્યને ઓવરરાઇટ નથી કરે); વારસાગત કી એક વાંચન ફોલબેક તરીકે એક રિલીઝ ચક્ર માટે સ્વીકારવામાં રહે છે.

#### પારદર્શિતા હેડર + આંકડા

વર્ણન-પરિવર્તિત પ્રતિસાદો ધરાવે છે
`x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>`
(`buildModalityBridgeHeader()` દ્વારા બનાવવામાં આવે છે `modalityBridge/bridgeStats.ts` માં,
`withModalityBridgeHeader()` દ્વારા સ્ટેમ્પ કરવામાં આવે છે `src/sse/handlers/chatHelpers.ts` માં).
ફરીથી માર્ગદર્શિત વિનંતીઓ **કોઈ** હેડર મેળવે છે — પેલોડ અસ્પષ્ટ હતું અને મોડેલ
સ્વેપ પહેલેથી જ પ્રતિસાદના શરીરના `model` ક્ષેત્રમાં દેખાય છે.

`GET /api/modality-bridge/stats` (વ્યવસ્થાપન ઓથ, સમાન સ્તર જેમ કે
`GET /api/settings`) મેમરીમાં પ્રતિ-મોડાલિટી કાઉન્ટર્સ પાછા આપે છે
`{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs,
latencySamples, averageLatencyMs, lastUsedAt }` માટે `vision`, `audio`, અને
`video`. `averageLatencyMs` `latencySamples` નો ઉપયોગ કરે છે, તમામ પ્રયાસો નહીં, તેના
ગણક તરીકે; સમય વિના એક ઓપરેશન શૂન્ય-મિલિસેકન્ડ નમૂના બનાવતું નથી. `bridged` સફળ
રૂપાંતરણો માટે પાછળની સુસંગત ઉપનામ રહે છે; નિષ્ફળ પ્રયાસો તેને વધારતા નથી.
કાઉન્ટર્સ ડિઝાઇન દ્વારા પ્રક્રિયા પુનઃપ્રારંભ પર રિસેટ થાય છે
(ટેલેમેટ્રી, હિસાબ નથી).

#### ડેશબોર્ડ કન્ફિગરેશન

ડેડિકેટેડ ડેશબોર્ડ પેજ છે  
`/dashboard/settings/modality-bridge` . તેની URL-સરનામે `Vision`, `Audio`, અને `Video` ટેબ્સ ક્વેરી પેરામીટર્સને જાળવે છે જ્યારે `tab` મૂલ્યને બદલવામાં આવે છે. વિઝન ટેબમાં સક્રિયતા, મોડ, મોડેલ પસંદગી (સ્વચાલિત ડિફોલ્ટ સહિત), કાર્ય-જાણકારી પ્રોમ્પ્ટિંગ, અદ્યતન ટાઇમઆઉટ/છબી/વર્ણન-લંબાઈ/કેશ મર્યાદાઓ, રનટાઇમ કાઉન્ટર્સ, અને એક સુરક્ષિત નમૂના વિનંતી દર્શાવવામાં આવે છે. ઓડિયો ટેબ પણ જીવંત છે: તે સક્રિયતા, STT-માત્ર મોડલ પિકર સાથે ઓટો, ટાઇમઆઉટ/મહત્તમ-ક્લિપ મર્યાદાઓ, ઓડિયો કાઉન્ટર્સ, અને એક `input_audio` નમૂના પરીક્ષણ દર્શાવે છે. વિડિયો ટેબ કાર્યાત્મક છે: તે FFmpeg/ffprobe રનટાઇમ રાજ્યને રિપોર્ટ કરે છે — ચાર સ્પષ્ટ UI રાજ્યમાંથી એક (`unknown` જ્યારે પ્રોબ ઉડાનમાં હોય અથવા પૂર્ણ કરી શકતું નથી, `restricted` એક નોન-લૂપબેક ડેશબોર્ડ હોસ્ટ પર જ્યાં પ્રોબ ક્લાયન્ટ-પક્ષે છોડી દેવામાં આવે છે, `unavailable` એકવાર પ્રોબ કરવામાં આવે છે અને ખોટું હોવાનું પુષ્ટિ કરવામાં આવે છે, અથવા `available` FFmpeg/ffprobe સંસ્કરણો સાથે) — સક્રિય/મોડલ/ફ્રેમ/વિડિયો/ટાઇમઆઉટ મર્યાદાઓ જાળવે છે, મોડલ પિકરને દ્રષ્ટિ-ક્ષમ મોડલ્સ સુધી મર્યાદિત કરે છે, અને વિડિયો કાઉન્ટર્સને પ્રદર્શિત કરે છે.

AI સેટિંગ્સ હેઠળનો પૂર્વ વિઝન બ્રિજ કાર્ડ નવા પેજ માટે એક સુસંગતતા લિંક છે; તે ફોર્મની બીજી નકલનો માલિક નથી. મીડિયા પ્રદાતાઓ પણ છબી-થી-ટેક્સ્ટ અને ભાષણ-થી-ટેક્સ્ટ વર્કફ્લોને સંબંધિત મોડાલિટી બ્રિજ ટેબ્સ સાથે લિંક કરે છે જે અસ્તિત્વમાં રહેલા ભાષણ-થી-ટેક્સ્ટ પ્લેગ્રાઉન્ડને દૂર કર્યા વિના.

**સ્વ-લૂપ પ્રવેશ બાયપાસ:** જ્યારે વર્ણન કૉલ ઓમ્નીરૂટના પોતાના `/v1` સ્વ-લૂપ (અસામાન્ય પ્રદાતા મોડેલ) દ્વારા માર્ગદર્શન કરે છે, ત્યારે ઉપ-વિનંતી `x-omniroute-admission-bypass: internal` મોકલે છે અને ઉકેલાયેલ સ્વ-લૂપ ક્રેડેંશિયલ સાથે માન્યતા પ્રાપ્ત થાય છે — સ્થાનિક મોડમાં સ્થાનિક `sk_omniroute` સેન્ટિનલ, અથવા ઓપરેટર-કન્ફિગર કરેલ `OMNIROUTE_API_KEY` / `ROUTER_API_KEY` env કી (#1350) જેથી `REQUIRE_API_KEY=true` ડિપ્લોયમેન્ટ હજુ પણ વર્ણન કૉલ ચલાવી શકે છે. બાયપાસ ફક્ત તે ચોક્કસ ક્રેડેંશિયલ્સ માટે માન્ય છે, તેથી બાહ્ય ક્લાયન્ટો પ્રવેશને બાયપાસ કરવા માટે હેડરનો ઉપયોગ કરી શકતા નથી.

વૈશ્વિક ડિફોલ્ટ્સ `src/shared/constants/visionBridgeDefaults.ts` માં રહે છે; નવા મોડ/કાર્ય-જાણકારી/કેશ ડિફોલ્ટ્સ અને સેટિંગ્સ રિઝોલ્વર `src/shared/constants/modalityBridgeDefaults.ts` માં રહે છે. ગાર્ડરેલ એક `deps` કન્સ્ટ્રક્ટર વિકલ્પ પ્રદર્શિત કરે છે જેથી પરીક્ષણો નકલી `getSettings` અને `callVisionModel` અમલને ઇન્જેક્ટ કરી શકે.

### ઓડિયો બ્રિજ (`audioBridge.ts`) — મોડાલિટી બ્રિજ PR-3

ઓડિયો ધરાવતી ચેટ વિનંતીઓને લક્ષ્ય સુધી પહોંચતા પહેલા અટકાવે છે જે ઓડિયો ઇનપુટ સ્વીકારવા માટે જાણીતી નથી. તે ક્યારેય ચેટ વિનંતીને ફરીથી માર્ગદર્શન આપતું નથી: ઓડિયો ભાગો અસ્તિત્વમાં રહેલા OpenAI-સંગત મલ્ટિપાર્ટ એન્ડપોઇન્ટ દ્વારા લખવામાં આવે છે અને પસંદ કરેલ ચેટ મોડલ લખાણના ટ્રાન્સક્રિપ્ટ સાથે ચાલુ રહે છે.

પ્રવાહ:

1. `supportsAudio` ને `getResolvedModelCapabilities()` દ્વારા ઉકેલવું. સ્પષ્ટ પ્રદાતા-રજિસ્ટ્રી મેટાડેટા જીતે છે, પછી સ્થિર મોડલ મેટાડેટા, પછી સમન્વિત `modalities_input` . `audio` વિના જાહેર કરેલ ઇનપુટ યાદી `false` છે; કોઈ ક્ષમતા પુરાવા `null` રહે છે. બંને `false` અને `null` સંરક્ષણાત્મક બ્રિજને સક્રિય કરે છે, જ્યારે `true` તેને બાયપાસ કરે છે.
2. `modalityBridgeAudio*` સેટિંગ્સને ઉકેલવું અને દરેક સંદેશામાંથી શેર કરેલ `detectMediaParts()` ડિટેક્ટર દ્વારા સ્પ્લાઇસેબલ ટોપ-લેવલ ઓડિયો ભાગો કાઢવા. સમર્થિત વાયર આકારો OpenAI `input_audio`, `audio_url`, અને `source.media_type: "audio/*"` છે. નેસ્ટેડ ઓડિયો માર્ગદર્શન માટે શોધવામાં આવે છે પરંતુ સ્પ્લાઇસ પાથ દ્વારા દૂર કરવામાં આવતું નથી. કાર્ય `modalityBridgeAudioMaxClips` દ્વારા મર્યાદિત છે; પછીના ભાગો અસ્પષ્ટ રહે છે.
3. એક કન્ફિગર કરેલ `provider/model`ને માન્યતા આપો, અથવા `selectAudioBridgeModel()` ને સ્થિર કૅટલોગ ક્રમમાં `AUDIO_TRANSCRIPTION_PROVIDERS` ને ચાલવા દો અને ઉપયોગી સક્રિય પ્રદાતા ક્રેડેંશિયલ સાથે પ્રથમ મોડલ પસંદ કરો.
4. `callAudioTranscription()` base64/data-URI ઓડિયોને મલ્ટિપાર્ટ `ફાઇલ`માં રૂપાંતરિત કરે છે, અથવા જાહેર-માત્ર આઉટબાઉન્ડ ગાર્ડ દ્વારા DNS પિનિંગ અને 25 MB બાઉન્ડ સાથે એક દૂરના `audio_url`ને ડાઉનલોડ કરે છે. તે પછી ફાઇલ અને પસંદ કરેલ મોડલને સ્થાનિક `/v1/audio/transcriptions` સ્વ-લૂપમાં પોસ્ટ કરે છે, જે `resolveSelfLoopBearer()` સાથે માન્યતા પ્રાપ્ત છે. અસ્તિત્વમાં રહેલ ટ્રાન્સક્રિપ્શન માર્ગ સામાન્ય ક્રેડેંશિયલ શોધ, કૂલડાઉન/દર-મર્યાદા હેન્ડલિંગ, અને પ્રદાતા વિતરણ કરે છે.
5. સફળ કૉલ તેમના ભાગોને `[Audio N]: <transcript>` સાથે બદલાવે છે. કૉલ `Promise.allSettled` સાથે ચાલે છે: એક વ્યક્તિગત નિષ્ફળતા મૂળ ઓડિયો ભાગને જાળવે છે (#4012 કરાર). જો દરેક કૉલ નિષ્ફળ જાય અને લક્ષ્યને સાબિત કરવામાં આવે `supportsAudio === false`, તો ભાગો બની જાય છે `[Audio N]: (unavailable — no STT provider connected)` (#8430 કરાર). અજાણ્યા લક્ષ્ય માટે (`null`), એક તમામ-નિષ્ફળ પરિણામ અસ્પષ્ટ રહે છે. એક સાબિત થયેલ ટેક્સ્ટ-માત્ર લક્ષ્ય જે કોઈ ઉપયોગી STT ક્રેડેંશિયલ નથી, તે નેટવર્ક કૉલ કર્યા વિના સમાન સ્પષ્ટ સ્ટબ પ્રાપ્ત કરે છે.

સફળ ટ્રાન્સક્રિપ્ટો પ્રક્રિયા-વિશાળ મોડાલિટી બ્રિજ LRU/TTL કેશનો ઉપયોગ કરે છે. કી ઓડિયો સંદર્ભ, સ્થિર `audio-transcription` ઓપરેશન લેબલ, અને પસંદ કરેલ STT મોડલને જોડે છે; નિષ્ફળતાઓ ક્યારેય કેશ કરવામાં આવતી નથી. ઓડિયો પ્રયાસો શેર કરેલ `bridged`, `cacheHits`, `failures`, અને `lastUsedAt` કાઉન્ટર્સને અપડેટ કરે છે. રૂપાંતરિત પ્રતિસાદો ધરાવે છે `x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>`; અસ્પષ્ટ વિનંતીઓને ઓડિયો બ્રિજ વિભાગ પ્રાપ્ત નથી.

રનટાઇમ સેટિંગ્સ DB-આધારિત અને Zod-માન્યતા પ્રાપ્ત છે:

| કી                            | ડિફોલ્ટ | શ્રેણી          |
| ----------------------------- | ------- | --------------- |
| `modalityBridgeAudioEnabled`  | `true`  | —               |
| `modalityBridgeAudioModel`    | `""`    | ઓટો અથવા STT ID |
| `modalityBridgeAudioTimeout`  | `60000` | 1000–300000     |
| `modalityBridgeAudioMaxClips` | `3`     | 1–10            |

શેર કરેલ કેશ `modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes`, અને `modalityBridgeCacheMaxEntries` દ્વારા નિયંત્રિત રહે છે.

### વિડિયો બ્રિજ (`videoBridge.ts`, `videoBridgePipeline.ts`)

ટોચના સ્તરના વિડિઓ ભાગોને ચેટ પૂર્ણતાઓ `messages` અને પ્રતિસાદો API `input` માંIntercept કરે છે, જ્યારે કોઈ લક્ષ્યને ઓળખવામાં આવતી સ્થાનિક વિડિઓ સપોર્ટ નથી. સમર્થિત આકારો છે `input_video`, `video_url`, `video_source`, HTTPS URLs, અને `data:video/*;base64,...` ડેટા URI. ટેક્સ્ટમાં સાદા ફાઇલ નામોને વિડિઓ તરીકે માનવામાં આવતું નથી.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) વિનંતી પસાર કરવાનું, ક્ષમતા/નીતિ ચકાસવું, પ્રતિ વિનંતી સંકલન, અને પ્રતિસાદ પેલોડનું માલિકી ધરાવે છે. પ્રતિ વિડિઓ કાર્ય — પ્રાપ્ત કરવું, સમગ્ર પરિણામ કેશ, ફ્રેમ ક્રમનું વર્ણન (જે કોઈ પણ caller-ઘોષિત ઓડિયો ટ્રાન્સક્રિપ્ટને મિશ્રિત કરે છે), અને પ્રતિ પ્રયાસ મેટ્રિક્સ/રદ/સફાઈ — `processVideoPart` પાછળ છુપાયેલું છે `videoBridgePipeline.ts` માં, જે `preCall` ના લૂપમાં પ્રતિ વિડિઓ ભાગ માટે એકવાર બોલાવવામાં આવે છે. તે મોડ્યુલ સ્પષ્ટ પોર્ટ સીમાઓને પણ વ્યાખ્યાયિત કરે છે `VideoMediaBrokerPort` (બાઇટ્સ મેળવવું અને નમૂનાકૃત ફ્રેમ્સ કાઢવું), `VideoAudioTranscriptionPort` (નમૂનાકૃત શીર્ષકો સાથે caller-ઘોષિત ઓડિયો ટ્રાન્સક્રિપ્ટને મિશ્રિત કરવું), અને `VideoDrilldownPort` (પરંપરાગત કાચા-સ્ટોર આકાર). ઉત્પાદન STT અને ફ્રેમ જાળવણી વર્ણન પોર્ટની આસપાસ રચાયેલ છે `createVideoSttAdapter` અને `createVideoDrilldownAdapter`; છેલ્લું શેર કરેલ ઓપેક-હેન્ડલ જીવનચક્રનો ઉપયોગ કરે છે.

જાહેર `/v1` વિનંતી માર્ગ ક્યારેય ઉપક્રમે અથવા ઉપપ્રક્રિયા શરૂ કરતું નથી. દૂરના વિડિઓ 50 MiB મર્યાદા હેઠળ ડાઉનલોડ કરવામાં આવે છે; ઇનલાઇન બેસ64 વિડિઓમાં 36 MiB ડિકોડેડ પ્રતિ-વિડિઓ મર્યાદા છે જેથી મોડેલ/સંદેશો/ફ્રેમિંગ લિફાફો જાહેર JSON વિનંતી પ્રવેશ મર્યાદા 50 MiBની અંદર રહી શકે. ઇનલાઇન લંબાઈ અને ડિકોડ કરેલ કદના અંદાજો ફાળવણી પહેલાં ચકાસવામાં આવે છે. HTTPS પ્રારંભિક દૂરના URL અને દરેક પુનઃદિશા પર જરૂરી છે, જે અસ્તિત્વમાં રહેલા જાહેર-માત્ર આઉટબાઉન્ડ ગાર્ડ સાથે DNS પિનિંગનો ઉપયોગ કરે છે. બાઇટ્સ પછી ચોક્કસ આંતરિક `POST /api/modality-bridge/video/extract` બ્રોકર સીમાને પાર કરે છે. તે માર્ગ `LOCAL_ONLY` અને `SPAWN_CAPABLE` છે, ફક્ત પ્રતિ-પ્રક્રિયા માન્ય, વિશ્વસનીય-લૂપબેક વિનંતી સ્વીકારે છે, અને ક્યારેય URL, ફાઇલ સિસ્ટમ પાથ, કાર્યક્ષમ, અથવા દલીલ યાદી સ્વીકારતું નથી. API બોડી-કદ પાઇપલાઇન અને હેન્ડલરના અંકલન બોડી રીડર સ્વતંત્ર રીતે 50 MiB બ્રોકર ઇનપુટ મર્યાદાને અમલમાં લાવે છે. તેની મર્યાદિત ક્યૂ એક સમયે એક જ નિષ્કર્ષણ ચલાવે છે, ચાર પેન્ડિંગ નોકરીઓની મંજૂરી આપે છે, અને પેન્ડિંગ ઇનપુટને 100 MiB પર મર્યાદિત કરે છે.

બ્રોકરમાં, `ffprobe` એક ખાનગી સ્થાનિક ફાઇલ વાંચે છે; નિશ્ચિત ફોર્મેટ મંજૂરી યાદી પ્લેલિસ્ટ અને મેનિફેસ્ટ ફોર્મેટને બહાર કરે છે. મંજૂર MOV-પરિવારના કન્ટેનરો માટે, બાહ્ય MOV ડેટા સંદર્ભો ડિફોલ્ટ દ્વારા નિષ્ક્રિય રહે છે, અને નિશ્ચિત આદેશ તેમાં સામેલ નથી. બંને `ffprobe` અને `ffmpeg` `file`-માત્ર પ્રોટોકોલ વ્હાઇટલિસ્ટ, એક થ્રેડ, નિશ્ચિત દલીલ એરે, કોઈ શેલ, અને `PATH`માંથી ઉકેલાયેલ કાર્યક્ષમનો ઉપયોગ કરે છે. જોડાયેલ-ચિત્ર કવર સ્ટ્રીમ્સ રમવા માટેના ઉમેદવારો નથી. તમામ રમવા માટેના સ્ટ્રીમ્સ મર્યાદાઓને સંતોષવા જોઈએ, અને એક સ્પષ્ટ ડિફોલ્ટ સ્ટ્રીમ નિર્ધારિત સૌથી નીચા-ઇન્ડેક્સ બેકઅપ પહેલાં પસંદ કરવામાં આવે છે. વિડિઓ 600 સેકંડ, 8,192 પિક્સલ પ્રતિ પરિમાણ, અને 33,554,432 સ્ત્રોત પિક્સલ સુધી મર્યાદિત છે. FFmpeg 1–16 મધ્યબિંદુ JPEG ફ્રેમ્સનું નમૂનાકરણ કરે છે, લાંબા કિનારે 1,024 પિક્સલ સુધીની ઊંચાઈમાં ઘટાડે છે, નાના ઇનપુટને અપસ્કેલ કર્યા વિના, અને ક્યારેય URL પ્રાપ્ત નથી કરે. નમૂનાકરણ ડિફોલ્ટ દ્વારા `uniform` છે. વૈકલ્પિક `scene_aware` અને પ્રયોગાત્મક `segment_aware` નીતિઓ પહેલાથી માન્ય સ્થાનિક સ્ટ્રીમ પર એક વધારાનો નિશ્ચિત FFmpeg પસાર કરે છે, મર્યાદિત `showinfo` દૃશ્ય સમયચિહ્નો પસંદ કરે છે, અને નિર્ધારિત રીતે નિશ્ચિત મધ્યબિંદુઓ પર પાછા ફરે છે જ્યારે ડિટેક્ટર નિષ્ફળ થાય છે, સમય મર્યાદા, ખોટા આઉટપુટ, અથવા ખાલી ઉમેદવાર સેટ. સેગમેન્ટ-જાણકાર મોડ માન્ય દૃશ્ય અંતરાલને અનુરૂપ મધ્યબિંદુ નમૂનાઓ ફાળવે છે; સેગમેન્ટ-જાણકાર પુરાવા અને બેકઅપ વર્તન નીચે વિગતવાર છે. કઠોર 16-ફ્રેમ મર્યાદા દરેક નીતિમાં પસંદગી પછી લાગુ થાય છે. જ્યારે દૃશ્ય-જાણકાર વિનંતીમાં ફક્ત એક-ફ્રેમ બજેટ હોય છે, ત્યારે તે સક્રિય સંપૂર્ણ-વિડિઓ અથવા ફોકસ વિન્ડોના સમાન મધ્યબિંદુનો ઉપયોગ કરે છે અને `policyEffective: uniform`ને અહેવાલ આપે છે: એક જ પસંદ કરેલ દૃશ્ય ફ્રેમ બંને સમયના અંતોને જાળવી શકતું નથી. એક caller વૈકલ્પિક રીતે એક મર્યાદિત ફોકસ વિન્ડો (`start`/`end` સેકંડ) પ્રદાન કરી શકે છે; મર્યાદાઓ મીડિયા સમયગાળા પર કંપન કરવામાં આવે છે, વળાંક અથવા અવિરત વિન્ડોને રદ કરવામાં આવે છે, અને તમામ નમૂનાકરણ નીતિઓ માત્ર માન્ય અંતરાલની અંદર કરવામાં આવે છે. પરિણામે વિન્ડો નમૂનાકરણ મેટાડેટા અને અવિશ્વસનીય વર્ણન પૂર્વફેક્સમાં સમાવિષ્ટ છે જેથી નીચેના મોડેલો ફોકસ કરેલ ઉદાહરણને સંપૂર્ણ સમયરેખામાંથી અલગ કરી શકે.

સેમેન્ટિક કૅપ્શન ફોકસ એક અલગ, સ્પષ્ટ સેટિંગ છે. ડિફોલ્ટ `full` વિશ્લેષણ મોડ અસ્તિત્વમાં રહેલા ફ્રેમ પ્રોમ્પ્ટને જાળવે છે અને ક્યારેય વિનંતી ટેક્સ્ટને કૅપ્શન મોડેલને આગળ મોકલતું નથી. `focused` મોડમાં, બ્રિજ ફક્ત સમાન ચેટ અથવા પ્રતિસાદ કન્ટેનરમાંથી તાજેતરના નોન-એમ્પ્ટ યુઝર-લેખિત `text`/`input_text`ને વાંચે છે, તેને NFCમાં સામાન્ય બનાવે છે, નિયંત્રણ અક્ષરો અને ખાલી જગ્યા ઘટાડી દે છે, અને તેને 500 યુનિકોડ કોડ પોઈન્ટ્સ સુધી મર્યાદિત કરે છે. ખાલી પરિણામ ચોક્કસ `full` પ્રોમ્પ્ટ પર પાછું ફરે છે. ઉપયોગી સંકેત એક સમર્પિત અવિશ્વસનીય-યુઝર-સંદર્ભ બ્લોકમાં JSON તરીકે સીરિયલાઇઝ કરવામાં આવે છે અને ફક્ત દેખાય તે વિગતોને પ્રાથમિકતા આપી શકે છે; તે મીડિયા માં દેખાતા અથવા સાંભળાતા સૂચનોને અનુસરણ કરવા વિરુદ્ધની અલગ ચેતવણીને ઓવરરાઈડ કરી શકતું નથી. ટેક્સ્ટ્યુઅલ ફોકસ ક્યારેય `start`/`end`ને અનુમાનિત નથી કે સમયના નમૂનાકારને બદલે નથી.

#### FU-07 બંધારણ વિભાગ પુરાવો

`segment_aware` પહેલાથી માન્ય સ્થાનિક વિડિઓ સ્ટ્રીમ પર એક મર્યાદિત પૂર્વ-વિશ્લેષણ પસાર કરે છે. નિશ્ચિત ફિલ્ટર ચેઇન પ્રથમ 320 પિક્સલ પહોળાઈમાં સ્કેલ કરે છે, દૃશ્ય પરિવર્તનો અને જમણાં સમયગાળા શોધે છે, પછી ધૂંધળા, સરેરાશ લ્યુમા, અને સ્થાન/સમયની માહિતી માટે પ્રતિ સેકંડ 1 ફ્રેમ નમૂનાકરણ કરે છે. પસાર 600 બંધારણ નમૂનાઓ, એક FFmpeg/ફિલ્ટર થ્રેડ, સમાન `file`-માત્ર પ્રોટોકોલ અને કન્ટેનર મંજૂરી યાદીઓ, 1 MiB પ્રક્રિયા-આઉટપુટ મર્યાદા, અને બ્રોકરના શેર કરેલ રદ/સમય મર્યાદામાં 30 સેકંડ સુધી મર્યાદિત છે. તે ક્યારેય વિનંતીમાંથી આદેશ, ફિલ્ટર, પાથ, અથવા URL સ્વીકારતું નથી.

ધાંધલાના મૂલ્યો નિર્ધારિત નમૂના પુરાવા છે, અર્થપૂર્ણ વિડિયો સમજણ નથી. તેઓ વિષયો, ક્રિયાઓ, શીર્ષકો, ભાષણ, અથવા વપરાશકર્તા ઇરાદા અનુમાનિત નથી. દૃશ્ય અને ફ્રીઝ સીમાઓ વિભાગો બનાવે છે; ફ્રીઝ કવરેજ, ધૂંધળાપણું, એક્સપોઝર, જગ્યા વિગતો, અને સમયગાળા બદલાવ માત્ર તે કેવી રીતે વર્તે છે તે પ્રભાવિત કરે છે જે હાલના 1–16 ફ્રેમ બજેટને ફાળવવામાં આવે છે. સંપૂર્ણ રીતે ફ્રીઝ થયેલ વિભાગ એક ફ્રેમ પર મર્યાદિત છે, જ્યારે નોન-ફ્રીઝ વિભાગો બાકી બજેટ માટે સ્પર્ધા કરે છે. જ્યારે સીમાઓ ફ્રેમ્સની સંખ્યાને વધુ હોય છે, ત્યારે સમાન સમયરેખા કવરેજ જાળવવામાં આવે છે જેથી ઝડપી પ્રારંભિક કટ્સ લાંબા પછડાટ વિભાગને છુપાવી ન શકે. 1-સેકન્ડના વિશ્લેષણના ઉકેલમાં ફ્રીઝ સીમાના અંદર દૃશ્ય સીમાઓ એકત્રિત થાય છે.

ગાયબ ફિલ્ટર્સ, ખોટા/ખાલી પુરાવા, ડિટેક્ટર ભૂલ, અથવા બાઉન્ડેડ પ્રી-વિશ્લેષણ ટાઇમઆઉટ ચોક્કસ સમાન મધ્ય બિંદુ નીતિ તરફ ખૂલે છે. એક કૉલર રદ અથવા બ્રોકર ડેડલાઇન ખૂલે નહીં: તે ફ્લાઇટમાં રહેલા સબપ્રોસેસને સમાપ્ત કરે છે, પછીના ફ્રેમ એક્સટ્રાક્શનને રોકે છે, અને ખાનગી તાત્કાલિક વૃક્ષ `finally` માં દૂર કરવામાં આવે છે.

`scripts/perf/video-bridge-fu07-eval.ts` પોસ્ટ-ડેડુપ શીર્ષક-કૉલ બચત, ઘન-મોશન બજેટ ફાળવણી, ધૂંધળાપણું/એક્સપોઝર/SI-TI પુરાવા, લાંબા પછડાટ સાથે ઝડપી કટ્સ, અને ધીમે-ફેડ ખોટા પોઝિટિવ્સ માટે નિર્ધારિત વાસ્તવિક FFmpeg ફિક્ચર્સ બનાવે છે. તે પ્રી-વિશ્લેષણની દિવાલનો સમય નોંધે છે અને જ્યાં `/usr/bin/time` ઉપલબ્ધ છે, ત્યાં બાળક CPU અને પીક RSS. તેની ગુણવત્તા ચકાસણીઓ ઢાંચાકીય ઓરેકલ્સ માત્ર છે. વાસ્તવિક શીર્ષક-મોડલની ગુણવત્તા `HOLD` પર રહે છે કારણ કે આ હાર્નેસ પાસે કોઈ અધિકૃત અંતિમ બિંદુ અથવા ફ્રીઝ જજ નથી. નાણાકીય બચત પણ `HOLD` પર રહે છે જો `--caption-cost-per-call-usd` સ્પષ્ટ સકારાત્મક પ્રતિ-કૉલ અંદાજ પૂરો પાડે છે; સ્ક્રિપ્ટ ક્યારેય કોઈપણ પરિણામ બનાવતી નથી.

પ્રત્યેક ફ્રેમ 4 MiB સુધી મર્યાદિત છે, તમામ કાચા ફ્રેમો સાથે 23 MiB સુધી, અને સીરિયલાઇઝ્ડ બ્રોકર પ્રતિસાદ 32 MiB સુધી. એક ખાનગી તાત્કાલિક ડિરેક્ટરી `finally` માં દૂર કરવામાં આવે છે. ઓમ્નીરૂટ FFmpegને બંડલ નથી કરતી અને કસ્ટમ એક્ઝિક્યુટેબલ પાથ સ્વીકારતી નથી. શીર્ષક આપ્યા પહેલા, બ્રિજ એક સંરક્ષણાત્મક દૃશ્ય ડેડુપ્લિકેશન પાસ લાગુ કરે છે: દરેક JPEGને 16×16 ગ્રેસ્કેલ બફરમાં ઘટાડવામાં આવે છે અને તે માત્ર છેલ્લી ફ્રેમ સાથે સરખાવવામાં આવે છે જે જાળવવામાં આવે છે. એક ફ્રેમથી વધુની માંગેલી શીર્ષક બજેટ માટે, એક્સટ્રાક્શન 16 ફ્રેમ્સથી વધુ ક્યારેય નહીં, તે બજેટના બે ગણી શકાય તેવા ઉમેદવારો પૂરા પાડે છે. માંગેલી મર્યાદા ડેડુપ્લિકેશન પછી જ લાગુ થાય છે, પ્રથમ અને અંતિમ પસંદ કરેલા ઉમેદવારોને અંતિમ પાતળા દરમિયાન જાળવવામાં આવે છે જ્યારે બજેટ ઓછામાં ઓછા બે હોય. સંસ્કરણવાળા `grayscale-16x16-mean-cells-v2` નીતિમાં સરેરાશ લ્યુમા ડેલ્ટા અને થંબનેલ સેલ્સનો ગુણોત્તર ઉપયોગ થાય છે જેના નોર્મલાઇઝ્ડ ડેલ્ટા ઓછામાં ઓછા 0.05 છે. ડુપ્લિકેટ થ્રેશોલ્ડ સ્થિર 0.04 છે, જે આગાહી માટે પસંદ કરવામાં આવી છે, નાની મોશન અને દૃશ્ય-ટેક્સ્ટ બદલાવ જાળવવા માટે. કોમ્પેરેટર અથવા ડિકોડર ભૂલો ખૂલે છે અને કવરેજ જાળવે છે. આઉટપુટ મેટાડેટા એક્સટ્રાક્ટેડ ઉમેદવારો, સફળતાપૂર્વક ઉપયોગમાં લેવાયેલા ફ્રેમ્સ, અને દૃશ્ય ડુપ્લિકેટ્સને અલગ કરે છે.

એક સ્પષ્ટ રીતે માર્ક કરેલ વિડિયો ભાગે ટાઇમસ્ટેમ્પ્ડ સંપર્ક શીટની માંગ કરી શકે છે. બ્રિજ મહત્તમ 4-કોલમ, 16-ફ્રેમ JPEG ગ્રિડ બનાવે છે. દરેક 512-પિક્સેલ સેલ તેના સ્ત્રોતના ટાઇમસ્ટેમ્પને ઉચ્ચ-વિરોધી તળિયાના બૅન્ડમાં બર્ન કરે છે, જ્યારે તે જ ટાઇમસ્ટેમ્પ્સ ટેક્સ્ટ મેટાડેટામાં નીચેના સંસાધન અને ઓડિટ માટે રહે છે. સંપૂર્ણ JPEG 32 MiB પર મર્યાદિત રહે છે. જો `sharp` ગ્રિડને ડિકોડ અથવા રચવા માટે અસમર્થ છે, તો બ્રિજ વ્યક્તિગત JPEG ફ્રેમ્સ પર પાછા જાય છે; એક ક્લાયન્ટ રદ હજુ પણ શીટ ઓપરેશનમાં પ્રસારિત થાય છે.

પ્રમોશન પુરાવો故意 રીતે સંશ્લેષણ રચના માઇક્રોબેન્ચમાર્કથી અલગ છે. `scripts/perf/video-bridge-contact-sheet-eval.ts` વાસ્તવિક OpenAI-સંગત દૃષ્ટિ મોડલ માટે એક સ્કીમા-સંસ્કરણિત A/B હાર્નેસ વ્યાખ્યાયિત કરે છે. તે પ્રદાતા-અહેવાલિત ટોકન્સ, અંત-થી-અંત દિવાલની વિલંબ (શીટ રચનાને સમાવેશ કરીને), મોડલ-કૉલ ગણતરી, અને મેનિફેસ્ટ-વ્યાખ્યાયિત તથ્ય જાળવણીને માપે છે. કાચા મોડલના પ્રતિસાદો રિપોર્ટમાં લખવામાં આવતાં નથી; ફક્ત SHA-256 ડિજેસ્ટ અને મેળ ખાતા તથ્ય ID જ રાખવામાં આવે છે. હાર્નેસ કોઈ નેટવર્ક અથવા ચૂકવેલ મોડલ કૉલ નથી કરતી જો `--execute-real` પસાર કરવામાં આવે છે અને `--model`, `OMNIROUTE_BASE_URL`, અને `OMNIROUTE_API_KEY` કન્ફિગર કરવામાં આવે છે. તે સ્પષ્ટ વાસ્તવિક ચલાવ્યા વિના, તેની મશીન-વાંચનક્ષમ ચુકાદો `HOLD` પર રહે છે; સંશ્લેષણ પે લોડ/કૉલ-ગણતરીના માપ જ પ્રમોશન પુરાવો નથી.

અલગ `scripts/perf/video-bridge-promotion-eval.ts` FU-07 અથવા FU-09 અવલોકનોનો ઉપયોગ કરે છે. પ્રમોશન પ્રવેશ માટે તમામ આઠ સંશ્લેષણ દૃશ્ય પ્રકારો અને એક સાફ કરેલ વાસ્તવિક ક્લિપની જરૂર છે, દરેક ભૂમિકા અને કેસ માટે ઓછામાં ઓછા ત્રણ માપેલા પુનરાવૃત્તિઓ, તમામ દસ જાહેર કરેલ મેટ્રિક્સ, ફ્રીઝ મીડિયા/પ્રોમ્પ્ટ/અપેક્ષિત-તથ્ય/સેટિંગ્સ ડિજેસ્ટ, અનન્ય અવલોકન ID અને માન્ય બીજિત A/B ક્રમ. અમલનો રસીદ કોર્પસ ડિજેસ્ટ, ચોક્કસ ઉમેદવાર SHA અને મોડલ સંસ્કરણને બાંધે છે. ગાયબ અથવા અમાન્ય માપો `HOLD` પર રહે છે, જેમાં CPU 30 સેકન્ડથી વધુ, પીક RSS 512 MiBથી વધુ અથવા પ્રી-વિશ્લેષણ 30 સેકન્ડથી વધુ હોય છે. આ પુરાવા-પ્રવેશ મર્યાદાઓ છે, નવી રનટાઇમ RSS અમલમાં લાવવાની ખાતરી નથી.

FU-07 માટે ઓછામાં ઓછા 98% ગુણવત્તા જાળવણી અને p95 વિલંબ 1.2x બેઝલાઇનથી વધુ નહીં, તેમજ સમાન સરેરાશ શીર્ષક કૉલ્સ પર 0.05 સંપૂર્ણ કેસ-સંતુલિત સરેરાશ પુનઃપ્રાપ્તિ સુધારો, અથવા ઓછામાં ઓછા 10% ઓછા સરેરાશ પોસ્ટ-ડેડુપ શીર્ષક કૉલ્સની જરૂર છે. FU-09 માટે ઓછામાં ઓછા 0.85 ગુણવત્તા, 95% જાળવણી, 20% p95 વિલંબ ઘટાડો અને 10% ટોકન ઘટાડો જરૂરી છે. મહત્વપૂર્ણ-તથ્ય ગુમાવવું, ઇન્જેક્શન અનુરૂપતા અથવા ગાયબ ઉપયોગ પ્રમોશનને રોકે છે. એક અમલ ક્યારેય કંઈપણ પ્રમોટ કરી શકતું નથી: `--previous-report` સમાન નીતિ/મોડલ સંસ્કરણ/ઉમેદવાર/કોર્પસના બે અલગ, નોન-ઓવરલેપિંગ, અનુક્રમણિકા માટેની લાયકાત ધરાવતી અમલની પુષ્ટિ કરે છે. એક નમૂના પ્રયોગ સંપર્ક-શીટ પ્રયોગની પુષ્ટિ કરી શકતું નથી.

કલેક્શન કરનારોએ યાદીમાં જવાબોનું સ્કોરિંગ કરવું જોઈએ અને `responseDigest` સાથે મેટ્રિક્સ અને અવલોકન બાઇન્ડિંગ્સને સાચવવું જોઈએ, ક્યારેય જવાબના લખાણને નહીં. ગ્રાહક પણ વારસાગત કાચા અવલોકનોને વાંચે છે પરંતુ ક્યારેય તે લખાણને તેની અહેવાલોમાં નકલ નથી કરે. દરેક અવલોકન માટે `responseDigest` અથવા `rawResponseText` માંથી ચોક્કસ એક સ્વીકારવામાં આવે છે. સંસ્કરણવાળા મંજૂરી યાદી ખાલી રહે છે જેમાં અપરિવર્તિત `hold` ડિફોલ્ટ છે. એક યોગ્ય પ્રવેશ માટે તેની પુરાવાની સંદર્ભ, નીતિ, મોડલ સંશોધન, ચોક્કસ ઉમેદવાર SHA, મેનિફેસ્ટ ડિજેસ્ટ અને બે અલગ-અલગ ચલાવવાની IDની જરૂર છે; વિરુદ્ધ સંદર્ભોને નકારી દેવામાં આવે છે. આ મેટાડેટા એક ઓડિટ કરાર છે, જે દર્શાવે છે કે સંદર્ભિત ફાઈલમાં સાચી માપદંડો છે. કોઈપણ પ્રવેશ ઉમેરવા પહેલાં વાસ્તવિક રસીદોની સમીક્ષા કરો. મેનેજમેન્ટ સ્ટેટ્સ એન્ડપોઈન્ટ અને વિડિયો ડેશબોર્ડ સંરક્ષણાત્મક તૈયારીઓ દર્શાવે છે. એક રૂપરેખાંકિત મોડલ ઉપનામ જ તેની સંશોધન અથવા ચાલતી ઉમેદવાર SHA સ્થાપિત નથી કરતી, તેથી વર્તમાન ડેશબોર્ડ `HOLD`ને રિપોર્ટ કરે છે, અન્ય અમલના સંદર્ભમાંથી યોગ્યતા પુનઃઉપયોગ કરતા. સ્પષ્ટ પ્રયોગાત્મક પસંદગી પ્રમોશનથી અલગ રહે છે; કોઈ ડિફોલ્ટ આપોઆપ બદલાતું નથી.

કોલર્સે સમર્થિત વિડિયો ભાગ સાથે વૈકલ્પિક `transcript.cues` એરે જોડવું શક્ય છે જ્યારે તેઓ પહેલેથી જ સંકલિત લખાણ ધરાવે છે. દરેક ક્યૂમાં `text`, એક મર્યાદિત `start`/`end` અંતર હોવું જોઈએ જે તપાસવામાં આવેલી અવધિની અંદર હોય, અને એક વ્હાઇટલિસ્ટેડ `source` (`client`, `embedded`, અથવા `audio-bridge`); `confidence` ડિફોલ્ટ તરીકે `1` છે અને `0` અને `1` વચ્ચે રહેવું જોઈએ. ચોક્કસ નકલ ક્યૂઓને સમકક્ષ કરવામાં આવે છે. ઓમ્નીરૂટ આ મેટાડેટા પરથી ટ્રાન્સક્રિપ્શન શરૂ કરતું નથી: માન્ય ક્યૂઓને વર્ણવેલ પરિણામમાં સ્ત્રોત, વિશ્વસનીયતા અને અંતર સાથે નકલ કરવામાં આવે છે, અને ફ્રેમ કૅપ્શન સાથે અવિશ્વસનીય અવલોકનો તરીકે રજૂ કરવામાં આવે છે. અમાન્ય, રેન્જની બહાર, અથવા પુરાવા-મુક્ત લખાણને કૅપ્શન સ્ટ્રીમમાં મિશ્રિત કરવામાં આવે છે. બંને વિનંતી-શરીર ટ્રાન્સક્રિપ્ટ ચેનલ્સ પુરવઠા પુરાવાને `client`માં નોર્મલાઇઝ કરે છે, જેમાં સ્વ-અધિકૃત `embedded` અથવા `audio-bridge` લેબલ્સનો સમાવેશ થાય છે. ફક્ત સર્વર-માલિક એડેપ્ટર જ આ વિશ્વસનીય લેબલ્સને કોડ-માત્ર `trustedSource` દલીલ દ્વારા સોંપી શકે છે; વિનંતી JSON ક્ષેત્ર તે દલીલ સુધી પહોંચી શકતું નથી. ટ્રાન્સક્રિપ્ટ લખાણ અવિશ્વસનીય મીડિયા-ઉપજિત સામગ્રી રહે છે, તેની પુરાવા કેવા હોય તે છતાં, અને ક્યારેય અધિકૃતતા નક્કી કરવી જોઈએ નહીં.

એક અદ્યતન કોલર સમાન વિડિયો માટે `audioTranscript` ટ્રેક પ્રદાન કરી શકે છે; તેને ક્લાયન્ટ-પ્રદાન કરેલ લખાણ તરીકે માનવામાં આવે છે, સર્વર ટ્રાન્સક્રિપ્શનનો પુરાવો નહીં. ફ્યુઝન સીમ એક જ સમયમર્યાદા અનેabort સંકેત હેઠળ દૃશ્ય અને ઓડિયો અવલોકનો ચલાવે છે, તેમને સામાન્ય સમયરેખા પર ઓર્ડર કરે છે, ચોક્કસ નકલને સમકક્ષ કરે છે, અને જ્યારે ફક્ત એક બાજુ સફળ થાય ત્યારે અંશિક પરિણામને રિપોર્ટ કરે છે. અમાન્ય `audioTranscript` તે અંશિક પરિણામમાં ઘટાડે છે - દૃશ્ય વર્ણન રાખવામાં આવે છે અને ઓડિયો શાખા એક સાફ કરવામાં આવેલ નિષ્ફળતા કોડને નોંધે છે - સમગ્ર વિડિયોને નિષ્ફળ બનાવવાની જગ્યાએ. દરેક શાખાની ઉપલબ્ધતા, અંશિક ધ્વજ, અને સાફ કરવામાં આવેલા નિષ્ફળતા કોડ્સ વર્ણવેલ પરિણામમાં, ગાર્ડરેલ મેટાડેટા (`audioFusionRuns`/`audioFusionPartials`/`audioFusionFailureCodes`), પરિણામ-કેશ મેટાડેટા, અને બ્રિજ ફ્યુઝન કાઉન્ટર્સમાં જાળવવામાં આવે છે. ડિફોલ્ટ વિડિયો બ્રિજ પાથ બોલી-થી-લેખનને પ્રેરિત નથી કરતી અથવા બીજું મીડિયા નકલ ડાઉનલોડ કરતી; તે સ્પષ્ટ ટ્રેક વિના, તે માત્ર વિડિયો રહે છે.

**ટ્રાન્સક્રિપ્ટ જાળવણી (#12150 P1).** જ્યારે વિડિયો બ્રિજ (તે પોતે ઓપ્ટ-ઇન) ટ્રાન્સક્રિપ્ટ ક્યૂને રજૂ કરે છે ત્યારે આ આપોઆપ લાગુ પડે છે - કોઈ અલગ જાળવણી ધ્વજ નથી. જ્યારે કોઈ વિનંતી કોઈપણ ટ્રાન્સક્રિપ્ટ ક્યૂ (એક કોલર-જાહેરાત `transcript` અથવા એક ફ્યુઝ્ડ `audioTranscript`)ને રજૂ કરે છે, ત્યારે ગાર્ડરેલ તેને `videoBridgeObserved` તરીકે માર્ક કરે છે અને વિડિયો વર્ણનનો એક રેડેક્ટેડ શેડો ઉત્પન્ન કરે છે - એક સમાન રેન્ડરિંગ જેમાં દરેક ક્યૂના મફત-લેખન શરીરને `[redacted-video-transcript]` દ્વારા બદલવામાં આવે છે, જે રચનાત્મક ક્યૂ ક્ષેત્રને બદલીને બનાવવામાં આવે છે પહેલાં સ્ટ્રિંગને એકત્રિત કરવામાં આવે છે (ક્યારેય સમકક્ષ લખાણને પાર્સ કરીને નહીં, તેથી કોઈ ક્યૂ સામગ્રી - વિરોધી અથવા સામાન્ય, જેમાં `]` ધરાવતી બોડી જેવી કે `[inaudible]`/`[music]` - જીવંત રહી શકતી નથી). જાળવેલ કોલ-લોગ વિનંતી શરીર દરેક વિડિયો-ઉપજિત લખાણના ભાગને તે રેડેક્ટેડ શેડો માટે બદલાવે છે, સામગ્રી સમાનતાના આધારે; `fullText` એન્કર પૂર્ણ થયેલ પૂર્વ-કોલ ગાર્ડરેલ પેઇલોડમાંથી ફરીથી વાંચવામાં આવે છે, તેથી મેચ પછીના ચેઇન ગાર્ડરેલ્સ (PII અને પ્રમાણપત્ર માસ્કર્સ, પ્રાથમિકતાઓ 10/95) વર્ણન લખાણને સ્થાનમાં ફરીથી લખે છે અને પછી સિસ્ટમ-પ્રોમ્પ્ટ/હેન્ડઓફ/મેમરી ઇન્જેક્શન સંદેશા એરેને પુનઃઆકાર આપે છે. મોડલને ઉપર મોકલવામાં આવેલ શરીર અપરિવર્તિત રહે છે. એક અવલોકિત વિનંતી પણ કોઈ ટકાઉ મેમરીને ભરતી નથી (વિનંતી અને જવાબ-ઉપજિત નિષ્કર્ષ બંને છોડી દેવામાં આવે છે), તેથી મોડલની પોતાની જવાબદારી મેમરીમાં ટ્રાન્સક્રિપ્ટ લખાણને પ્રતિબિંબિત કરી શકતી નથી.

**કાચા વિડિયો ક્ષેત્રો (#12430).** જ્યારે બ્રિજ સક્રિય હોય છે અને મૂળ વિડિયો સપોર્ટ અજ્ઞાત અથવા ગેરહાજર હોય છે, ત્યારે વ્યાખ્યાયિત `transcript`/`audioTranscript` ક્ષેત્રો પણ `videoBridgeObserved`ને સક્રિય કરે છે, વર્ણન નિષ્ફળતા અથવા `maxVideos` મર્યાદા પછી પણ. `null` અને ખાલી સ્ટ્રિંગ્સ ગણવામાં આવે છે; ગેરહાજર ક્ષેત્રો અને નોન-વિડિયો મેટાડેટા નથી. જાળવેલ નકલ આ ક્ષેત્રોને રેડેક્ટ કરે છે અથવા વિનંતી છોડી દે છે, અને કેશ/મેમરીને બાયપાસ કરવામાં આવે છે. પ્રદાતા પેઇલોડ અપરિવર્તિત રહે છે.

વધુ જાળવેલ નકલ એ જ અવલોકિત-વિનંતી સંકેતનો ઉપયોગ કરે છે. કાચા પૂર્વ-ગાર્ડરેલ ક્લાયન્ટ-વિનંતી સ્નેપશોટ, મેમરીમાં પેન્ડિંગ વિનંતી, અને વહેલા નકારી દેવામાં આવેલી વિનંતી લોગ ઢાંચાકીય રીતે વિડિયો ભાગોમાં ટ્રાન્સક્રિપ્ટ ક્ષેત્રોને બદલે છે; પાઇપલાઇન તબક્કાઓ અને સંદર્ભ હેન્ડઓફ દ્વારા સંશ્લેષિત સ્ટ્રિંગ પ્રોમ્પ્ટ્સ જાળવેલ-વિનંતી-શરીર સિંકમાં રેડેક્ટ કરવામાં આવે છે. જાળવેલ `video_content_removed` માર્કર `previous_response_id` ચાલુ રહેવું નિષ્ફળ કરે છે, તે લખાણને પુનઃનિર્માણ કરવાની જગ્યાએ જે ઇરાદાપૂર્વક નિકાલ કરવામાં આવ્યું હતું. જો એક અવલોકિત વિનંતી તેના દરેક ભાગના રેડક્શન શેડોને લોગિંગ પહેલાં ગુમાવે છે, અથવા પછીના વિનંતી પરિવર્તનો પછી ઘણા વિડિયો શેડોમાંથી એક પણ મેળ ખાતું નથી, તો જાળવેલ વિનંતી શરીર સંપૂર્ણપણે છોડી દેવામાં આવે છે, ભાગિક રીતે રેડેક્ટેડ ટ્રાન્સક્રિપ્ટને જાળવવા બદલે.

એક અવલોકિત વિનંતી માટે, એક મોડેલ પ્રતિસાદ ટ્રાન્સક્રિપ્ટના કોઈપણ ભાગને સંરચિત સૂચક બાઉન્ડરી વિના ઉલ્લેખિત કરી શકે છે. તેથી, તેની સ્થાયી કૉલ-લોગ `responseBody`ને એક ઉલટાવ ચિહ્ન દ્વારા બદલવામાં આવે છે; વિગતવાર પાઇપલાઇન આર્ટિફેક્ટ (જેમાં અપસ્ટ્રીમ/ક્લાયન્ટ બોડી અને સ્ટ્રીમ ચંક્સનો સમાવેશ થઈ શકે છે) જાળવવામાં આવતો નથી. સેમેન્ટિક, આઇડેમ્પોટેન્સી, અને રીઝનિંગ-રિપ્લે કેશ એ વિનંતી માટે વાંચન અને લખાણને બાયપાસ કરે છે. પ્રદાતા વિનંતી અને ક્લાયન્ટ-દૃશ્ય પ્રતિસાદ અપરિવર્તિત રહે છે. વિગતવાર આર્ટિફેક્ટને છોડી દેવામાં આવતા સમયે તાત્કાલિક કીપલાઇવ બાઇટ્સ તાત્કાલિક બફરમાંથી કાઢી લેવામાં આવે છે. કિરોની ખોટી ઇવેન્ટસ્ટ્રીમ ચેતવણી માત્ર પેલોડ બાઇટ ગણતરીને અહેવાલ આપે છે, ક્યારેય તેની સામગ્રી અથવા JSON પાર્સરની કાચી ભૂલને નહીં.

આ દાવો નથી કે દરેક અપ્રાસંગિક પ્રદાતા/પ્લગિન નિદાનની સમીક્ષા કરવામાં આવી છે; વ્યાપક જાળવવામાં આવેલા-સિંક સ્વીપને #11658માં ટ્રેક કરવામાં આવે છે.

આંતરિક `/api/modality-bridge/video/drilldown` જીવનચક્ર એક અલગ, લૂપબેક/ટોકન-પ્રમાણિત કેશ આધારભૂત છે. દરેક ઓપરેશન માટે એક કૅનોનિકલ ઓપેક પ્રિન્સિપલ IDની જરૂર છે. ઉત્પાદન કોલર સક્રિય થાય તે પહેલાં, તેને પ્રમાણિત ભાડેથી તે ID મેળવવી જોઈએ અને તે ક્યારેય ક્લાયન્ટ-ચૂંટાયેલ મૂલ્યને આગળ નહીં વધારવું જોઈએ. કેશ કી તે પ્રિન્સિપલને કૅનોનિકલ સત્ર અને વિડિઓ-સંદર્ભ ID સાથે બાંધે છે, ફક્ત તેમના SHA-256-ઉત્પાદિત કી જાળવે છે, અને વાંચન અને કાઢી નાખવા બંનેને સમાન પ્રિન્સિપલ સુધી મર્યાદિત કરે છે. કેશમાં દરેક એન્ટ્રી માટે મહત્તમ 16 ઉત્પન્ન JPEG ફ્રેમ્સ જાળવવામાં આવે છે, દસ મિનિટ પછી તેમને સમાપ્ત કરે છે, અને મર્યાદિત `start`/`end` વાંચન અથવા સ્પષ્ટ સત્ર કાઢી નાખવા માટે સમર્થન આપે છે.

દરેક પ્રિન્સિપલ 16 એન્ટ્રીઓ અને 64 MiB કૅનોનિકલ JPEG ડેટા સુધી મર્યાદિત છે. આ મર્યાદાઓ વૈશ્વિક 64-એન્ટ્રી/256 MiB છતથી સ્વતંત્ર છે: પ્રિન્સિપલ ક્વોટા દબાણ માત્ર તે પ્રિન્સિપલના ઓછામાં ઓછા-તાજેતરના ઉપયોગમાં આવેલા એન્ટ્રીઓને દૂર કરે છે, પહેલાં વૈશ્વિક LRU ખસેડવા પર વિચાર કરવામાં આવે છે. સમાપ્ત થયેલ એન્ટ્રીઓ કેશ પ્રવૃત્તિ પર પ્રિન્સિપલ અને વૈશ્વિક હિસાબમાંથી દૂર કરવામાં આવે છે, જ્યારે રદ કરવું અને માન્યતા નિષ્ફળતા આংশિક બદલાવને પ્રતિબદ્ધ નથી કરે.

કેશ નોન-કૅનોનિકલ બેસ64, વધુ પેડિંગ, નોન-JPEG મીડિયા, ખોટા અથવા કાપેલા JPEGs, અને JPEGsને નકારી નાખે છે જે મર્યાદિત સંપૂર્ણ-છબી `sharp` ડિકોડ દરમિયાન ચેતવણી આપે છે. તે દરેક સ્વીકૃત છબીને કૅનોનિકલ JPEG તરીકે ફરીથી કોડ કરે છે, ડિકોડ થયેલ બાઇટ્સમાંથી પહોળાઈ અને ઊંચાઈ મેળવવા માટે કોલર ફીલ્ડ્સ પર વિશ્વાસ ન રાખે, અને કોઈપણ પછાત પોલીગ્લોટ બાઇટ્સને જાળવવા બદલે દૂર કરે છે. ફક્ત મર્યાદિત કૅનોનિકલ સંકોચિત બફર બંને ક્વોટા પર ચાર્જ કરવામાં આવે છે. JSON વાયર મર્યાદા 32 MiB ડિકોડ-ઇનપુટ છત માટે બેસ64 ઓવરહેડને સમાવેશ કરે છે. દરેક જાળવેલ ઉત્પન્ન તેની માન્ય JPEG ફોર્મેટ/રિઝોલ્યુશન, નમૂના નીતિ, ઉત્પન્ન સંસ્કરણ, સર્જન સમય, સર્વર-ગણિત સામગ્રી હેશ, અને હેશ કરેલ પેરન્ટ સંદર્ભ સાથે સાથે વિશ્વસનીય કોલરના પેરન્ટ-સામગ્રી હેશને નોંધે છે. રદ કરવું અસંબંધિત ડિકોડ/હેશ તબક્કાઓ વચ્ચે ચકાસવામાં આવે છે પહેલાં આટોમિક કેશ પ્રતિબદ્ધતા.

ઉત્પાદન ઉત્પાદક સફળ દૃશ્ય વિશ્લેષણ પછી જ પહેલાથી ઉત્પન્ન બ્રોકર ફ્રેમ્સને પુનઃઉપયોગ કરે છે, બીજું વિડિઓ ડાઉનલોડ/ઉત્પાદન વગર. તે ઓપરેટર `modalityBridgeVideoDrilldownEnabled=true`, કડક પ્રતિભાગ `drilldown: true`, અને એક પ્રમાણિત API-કી રેકોર્ડ IDની જરૂર છે. ક્લાયન્ટ-જાહેરાત કરેલ પ્રિન્સિપલ/સત્ર મૂલ્યો ક્યારેય માલિકી સ્થાપિત નથી કરે. આ ત્રણ શરતો વિના તે હેશ, પુનઃમાપે અથવા વધારાના ફ્રેમ્સને જાળવે નહીં. જાળવણી નિષ્ફળતા ઉપયોગી દૃશ્ય પ્રતિસાદને જાળવે છે. સંમતિ પ્રાપ્ત વિનંતીઓ સમગ્ર-વિડિઓ પરિણામ કેશને બાયપાસ કરે છે જેથી કેશ કરેલા પરિણામો ક્યારેય હેન્ડલને પુનરાવર્તિત નથી કરે.

સફળ JSON અને SSE પ્રતિસાદ મર્યાદિત `x-omniroute-video-drilldown` હેડરમાં મહત્તમ ચાર ઓપેક હેન્ડલને પ્રદર્શિત કરે છે. અધિકૃત બ્રાઉઝર મૂળો તે હેડરને વાંચી શકે છે વિના CORS મૂળ નીતિને વિસ્તૃત કર્યા વિના. નવા હેન્ડલ `v1.<32-byte random base64url token>`નો ઉપયોગ કરે છે, અને રજિસ્ટ્રી ફક્ત તેમના SHA-256 હેશને જાળવે છે. રીડર/હેડર પાર્સર પણ વારસાગત 64-હેક્સ હેન્ડલને સ્વીકારે છે. પ્રમાણિત જાહેર ગ્રાહક છે `GET /api/v1/video-bridge/drilldown?handle=...`, સ્વતંત્ર રીતે ગેટેડ દ્વારા `modalityBridgeVideoDrilldownRemoteEnabled=true`. સ્પષ્ટ સ્થાયી ખોટી પ્રવેશને રદ કરે છે, ભલે જ વારસાગત `OMNIROUTE_VIDEO_BRIDGE_DRILLDOWN_REMOTE_ENABLED` env ફોલબેક સક્રિય હોય. ઉત્પાદન જાળવણીમાં સમાન વારસાગત `OMNIROUTE_VIDEO_BRIDGE_DRILLDOWN_ENABLED` ફોલબેક છે. બંને ફોલબેક ડિફોલ્ટ બંધ છે.

ગ્રાહક પ્રમાણિત કીમાંથી માલિકી મેળવશે, કી નીતિ લાગુ કરશે, અને અજ્ઞાત, સમાપ્ત અને અન્ય કી હેન્ડલ માટે સમાન 404 પાછું આપે છે. તે સ્વીકાર કરે છે `variant=preview|standard|detail` (મહત્તમ JPEG પરિમાણ 320/640/1280, ક્યારેય અપસ્કેલ ન થાય), `limit=1..8` (અથવા વારસાગત `frames` ઉપનામ, ક્યારેય બંને નહીં), શૂન્ય આધારિત `page`, અને વૈકલ્પિક `start`/`end` ફોકસ સેકંડ. નકલ ક્વેરી કી અને વિરુદ્ધ ફોકસ વિન્ડોને નકારી દેવામાં આવે છે. દરેક પાછા મળેલ વૈવિધ્યમાં તેની વાસ્તવિક સામગ્રી અને વાસ્તવિક રિઝોલ્યુશન મેટાડેટાનો હેશ હોય છે, જે જાળવેલ સ્ત્રોત સાથે જોડાયેલ છે. વૈવિધ્ય વાંચન પર ઉત્પન્ન થાય છે, વધારાના જાળવેલ નકલ તરીકે જાળવવામાં નથી. JSON પ્રતિસાદ, જેમાં બેસ64/એન્વેલોપનો સમાવેશ થાય છે, 32 MiB પર મર્યાદિત છે; એક વિશાળ પાનું 413 પાછું આપે છે અને ક્લાયન્ટને ઓછા ફ્રેમ્સની વિનંતી કરવી જોઈએ. વાંચનો દરેક પુનઃમાપની આસપાસ રદ કરવાનું ચકાસે છે અને પાછા ફરતા પહેલા હેન્ડલ માન્યતાને ફરીથી ચકાસે છે. માલિક દ્વારા `DELETE` આઇડેમ્પોટેન્ટ છે; કાઢી નાખવું અથવા TTL સમાપ્ત થવું જાળવેલ સ્ત્રોત અને ઉપયોગ હિસાબને મુક્ત કરે છે.

શેર કરેલ સ્ટોર પ્રક્રિયા-સ્થાનિક છે: હેન્ડલ ફરી શરૂ કરવામાં સમાપ્ત થાય છે અને સ્વતંત્ર ઓમ્નીરૂટ પ્રક્રિયાઓ વચ્ચે પરિવહન કરી શકાતી નથી. વ્યવસ્થાપન આંકડાઓ અસરકારક જાળવણી/દૂરના નીતિ અને એકત્રિત જાળવેલ એન્ટ્રીઓ/બાઇટ્સને જ પ્રદર્શિત કરે છે, ક્યારેય મીડિયા, સંદર્ભો, પ્રિન્સિપલ ID અથવા હેન્ડલને નહીં. વિડિઓ સેટિંગ્સ પેનલ આ મૂલ્યોને દર્શાવે છે અને બંને સંમતિ સ્વિચને જાળવી શકે છે. આ અમલ દસ્તાવેજ જીવંત અમલ અથવા પ્રમોશન પુરાવા નથી; વાસ્તવિક-મોડેલ સ્વીકૃતિ અલગથી ટ્રેક કરવામાં આવે છે.

ફ્રેમોને કન્ફિગર કરેલા વિડિયો મોડલ સાથે ક્રમવાર કેપ્શન કરવામાં આવે છે. ખાલી વિડિયો ઓવરરાઇડ વિઝન સેટિંગને વારસામાં લે છે; જો બંને ખાલી હોય, તો વિઝન ઓટો-રાઉટર અસરકારક વિઝન-ક્ષમ મોડલ પસંદ કરે છે. સફળ કેપ્શન મૂળ ભાગને સ્થિર `[Video description:` પ્રિફિક્સ સાથે બદલે છે જે ટેક્સ્ટને અવિશ્વસનીય મીડિયા-ઉત્પન્ન અવલોકન તરીકે પણ ચિહ્નિત કરે છે અને નીચેના મોડલને મીડિયા માં મળેલા સૂચનોને અનુસરણ ન કરવા માટે કહે છે. ફ્રેમ-કેપ્શન કેશ કી JPEG બાઇટ્સ, પ્રોમ્પ્ટ, ટાઇમસ્ટેમ્પ અને અસરકારક મોડલને સમાવેશ કરે છે; ફક્ત સફળ કેપ્શન જ કેશ કરવામાં આવે છે. કેશ એન્ટ્રીઓ વાસ્તવિક સફળ ઉત્પાદક મોડલને જાળવે છે, જેમાં એક ફોલબેક મોડલ પણ હોય છે; બ્રિજ `mixed` રિપોર્ટ કરે છે જ્યારે અલગ મોડલ દ્વારા અલગ ફ્રેમો ઉત્પન્ન કરવામાં આવ્યા હતા. કેશ હિટ તે ઉત્પાદક ઓળખને ફરીથી ઉપયોગ કરે છે તેના બદલે તેને વિનંતી કરેલા રાઉટિંગ યોજના તરીકે પુનઃલેબલ કરે છે. સમગ્ર-વિડિયો પરિણામ કેશ દરેક ઇનપુટ પર કી કરવામાં આવે છે જે આઉટપુટને બદલાવે છે — પ્રોમ્પ્ટ, અસરકારક મોડલ, નમૂનાકરણ નીતિ, ફ્રેમ ગણતરી, સેમેન્ટિક વિશ્લેષણ મોડ, નોર્મલાઇઝ્ડ ફોકસ હિન્ટનું SHA-256 ફિંગરપ્રિન્ટ, ફોકસ વિન્ડો, `transcript`, `audioTranscript`, અને સંપર્ક-શીટ ધ્વજ — તેથી આમાંના કોઈપણ પરિમાણોને બદલવું કેશ મિસ છે, ક્યારેય જૂના પુનઃઉપયોગ નથી. વિઝ્યુઅલ ડેડુપ નીતિ સંસ્કરણ, થ્રેશોલ્ડ, અને બાઉન્ડેડ કૅન્ડિડેટ-ફ્રેમ ગણતરી પણ પરિણામ-કેશ કી અને મેટાડેટામાં સ્પષ્ટ છે; તેથી નીતિમાં ફેરફાર જૂના સમગ્ર-વિડિયો વર્ણનને પુનઃઉપયોગ કરી શકતું નથી. પરિણામ-કેશ v4 મેટાડેટા મોડ અને ફિંગરપ્રિન્ટને રાખે છે, ક્યારેય કાચા યુઝર કાર્યને નહીં. ગાર્ડરેલ મેટાડેટા વિનંતી કરેલા અને અસરકારક વિશ્લેષણ મોડ બંનેને રિપોર્ટ કરે છે; ઉપયોગી યુઝર ટેક્સ્ટ વિના વિનંતી કરેલો `focused` મોડ અસરકારક રીતે `full` તરીકે રિપોર્ટ કરવામાં આવે છે.

ગાર્ડરેલ દરેક સપોર્ટેડ વિડિયો ભાગને કાઢે છે પરંતુ `modalityBridgeVideoMaxVideos` કરતાં વધુ વર્ણવતું નથી. એક લક્ષ્ય જે `supportsVideo === false` ધરાવે છે, નિષ્ફળ અને ઓવર-લિમિટ વિડિયો સ્પષ્ટ સુરક્ષિત ટેક્સ્ટ માર્કરોમાં રૂપાંતરિત થાય છે જેથી કોઈ કાચા વિડિયો જીવંત ન રહે. જ્યારે ક્ષમતા અજાણ હોય, ત્યારે તે ભાગો અપરિવર્તિત રહે છે. લક્ષ્યો સાથે `supportsVideo === true` બ્રિજને બાયપાસ કરે છે. ક્લાયન્ટ વિનંતી બંધ સિગ્નલ ડાઉનલોડ, બ્રોકર ક્યૂ, સબપ્રોસેસ અને કેપ્શન કોલ્સમાં પ્રસારિત થાય છે; બંધ કરવું વિડિયો વચ્ચે રોકે છે અને ક્યારેય કાચા મીડિયા માટે ખૂલે નહીં.

લેગસી પર્સિસ્ટેડ વિડિયો ટાઇમઆઉટ મૂલ્યો 120 સેકન્ડથી વધુને બ્રોકર ડેડલાઇન પર ક્લેમ્પ કરવામાં આવે છે; તે મર્યાદા ઉપર નવા સેટિંગ્સ લખાણો નકારી દેવામાં આવે છે. `GET /api/modality-bridge/video/runtime` માન્યતા અથવા રનટાઇમ પ્રોબિંગ પહેલાં વિશ્વસનીય સ્ટેમ્પેડ લૂપબેક લોકલિટીની જરૂર છે, પછી મેનેજમેન્ટ ઓથેન્ટિકેશનની જરૂર છે. તે ફક્ત `available`, sanitized FFmpeg/ffprobe સંસ્કરણો, અને જ્યારે રનટાઇમ ઉપલબ્ધ નથી ત્યારે એક નિશ્ચિત કારણ પાછું આપે છે. આંતરિક નિષ્કર્ષ બિંદુ જાહેર અપલોડ API નથી: ક્યૂ સંતૃપ્તિ `503` સાથે `Retry-After` પાછું આપે છે, એક કોલર ડિસ્કનેક્ટ `499` પાછું આપે છે, અને નિશ્ચિત બ્રોકર ડેડલાઇન `504` પાછું આપે છે. રૂપાંતરિત પ્રતિસાદો કેન્દ્રિય `x-omniroute-modality-bridge` હેડરમાં `video->text;model=<visionModel>;parts=<videos>` ઉમેરે છે વિઝન અથવા ઓડિયો સેગમેન્ટને દૂર કર્યા વિના.

### PII Masker (`piiMasker.ts`)

**બન્ને** તબક્કાઓ પર ચાલે છે.

- **`preCall`** પેલોડને ક્લોન કરે છે, `system`, `messages`, `input`, અને `prompt` (સાધારણ સ્ટ્રિંગ આઇટમ્સને સમાવેશ કરે છે) ને ચાલે છે, અને `processPII()` (થી `@/shared/utils/inputSanitizer`) ને સ્ટ્રિંગ `content`/`text` ફીલ્ડ્સ પર લાગુ કરે છે. જ્યારે `PII_REDACTION_ENABLED=true` હોય, ત્યારે શોધવામાં આવેલ PII આઉટબાઉન્ડ પેલોડમાં છુપાવવામાં આવે છે. આ `INPUT_SANITIZER_MODE` (જે ફક્ત પ્રોમ્પ્ટ-ઇન્જેક્શન નીતિને નિયંત્રિત કરે છે) થી સ્વતંત્ર છે. જ્યારે છુપાવવું બંધ હોય, ત્યારે કોલ ડિટેક્શન ગણતરીઓને નોંધે છે કન્ટેન્ટને ફરીથી લખ્યા વિના.
- **`postCall`** પ્રતિસાદને ડીપ-ક્લોન કરે છે, `sanitizePIIResponse()` ચલાવે છે અને પ્રતિસાદ-API-આકાર માસ્કર (`maskResponsesOutput` — `output_text` અને `output[].content[].text`ને આવરી લે છે). જો કોઈ છુપાવણ થાય છે, તો ફેરફાર કરેલો પ્રતિસાદ મૂળને બદલે છે.

ગાર્ડરેલ ક્યારેય અવરોધિત નથી; તે ફક્ત નોંધ કરે છે (`meta.detections`, `meta.redacted`) અથવા ફરીથી લખે છે.

### Prompt Injection (`promptInjection.ts`)

યુઝર-પ્રદાન કરેલ કન્ટેન્ટમાં વિરોધી માળખાઓને શોધે છે અને કન્ફિગર કરેલી નીતિને અમલમાં લાવે છે. વર્તન પર્યાવરણ ચલ અને કન્સ્ટ્રક્ટર વિકલ્પો દ્વારા ચલાવવામાં આવે છે:

| સેટિંગ          | એન્વી વેર                                                                                             | ડિફોલ્ટ | અસર                                                                                                                                                                                          |
| --------------- | ----------------------------------------------------------------------------------------------------- | ------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| સક્રિય          | `INPUT_SANITIZER_ENABLED`                                                                             | `true`  | જ્યારે `false` હોય, ત્યારે ગાર્ડરેલ શોર્ટ-સર્કિટ થાય છે.                                                                                                                                     |

`INJECTION_GUARD_MODE` **ડેટાબેસ ફીચર-ફ્લેગ ઓવરરાઈડ** (ડેશબોર્ડ → સેટિંગ્સ →
ફીચર ફ્લેગ્સ) → `INJECTION_GUARD_MODE` એન્વી → `INPUT_SANITIZER_MODE` એન્વી →
`warn`. તેથી, ડેશબોર્ડ ઓવરરાઈડ એન્વી વેરની ઉપર છે, તેથી ફીચર ફ્લેગ્સ UI જીવંત ગાર્ડને ચલાવે છે (કોઈ પુનઃપ્રારંભ નથી). DB વાંચન નિષ્ફળ-સુરક્ષિત છે:
જો તે ભૂલ કરે છે, તો ગાર્ડ એન્વી આધારિત વર્તન પર પાછું ફરે છે, અને જ્યારે કોઈ ઓવરરાઈડ સેટ નથી ત્યારે વર્તન એન્વી-માત્ર ઉકેલ સાથે સમાન છે.

ખોજના સ્ત્રોતો:

1. `sanitizeRequest()` from `@/shared/utils/inputSanitizer` (શેર કરેલ ડિટેક્ટર
   સેટ જે પાઇપલાઇનમાં અન્ય જગ્યાએ ઉપયોગમાં લેવાય છે).
2. બિલ્ટ-ઇન `DEFAULT_GUARD_PATTERNS` (હાલમાં `system_override_inline` અને
   `markdown_system_block`, બંને `high` ગંભીરતા).
3. વૈકલ્પિક `customPatterns` કન્સ્ટ્રક્ટર વિકલ્પો દ્વારા પસાર કરવામાં આવે છે (સ્ટ્રિંગ, regex,
   અથવા `{ name, pattern, severity }` રેકોર્ડ).

જ્યારે `mode === "block"` **અને** ઓછામાં ઓછા એક શોધ ગંભીરતા થ્રેશોલ્ડને પૂર્ણ કરે છે,
`preCall` `{ block: true, message: "વિનંતી નકારી દેવામાં આવી: શંકાસ્પદ સામગ્રી શોધાઈ" }` પરત આપે છે. `warn`/`log` મોડમાં ગાર્ડરેલ લોગ કરે છે પરંતુ
કોલને મંજૂરી આપે છે. શેર કરેલ હેલ્પર `evaluatePromptInjection()` પણ નિકાસ કરવામાં આવે છે
તેથી કોલર્સને રજિસ્ટ્રીમાં જવા વિના પ્રોમ્પ્ટ્સનું મૂલ્યાંકન કરવાની જરૂર છે.

**સ્કેન બાઉન્ડ (v3.8.20):** ડિટેક્ટર માત્ર **પ્રથમ 16 KB** જોડાયેલા પ્રોમ્પ્ટ ટેક્સ્ટનું નિરીક્ષણ કરે છે — `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 બાઇટ) માં
`src/shared/utils/inputSanitizer.ts`. બંને `detectInjection()` અને
`evaluatePromptInjection()` `slice(0, MAX_INJECTION_SCAN_BYTES)` પેટર્ન લૂપ ચલાવ્યા પહેલા કરે છે. ઇન્જેક્શન નિર્દેશો ઇનપુટના ટોચની નજીક બેસે છે, તેથી આ
મલ્ટી-સો-KB પે લોડ પર regex CPU/GCને કાપે છે અને શોધને નબળું કર્યા વિના (cf.
#3932, #4041).

### ક્રેડેંશિયલ માસ્કર (`credentialMasker.ts`)

**બન્ને** તબક્કાઓ પર ચાલે છે, ડિફોલ્ટ ચેઇનમાં છેલ્લું (પ્રાથમિકતા `95`). આઉટબાઉન્ડ પે લોડ (સંદેશા
સામગ્રી, ટૂલ-કોલ દલીલ, ટૂલ પરિણામો)માંથી જાણીતા API-કી / સિક્રેટ-ટોકન પેટર્નને રેડેક્ટ કરે છે **અને** પ્રદાતા પ્રતિસાદ, તેથી પ્રોમ્પ્ટમાં પેસ્ટ કરેલ ક્રેડેંશિયલ (અથવા ટૂલ પરિણામ દ્વારા પાછું પ્રતિસાદ) ઉપરના પ્રદાતા અથવા ક્લાયન્ટને લીક થતું નથી.

- **ઓપ્ટ-ઇન માત્ર**, PII રેડક્શન જેવી જ પરંપરા (હાર્ડ રૂલ #20-સંબંધિત):
  જ્યારે સુધી `settings.credentialRedactionEnabled === true` **અથવા**
  `CREDENTIAL_REDACTION_ENABLED=true` નથી, ત્યારે બંધ છે. જ્યારે તે બંધ હોય, ત્યારે ગાર્ડરેલ એક નોન-ઓપ છે —
  તે ક્યારેય બ્લોક નથી કરે અને ક્યારેય પુનરલેખન નથી કરે.
- `redactCredentials()` સંપૂર્ણ પે લોડ/પ્રતિસાદ વૃક્ષને ચાલે છે (`walkValue()`,
  પ્રોટોટાઇપ-પ્રદૂષણ-સુરક્ષિત, ચક્ર-સુરક્ષિત `WeakSet` દ્વારા) અને મેળ ખાય તે વસ્તુઓને બદલે
  `[REDACTED:<type>]` પ્લેસહોલ્ડર સાથે, ફક્ત તે શાખાઓને ક્લોન કરે છે જે ખરેખર
  બદલાઈ ગઈ છે.
- `CREDENTIAL_PATTERNS` LLM પ્રદાતા કી (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), VCS/SaaS ટોકન (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), ચુકવણી કી (Stripe, Square), ક્લાઉડ
  કી (AWS ઍક્સેસ કી, Twilio, SendGrid, Mailgun), ખાનગી કી / JWTs,
  ક્રેડેંશિયલ ધરાવતી કનેક્શન સ્ટ્રિંગ્સ (`mongodb://user:pass@...`, વગેરે), અને
  સામાન્ય `Authorization`/`x-api-key`/`api-key`/`apikey` હેડર-મૂલ્ય
  પેટર્ન. હેડર-આકારની કી (`authorization`, `x-api-key`, `api-key`,
  `apikey`) ઢાંચાકીય રીતે રેડેક્ટ થાય છે (મૂલ્ય જ, સ્કીમ પ્રિફિક્સ જેમ કે
  `Bearer `/`Basic ` જાળવવામાં આવે છે) સામાન્ય ટેક્સ્ટ regex દ્વારા નહીં.
- ગાર્ડરેલ ક્યારેય બ્લોક નથી કરે; તે ફક્ત પુનરલેખન કરે છે (`modifiedPayload` /
  `modifiedResponse`) અને નોંધ કરે છે (`meta.credentialsRedacted`, `meta.count`).

પુનરાવર્તન ગાર્ડ: `tests/unit/credential-masker-guardrail.test.ts`.

## મૂળભૂત કરાર (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(
    payload: unknown,
    context: GuardrailContext,
  ): Promise<GuardrailResult | void>;

  async postCall(
    response: unknown,
    context: GuardrailContext,
  ): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true ચેઇનને તરત જ અટકાવે છે
  message?: string; // અવરોધિત કરતી વખતે દર્શાવવામાં આવે છે
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // વિનંતીને ફરી લખવા માટે preCall દ્વારા પરત કરવામાં આવે છે
  modifiedResponse?: TValue; // પ્રતિસાદને ફરી લખવા માટે postCall દ્વારા પરત કરવામાં આવે છે
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

ગાર્ડરેલ `void`, `{}`, અથવા `{ block: false }` પરત કરીને "કોઈ ફેરફાર નહીં"નો સંકેત આપે છે. `modifiedPayload`/`modifiedResponse` પરત કરવાથી ચેઇનમાં આગળના ગાર્ડરેલ્સ તરફ વહેતું મૂલ્ય બદલાઈ જાય છે.
`signal?: AbortSignal` કૉલરની લાઇફસાઇકલને ગાર્ડરેલ્સ સુધી લઈ જાય છે. વિનંતી રદ થવી એ ઇરાદાપૂર્વકનો fail-open અપવાદ છે: મીડિયા બ્રિજ કામ અટકાવે છે અને જે લક્ષ્ય તેને સપોર્ટ કરતું નથી તે જાણીતું હોવા છતાં તેમાં મૂળ મીડિયા પુનઃસ્થાપિત કર્યા વિના ક્લીનઅપ કરે છે.

## રજિસ્ટ્રી (`registry.ts`)

સિંગલટન `guardrailRegistry` નીચેની સુવિધાઓ પ્રદાન કરે છે:

- `register(guardrail)` — ગાર્ડરેલ ઉમેરે છે (અથવા સામાન્યકૃત નામ દ્વારા બદલે છે) અને
  ચઢતા `priority` મુજબ ફરીથી ગોઠવે છે.
- `clear()` / `list()` — વહીવટી સહાયકો.
- `runPreCallHooks(payload, context)` — સક્રિય ગાર્ડરેલ્સ પર ક્રમશઃ ફરે છે, પેલોડને
  `modifiedPayload` મારફતે આગળ ધપાવે છે અને પ્રથમ `block: true` પર અટકે છે.
- `runPostCallHooks(response, context)` — પ્રતિસાદની બાજુએ સમાન પ્રવાહ.
- `resetGuardrailsForTests({ registerDefaults })` — સ્વચ્છ ટેસ્ટ અલગીકરણ માટે સ્ટેટ સાફ કરે છે અને વૈકલ્પિક રીતે
  ડિફૉલ્ટ્સને ફરીથી રજિસ્ટર કરે છે.

બંને રનર્સ `{ blocked, payload|response, results, guardrail?, message? }`
પરત કરે છે, જ્યાં `results` એ `GuardrailExecutionResult` રેકોર્ડ્સની એરે છે, જેમાં
દરેક ગાર્ડરેલ માટેના `blocked`, `skipped`, `modified`, `error`, અને `meta` ફીલ્ડ્સ
સમાવિષ્ટ હોય છે, જે ટ્રેસિંગ માટે ઉપયોગી છે.

### દરેક વિનંતી માટે ગાર્ડરેલ્સ અક્ષમ કરવા

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` વર્તમાન
વિનંતી માટે છોડવામાં આવનાર ગાર્ડરેલ નામોની ડુપ્લિકેટ-રહિત યાદી એકત્રિત કરે છે.
સ્ત્રોતો (બધા વૈકલ્પિક, બધા મર્જ કરવામાં આવે છે):

- `apiKeyInfo.disabledGuardrails`
- વિનંતી બોડીનું `disabledGuardrails` (ટોચના સ્તરે)
- વિનંતી બોડીનું `metadata.disabledGuardrails`
- હેડર `x-omniroute-disabled-guardrails` (અથવા જૂનું
  `x-disabled-guardrails`)

મૂલ્યો સ્ટ્રિંગ્સની એરે અથવા કૉમાથી અલગ કરેલી સ્ટ્રિંગ હોઈ શકે છે; નામોને
લોઅરકેસ kebab-caseમાં સામાન્યકૃત કરવામાં આવે છે (`pii_masker` → `pii-masker`). પરિણામ
`context.disabledGuardrails` મારફતે રજિસ્ટ્રીને આપવામાં આવે છે, જે
મેળ ખાતા ગાર્ડરેલ્સને છોડી દે છે (`results`માં `skipped: true`).

## અમલીકરણ ક્રમ

`src/sse/handlers/chat.ts` અને
`open-sse/handlers/chatCore.ts`માંથી પસાર થતી દરેક વિનંતી માટે:

1. `resolveDisabledGuardrails(...)` API કી, બોડી અને હેડર્સમાંથી સ્કિપ સૂચિ બનાવે છે.
2. `guardrailRegistry.runPreCallHooks(body, ctx)` ચડતા પ્રાથમિકતા ક્રમમાં ગાર્ડરેલ્સ ચલાવે છે:
   - અક્ષમ કરેલા ગાર્ડરેલ્સ `skipped` તરીકે નોંધાય છે.
   - દરેક ગાર્ડરેલનું `preCall`, `modifiedPayload` મારફતે પેલોડને ફરી લખી શકે છે.
   - પ્રથમ `block: true` ચેઇનને શોર્ટ-સર્કિટ કરે છે અને હેન્ડલર
     ગાર્ડરેલ અસ્વીકાર પ્રતિસાદ પરત કરે છે.
3. (સંભવિત રીતે ફરી લખાયેલો) પેલોડ કોમ્બો રાઉટિંગ અને અપસ્ટ્રીમ
   ડિસ્પેચમાં જાય છે.
4. પ્રતિસાદ તૈયાર થયા પછી, `guardrailRegistry.runPostCallHooks(...)`
   પ્રતિસાદ પર એ જ ચેઇન ચલાવે છે. અહીં `block: true` અપસ્ટ્રીમ
   પ્રતિસાદને કાઢી નાખે છે.

જે ગાર્ડરેલ્સ અપવાદ ફેંકે છે તે `error: <message>` સાથે નોંધાય છે અને
`logger.warn` મારફતે લૉગ થાય છે, પરંતુ ચેઇન ચાલુ રહે છે — ડિઝાઇન મુજબ ફેઇલ-ઓપન.

## રૂપરેખાંકન

બિલ્ટ-ઇન ગાર્ડરેલ્સ દ્વારા વાંચવામાં આવતા એન્વાયર્નમેન્ટ વેરિએબલ્સ:

| વેરિએબલ                               | આના દ્વારા વપરાય છે        | અસર                                                                                                             |
| ------------------------------------- | -------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`         | શોધને સંપૂર્ણપણે અક્ષમ કરવા માટે `false` સેટ કરો.                                                               |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`         | ઇન્જેક્શન નીતિ: `warn`, `block`, અથવા `log`. લેગસી મૂલ્ય `redact` ઇન્જેક્શન ટેક્સ્ટને ફરીથી લખતું નથી.          |
| `INJECTION_GUARD_MODE`                | `prompt-injection`         | ઇન્જેક્શન ગાર્ડ માટેનો મોડ; આ DB ફીચર ફ્લેગ પણ છે, જે એન્વાયર્નમેન્ટ વેરિએબલ્સને **ઓવરરાઇડ** કરે છે (DB > ENV). |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`         | `MODE=block` દ્વારા અસ્વીકાર થવા માટેની ન્યૂનતમ ગંભીરતા: `high` (ડિફૉલ્ટ), `medium`, અથવા `low`.                |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`         | `INPUT_SANITIZER_BLOCK_THRESHOLD` માટેનો લેગસી ઉપનામ.                                                           |
| `PII_REDACTION_ENABLED`               | `pii-masker`               | જ્યારે `true` હોય, ત્યારે વિનંતીમાં રહેલી PII રિડેક્ટ થાય છે (ઇન્જેક્શન મોડથી સ્વતંત્ર).                        |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (ડાઉનસ્ટ્રીમ) | પ્રતિસાદ-બાજુના માસ્કરની વર્તણૂકને નિયંત્રિત કરે છે.                                                            |

Modality Bridge ગાર્ડરેલ્સ એન્વાયર્નમેન્ટ વેરિએબલ્સને બદલે DB-આધારિત સેટિંગ્સ
સ્ટોર (`getSettings()`)માંથી રનટાઇમ રૂપરેખાંકન વાંચે છે. Visionની પ્રાથમિક કીઓ
`modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`,
`modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`,
`modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`,
`modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`,
`modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes`, અને
`modalityBridgeCacheMaxEntries` છે. લેગસી
`visionBridge*` કીઓ ફક્ત દસ્તાવેજીકૃત એક-ચક્ર રીડ
ફૉલબૅક તરીકે સ્વીકારવામાં આવે છે; ડૅશબોર્ડ રાઇટ્સ પ્રાથમિક કીઓનો ઉપયોગ કરે છે. ડિફૉલ્ટ્સ અને ફૉલબૅક
રિઝૉલ્વર `src/shared/constants/modalityBridgeDefaults.ts`માં છે, જ્યારે લેગસી
કોન્સ્ટન્ટ્સ `src/shared/constants/visionBridgeDefaults.ts`માં જાળવી રાખવામાં આવ્યા છે.

Audio, `modalityBridgeAudioEnabled`, `modalityBridgeAudioModel`,
`modalityBridgeAudioTimeout`, અને `modalityBridgeAudioMaxClips`, તેમજ શેર કરેલ
`modalityBridgeCache*` સેટિંગ્સનો ઉપયોગ કરે છે. Audio માટે કોઈ લેગસી-કી ફૉલબૅક નથી, કારણ કે આ
કીઓ Modality Bridge સ્કીમા સાથે રજૂ કરવામાં આવી હતી.

Video, `modalityBridgeVideoEnabled`, `modalityBridgeVideoAnalysisMode`,
`modalityBridgeVideoModel`,
`modalityBridgeVideoFrameCount`, `modalityBridgeVideoSamplingPolicy`,
`modalityBridgeVideoMaxVideos`, અને
`modalityBridgeVideoTimeout`, તેમજ શેર કરેલ `modalityBridgeCache*` સેટિંગ્સનો ઉપયોગ કરે છે.
તે ડિફૉલ્ટ રૂપે અક્ષમ છે કારણ કે FFmpeg/ffprobe વૈકલ્પિક ઓપરેશનલ
ડિપેન્ડન્સીઝ છે અને ફ્રેમ કૅપ્શનિંગ લેટન્સી અને મોડેલ ખર્ચ વધારે છે.

## કસ્ટમ ગાર્ડરેલ્સ

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

પગલાં:

1. `BaseGuardrail`ને વિસ્તૃત કરતી `src/lib/guardrails/myGuardrail.ts` બનાવો.
2. `preCall` અને/અથવા `postCall` અમલમાં મૂકો.
3. કાં તો ઇમ્પોર્ટ સમયે નોંધણી કરો (`registerDefaultGuardrails`માંથી પુશ કરો) અથવા
   રનટાઇમ પર `guardrailRegistry.register(...)` કૉલ કરો — રજિસ્ટ્રી સમાન સામાન્યકૃત
   નામ ધરાવતા કોઈપણ અગાઉના ગાર્ડરેલને બદલી નાખે છે.
4. `tests/unit/` હેઠળ પરીક્ષણો ઉમેરો (હાલનાં ઉદાહરણો:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`).

## પરીક્ષણ

જાણીતી સ્થિતિથી શરૂઆત કરવા માટે પરીક્ષણો વચ્ચે `resetGuardrailsForTests()`નો ઉપયોગ કરો.
ખાલી રજિસ્ટ્રીથી શરૂઆત કરવા માટે `{ registerDefaults: false }` પાસ કરો અને
માત્ર પરીક્ષણ હેઠળના ગાર્ડરેલ્સની નોંધણી કરો. Vision Bridge ડિપેન્ડન્સી
ઇન્જેક્શન (`deps.getSettings`, `deps.callVisionModel`) સ્વીકારે છે; Audio Bridge
સેટિંગ્સ, ક્ષમતાઓ, STT મોડેલ પસંદગી, ક્રેડેન્શિયલ તપાસો અને ટ્રાન્સક્રિપ્શન માટે
સમકક્ષ સીમ્સ ઉપલબ્ધ કરાવે છે. તેથી પરીક્ષણો DB અથવા નેટવર્ક ઍક્સેસ વિના બંને
પ્રવાહોને ચકાસી શકે છે.

## ઇન્જેક્શન-ગાર્ડ રૂટ કવરેજ અને રેડ-ટીમ (તબક્કો 8 · બ્લૉક D)

ઇન્જેક્શન-ગાર્ડ (`createInjectionGuard` / `withInjectionGuard`) વપરાશકર્તા પ્રોમ્પ્ટ્સ
સ્વીકારતા તમામ રૂટ્સને આવરી લે છે. તે `INJECTION_GUARD_MODE`નું પાલન કરે છે (ડિફૉલ્ટ
`warn` = ફક્ત લૉગ; `block` = HTTP 400 `SECURITY_001` પરત કરે છે).

| પ્રકાર           | રૂટ્સ                                                                                                                                                | ડિફૉલ્ટ મોડ |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ----------- |
| ટેક્સ્ટ (હાલનું) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn        |
| જનરેટિવ          | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn        |
| ડેટા             | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn        |

ટેક્સ્ટ નિષ્કર્ષણ (`extractMessageContents`) `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`ને આવરી લે છે.

**રેડ-ટીમ (દરરોજ રાત્રે, `nightly-llm-security.yml`):** promptfoo ચકાસે છે કે દરેક રૂટ
`INJECTION_GUARD_MODE=block`માં OWASP-LLM કોર્પસને બ્લૉક કરે છે; garak પ્રોબ્સ ચલાવે છે
(સિક્રેટ વિના સ્કિપ કરે છે). સુસંગતતા માટે `moderations`નો સમાવેશ કરવામાં આવ્યો છે —
બ્લૉક-મોડમાં ઑપરેટર્સ `resolveDisabledGuardrails` મારફતે તેને મુક્તિ આપી શકે છે.

રાત્રિકાલીન વર્કફ્લો (`.github/workflows/nightly-llm-security.yml`, cron + મેન્યુઅલ
ડિસ્પેચ)માં બે જૉબ્સ છે:

- **`promptfoo-guard` (બ્લૉકિંગ)** — `INJECTION_GUARD_MODE=block` સાથે
  `promptfoo eval -c promptfooconfig.yaml` ચલાવે છે. દરેક પ્રતિકૂળ કેસ (દા.ત. "અગાઉની
  તમામ સૂચનાઓ અવગણો…", DAN-શૈલીના જેલબ્રેક્સ) ખાતરી કરે છે કે પ્રતિસાદમાં
  `error.code === "SECURITY_001"` હોય, એટલે કે ગાર્ડે વિનંતીને ખરેખર નકારી હતી.
- **`garak` (સલાહકારી)** — સ્થાનિક OmniRoute ઇન્સ્ટન્સ
  (`http://localhost:20128/v1`) સામે garak `--probes promptinject,dan,leakreplay`
  ચલાવે છે. તે પ્રોવાઇડર સિક્રેટ (`PROMPTFOO_PROVIDER_KEY`) પર આધારિત છે; સિક્રેટ
  ન હોય તો સરળતાથી સ્કિપ કરે છે અને તેની પાછળ `|| true` જોડાયેલું છે, તેથી તે CIને
  નિષ્ફળ કર્યા વિના રિપોર્ટ કરે છે.

ગાર્ડ હેલ્પર (`createInjectionGuard` / `withInjectionGuard`)નું કવરેજ પ્રોમ્પ્ટ ધરાવતા
દરેક `/v1` રૂટ સુધી વિસ્તરે છે; પ્રોમ્પ્ટ ટેક્સ્ટને
`src/shared/utils/inputSanitizer.ts`માંના `extractMessageContents()` દ્વારા
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`માંથી
લેવામાં આવે છે.
