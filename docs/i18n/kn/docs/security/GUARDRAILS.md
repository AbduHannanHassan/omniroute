> **ಸತ್ಯದ ಮೂಲ:** `src/lib/guardrails/`
> **ಕೊನೆಯ ನವೀಕರಣ:** 2026-08-29 — v3.8.51 (Video Bridge ಪ್ರತಿಲೇಖದ ಮೂಲವನ್ನು ಕರೆಮಾಡುವವರು ಘೋಷಿಸುತ್ತಾರೆ,
> ಸರ್ವರ್ ಇನ್ನೂ ಅದನ್ನು ಪರಿಶೀಲಿಸುವುದಿಲ್ಲ — #11661 ಪ್ರಕಾರ ಸ್ಪಷ್ಟಪಡಿಸಲಾಗಿದೆ)

Guardrails, OmniRoute ಮತ್ತು ಅಪ್ಸ್ಟ್ರೀಮ್ ಪೂರೈಕೆದಾರರ ನಡುವಿನ ಗಡಿಯಲ್ಲಿ ಸುರಕ್ಷತೆ,
ನೀತಿ ಮತ್ತು ವಿಷಯ ರೂಪಾಂತರಗಳನ್ನು ಜಾರಿಗೊಳಿಸುತ್ತವೆ. ಪ್ರತಿಯೊಂದು guardrail ವಿನಂತಿಯ
ಪೇಲೋಡ್ಗಳನ್ನು (`preCall`) ಮತ್ತು ಅಪ್ಸ್ಟ್ರೀಮ್ ಪ್ರತಿಕ್ರಿಯೆಗಳನ್ನು (`postCall`)
ಪರಿಶೀಲಿಸಬಹುದು (ಮತ್ತು ಐಚ್ಛಿಕವಾಗಿ ತಿರಸ್ಕರಿಸಬಹುದು, ರೂಪಾಂತರಿಸಬಹುದು ಅಥವಾ ಟಿಪ್ಪಣಿ ಸೇರಿಸಬಹುದು).

ಈ ವ್ಯವಸ್ಥೆಯು **fail-open** ಆಗಿದೆ: ಕಾರ್ಯಗತಗೊಳ್ಳುವಾಗ guardrail ದೋಷವನ್ನು ಎಸೆದರೆ,
registry ಆ ದೋಷವನ್ನು ದಾಖಲಿಸಿ, ವಿನಂತಿಯನ್ನು ವಿಫಲಗೊಳಿಸುವ ಬದಲು ಮುಂದಿನ guardrail
ಜೊತೆಗೆ ಮುಂದುವರಿಯುತ್ತದೆ. ನಿರ್ಬಂಧಿಸುವುದು ಸ್ಪಷ್ಟ ನಿರ್ಧಾರವಾಗಿದೆ (`block: true`),
ಎಂದಿಗೂ ಆಕಸ್ಮಿಕವಲ್ಲ.

## ನಿರ್ಮಿತ ಗಾರ್ಡ್‌ರೇಲ್ಸ್

ನೋಂದಣಿ ಆಮದು ಮಾಡುವಾಗ ಪ್ರಾಥಮಿಕ ಆದ್ಯತೆಯ ಆಕ್ರಮದಲ್ಲಿ ಆಟೋ-ಲೋಡ್ ಆಗುವ ಆರು ಗಾರ್ಡ್‌ರೇಲ್ಸ್ (ಕೋಡ್ `registry.ts` → `registerDefaultGuardrails()`):

| ಆದ್ಯತೆ | ಹೆಸರು               | ಹಂತ(ಗಳು)       | ಫೈಲ್                  |
| ------ | ------------------- | -------------- | --------------------- |
| `5`    | `vision-bridge`     | `preCall`      | `visionBridge.ts`     |
| `6`    | `audio-bridge`      | `preCall`      | `audioBridge.ts`      |
| `7`    | `video-bridge`      | `preCall`      | `videoBridge.ts`      |
| `10`   | `pii-masker`        | `pre` + `post` | `piiMasker.ts`        |
| `20`   | `prompt-injection`  | `preCall`      | `promptInjection.ts`  |
| `95`   | `credential-masker` | `pre` + `post` | `credentialMasker.ts` |

ಕಡಿಮೆ ಆದ್ಯತೆ ಸಂಖ್ಯೆಗಳು **ಮೊದಲು** ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತವೆ.

### ದೃಷ್ಟಿ ಬ್ರಿಡ್ಜ್ (`visionBridge.ts`) — ಮೋಡಾಲಿಟಿ ಬ್ರಿಡ್ಜ್ PR-1

**ಅದೃಷ್ಟಿ ಮಾದರಿಗಳಿಗೆ** ಗುರಿಯಾಗಿರುವ ಚಿತ್ರ-ಧಾರಿತ ವಿನಂತಿಗಳನ್ನು ಅಡ್ಡಗಟ್ಟುತ್ತದೆ ಮತ್ತು ಸಂಪೂರ್ಣ ವಿನಂತಿಯನ್ನು ದೃಷ್ಟಿ-ಸಾಧ್ಯ ಮಾದರಿಗೆ ಪುನರ್‌ನಿರ್ದೇಶಿಸುತ್ತದೆ ಅಥವಾ ಮೇಲ್ಮಟ್ಟದ ಕರೆಗೂ ಮುನ್ನ ಕಾನ್ಫಿಗರ್‌ ಮಾಡಬಹುದಾದ ದೃಷ್ಟಿ ಮಾದರಿಯ ಮೂಲಕ ಉತ್ಪಾದಿತ ಪಠ್ಯ ವಿವರಣೆಗಳೊಂದಿಗೆ ಚಿತ್ರ ಭಾಗಗಳನ್ನು ಬದಲಾಯಿಸುತ್ತದೆ. ಇದು ಪಠ್ಯ-ಮಾತ್ರ ಒದಗಿಸುವವರಿಗೆ ಬಹು-ಮೋಡಲ್ ಪೇಲೋಡ್‌ಗಳನ್ನು ಪಾರದರ್ಶಕವಾಗಿ ನಿರ್ವಹಿಸಲು ಅನುಮತಿಸುತ್ತದೆ.

ಹರಿವು:

1. ಗುರಿ ಮಾದರಿ ಈಗಾಗಲೇ ದೃಷ್ಟಿಯನ್ನು ಬೆಂಬಲಿಸುತ್ತಿದ್ದರೆ (ಬಲವಾದ-ಬ್ರಿಡ್ಜ್ ಪಟ್ಟಿಯಲ್ಲಿ `isVisionBridgeForcedModel` ಕಾಣದಿದ್ದರೆ) ಬಿಟ್ಟು ಹೋಗಿ.
2. `extractImageParts(messages)` ಮೂಲಕ ಚಿತ್ರ ಭಾಗಗಳನ್ನು ತೆಗೆದುಹಾಕಿ (`visionBridgeHelpers.ts`), ಇದು **ಊಟಾದ ಮಾಧ್ಯಮ ಪತ್ತೆಗಾರ** `detectMediaParts()` ಗೆ ನಿಯೋಜಿಸುತ್ತದೆ `open-sse/utils/mediaParts.ts` — ಕಾಂಬೋ ಹೊಂದಾಣಿಕೆ ಫಿಲ್ಟರ್‌ೊಂದಿಗೆ ಹಂಚಿಕೊಳ್ಳುವ ಏಕೈಕ ಸತ್ಯದ ಮೂಲ. ತೆಗೆದುಹಾಕುವುದು `replaceImageParts` ಪುನಃ ಸೇರಿಸಲು ಸಾಧ್ಯವಾಗುವ ಶ್ರೇಣಿಯ ಮೇಲ್ಮಟ್ಟದ ಭಾಗಗಳಿಗೆ ಅನುಮತಿಸಲಾಗಿದೆ (ತೆಗೆದುಹಾಕು↔ಬದಲಾಯಿಸುವ ಒಪ್ಪಂದ): OpenAI `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL `source.type:"url"`, ಮತ್ತು Responses API `input_image`. ನೆಟ್ಟಗೆ ಹಿಟ್‌ಗಳು ಮತ್ತು ಸೂಚಕ-ಮಾತ್ರ ಶ್ರೇಣಿಗಳು ಕಾಂಬೋ-ಫಿಲ್ಟರ್ ವಸ್ತು ಮತ್ತು ಎಂದಿಗೂ ತೆಗೆದುಹಾಕಲಾಗುವುದಿಲ್ಲ. ಯಾವುದೂ ಕಂಡುಬಂದಿಲ್ಲದಿದ್ದರೆ ಬಿಟ್ಟು ಹೋಗಿ.
3. `resolveVisionBridgeRuntimeSettings()` ಮೂಲಕ ಕಾರ್ಯಾಚರಣೆ ಕಾನ್ಫಿಗ್ ಅನ್ನು ಪರಿಹರಿಸಿ (`src/shared/constants/modalityBridgeDefaults.ts`): ಹೊಸ `modalityBridge*` ಸೆಟ್ಟಿಂಗ್ ಕೀಗಳು ಗೆಲ್ಲುತ್ತವೆ; ಹಳೆಯ `visionBridge*` ಕೀಗಳು **ಒಂದು-ಚಕ್ರದ ಹಿಂಬಾಲಣೆ** (ರೋಲ್‌ಬಾಕ್ ಕಿಟಕಿಯ). ಬ್ರಿಡ್ಜ್ ಅಸಕ್ರಿಯವಾಗಿರುವಾಗ ಯಾವುದೇ ಮಾಧ್ಯಮ ಪಥದ ಮುನ್ನ ಬಿಟ್ಟು ಹೋಗಿ.
4. ಮೋಡ್ ಆಯ್ಕೆಯು (`modalityBridgeVisionMode`, ಕೆಳಗಿನ ಪಟ್ಟಿಯನ್ನು ನೋಡಿ) ಪುನರ್‌ನಿರ್ದೇಶನ ವಿರುದ್ಧ ವಿವರಣೆ ನಿರ್ಧರಿಸುತ್ತದೆ. ಪುನರ್‌ನಿರ್ದೇಶನವು `modifiedPayload` ಅನ್ನು ಮಾತ್ರ `model` ಬದಲಾಯಿತಾದಂತೆ, ಜೊತೆಗೆ ಮೆಟಾ `{ rerouted, fromModel, toModel, imagesKept }` ಅನ್ನು ಹಿಂತಿರುಗಿಸುತ್ತದೆ.
5. ವಿವರಣೆ ಮಾರ್ಗ: `maxImages` ನಲ್ಲಿ ಚಿತ್ರಗಳನ್ನು ಮಿತಿಗೊಳಿಸಿ, ಕಾರ್ಯ-ಜ್ಞಾನದ ಪ್ರಾಂಪ್ಟ್ ಅನ್ನು ರೂಪಿಸಿ, ವಿವರಣೆ ಕಾಶ್ ಅನ್ನು ಪರಿಗಣಿಸಿ, ದೃಷ್ಟಿ ಮಾದರಿಯನ್ನು **ಪ್ಯಾರಲೆಲ್‌ನಲ್ಲಿ** ಕರೆ ಮಾಡಿ (`Promise.allSettled`), ಮತ್ತು `[Image N]: <description>` ಪಠ್ಯ ಭಾಗಗಳನ್ನು ಅವರ ಸ್ಥಳದಲ್ಲಿ ಸೇರಿಸಿ. ವಿಫಲವಾದ ವಿವರಣೆ `null` ಅನ್ನು ನೀಡುತ್ತದೆ ಮತ್ತು ಮೂಲ ಚಿತ್ರ ಭಾಗವು **ಕಾಪಾಡಲಾಗುತ್ತದೆ** (#4012) — ಎಲ್ಲ ವಿವರಣೆ ವಿಫಲವಾದಾಗ ಕಾಂಬೋ ವಿವರಣೆ ಮಾರ್ಗದಲ್ಲಿ ಹೊರತುಪಡಿಸಿ, ದೃಷ್ಟಿ-ಸಾಧ್ಯ ಒದಗಿಸುವವರೊಂದಿಗೆ ದೃಢೀಕೃತ ಅಸಾಧ್ಯ ಮೇಲ್ಮಟ್ಟಕ್ಕೆ `(unavailable — no vision-capable provider connected)` ಸ್ಟಬ್ ಅನ್ನು ಬದಲಾಗಿ ನೀಡುತ್ತದೆ (#8430).
6. `modifiedPayload` + ಮೆಟಾ (`imagesProcessed`, `descriptions`, `processingTimeMs`, `visionModel`) ಅನ್ನು ಹಿಂತಿರುಗಿಸಿ.

#### ಮೋಡ್ ಆಯ್ಕೆಗಾರ (`modalityBridgeVisionMode`)

| ಮೋಡ್       | ಡೀಫಾಲ್ಟ್ | ವರ್ತನೆ                                                                                                                                                                                                                                                                               |
| ---------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `auto`     | ✔        | ಹಳೆಯ ಹೊರಿಕೆಯನ್ನು, ಬದಲಾಯಿಸಲಾಗದ (#6640/#7204): ನಾನ್-ಕಾಂಬೋ/`auto/` ಮಾದರಿಗಳು ಉತ್ತಮ ದೃಷ್ಟಿ ಮಾದರಿಗೆ ಪುನರ್‌ನಿರ್ದೇಶಿಸುತ್ತವೆ, ಮೂಲ ಮಾದರಿಯು ಬಳಸಬಹುದಾದ ಪ್ರಮಾಣಪತ್ರಗಳನ್ನು ಹೊಂದಿದ್ದರೆ (ಅಂದರೆ ವಿವರಣೆ); ಕಾಂಬೋ ಗುರಿಗಳು ಯಾವಾಗಲೂ ವಿವರಣೆ ನೀಡುತ್ತವೆ.                                                      |
| `describe` |          | ಯಾವಾಗಲೂ ವಿವರಣೆ — ಪುನರ್‌ನಿರ್ದೇಶನ ಬ್ಲಾಕ್ ಸಂಪೂರ್ಣವಾಗಿ ಬಿಟ್ಟುಹೋಗುತ್ತದೆ; ಬಳಕೆದಾರನ ಆಯ್ಕೆಯಾದ ಮಾದರಿ ಯಾವಾಗಲೂ ಉತ್ತರಿಸುತ್ತದೆ.                                                                                                                                                                   |
| `reroute`  |          | ಬಲವಾದ ಪುನರ್‌ನಿರ್ದೇಶನ: ಕೀಪ್-ಕ್ರೆಡೆನ್ಷಿಯಲ್-ಮಾಡಲ್ ಗಾರ್ಡ್ ಅನ್ನು ಬದಲಾಗುತ್ತದೆ. ಪುನರ್‌ನಿರ್ದೇಶನ-**ಗುರಿ** ಕ್ರೆಡೆನ್ಷಿಯಲ್ ಗಾರ್ಡ್ ಇನ್ನೂ ಅನ್ವಯಿಸುತ್ತದೆ — ಬಳಸಬಹುದಾದ ದೃಷ್ಟಿ ಗುರಿ ಇಲ್ಲದಾಗ, ವಿನಂತಿ ವಿವರಣೆಗೆ ಬಿದ್ದುಹೋಗುತ್ತದೆ, ಆದ್ದರಿಂದ ಕಚ್ಚಾ ಚಿತ್ರಗಳು ಪಠ್ಯ-ಮಾತ್ರ ಬೆಂಡಕ್ಕೆ ಎಂದಿಗೂ ತಲುಪುವುದಿಲ್ಲ (#8430). |

ಬಲವಾದ ಮೋಡ್‌ಗಳು **ಆಟೋ ಹೊರಿಕೆಯನ್ನು** ಕಾರ್ಯನಿರ್ವಹಿಸುವ ಮೊದಲು ಶಾರ್ಟ್-ಸರ್ಕ್ಯೂಟ್ ಮಾಡುತ್ತವೆ; `auto` ವರ್ತನೆ pre-PR-1 ಗಾರ್ಡ್‌ರೇಲ್‌ಗೆ ಬೈಟ್-ಐಡೆಂಟಿಕಲ್ ಆಗಿದೆ.

#### ಕಾರ್ಯ-ಜ್ಞಾನದ ವಿವರಣೆ ಪ್ರಾಂಪ್ಟ್ (`modalityBridgeVisionTaskAware`)

ಡೀಫಾಲ್ಟ್ **ಸತ್ಯ**. `composeVisionPrompt()` (`visionBridgeHelpers.ts`) ಕೊನೆಯ ಬಳಕೆದಾರ ಸಂದೇಶದ ಪಠ್ಯವನ್ನು (500 ಅಕ್ಷರಗಳಿಗೆ ಕಡಿತಗೊಳಿಸಲಾಗಿದೆ) ಮೂಲ ವಿವರಣೆ ಪ್ರಾಂಪ್ಟ್‌ಗೆ ಸೇರಿಸುತ್ತದೆ, ವಿವರಣೆಯನ್ನು ಬಳಕೆದಾರನು ವಾಸ್ತವವಾಗಿ ಕೇಳಿದದ್ದಕ್ಕೆ ತಿರುಗಿಸುತ್ತದೆ (ಕೋಡೆಕ್ಸ್-ದೃಷ್ಟಿ-ಪ್ರಾಕ್ಸಿ ಮಾದರಿ) ಮತ್ತು ದೃಷ್ಟಿ ಮಾದರಿಯು ದೃಶ್ಯ ಪಠ್ಯವನ್ನು ವರ್ಗಾಯಿಸಲು ಕೇಳುತ್ತದೆ. ಧ್ವಜವನ್ನು выключить ಮಾಡಿದಾಗ — ಅಥವಾ ಬಳಕೆದಾರ ಪಠ್ಯವಿಲ್ಲ — ಮೂಲ ಪ್ರಾಂಪ್ಟ್ ಬದಲಾಯಿಸಲಾಗದೆ ಬಳಸಲಾಗುತ್ತದೆ.

The describe self-loop's own OpenAI-compatible request (`callVisionModelSingle()`
in `visionBridgeHelpers.ts`) ಯಾವಾಗಲೂ `image_url.detail: "high"` ಅನ್ನು ಕೇಳುತ್ತದೆ —
ಅನಿವಾರ್ಯವಾಗಿ, ಪ್ರತಿ ಕರೆಗಾರ/ಪೂರೈಕೆದಾರರಿಗಾಗಿ, ಯಾವುದೇ ಕ್ಲೈಂಟ್ ಸಂಕೇತದ ಮೇಲೆ ನಿರ್ಬಂಧಿತವಾಗಿಲ್ಲ.
ಕೀಳ್ಮಟ್ಟದ ಮಾದರಿಯ ಮಾದರಿಯು OCR ಶುದ್ಧತೆಯನ್ನು ಹಾಳು ಮಾಡುತ್ತದೆ, ಈ ಪ್ರಾಂಪ್ಟ್ ಕೇಳುವ
ಪಠ್ಯ-ಪರಿವರ್ತನೆಯ ಕಾರ್ಯಕ್ಕಾಗಿ, ಆದ್ದರಿಂದ ವಿವರಣೆ ಕರೆ ಸ್ವತಃ ಯಾವಾಗಲೂ ಉನ್ನತ
ವಿವರವನ್ನು ಕೇಳುತ್ತದೆ, ಮೂಲ ಪ್ರವೇಶದ ವಿನಂತಿಯು ಯಾವ ವಿವರ ಮಟ್ಟವನ್ನು ಬಳಸಿದರೂ. ಇದು
ಆಂತರಿಕ ವಿವರಣೆ ವಿನಂತಿಯ ಶರೀರವನ್ನು ಮಾತ್ರ ಪ್ರಭಾವಿತ ಮಾಡುತ್ತದೆ; ಇದು OmniRoute
ಕರೆಗಾರನ ಸ್ವಂತ `image_url.detail` ಅನ್ನು ಪ್ರಾಥಮಿಕ ವಿನಂತಿಯಲ್ಲಿ ಹೇಗೆ ಮುಂದುವರಿಸುತ್ತೆ ಎಂಬುದನ್ನು
ಬದಲಾಯಿಸುವುದಿಲ್ಲ — ಆ ಡೀಫಾಲ್ಟ್ ಅನ್ನು ಪ್ರತ್ಯೇಕವಾಗಿ, ಮತ್ತು ಕೇವಲ ಪತ್ತೆಹಚ್ಚಿದ OpenCode
ಕ್ಲೈಂಟ್‌ಗಳಿಗೆ ಮಾತ್ರ ಅನ್ವಯಿಸಲಾಗುತ್ತದೆ, `defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`).
ವಿವರಣೆ ಸ್ವತಃ-ಲೂಪ್‌ನ Anthropic ವೈರ್-ಫಾರ್ಮಾಟ್ ಶಾಖದಲ್ಲಿ ಯಾವುದೇ `detail` ಕ್ಷೇತ್ರವಿಲ್ಲ
ಮತ್ತು ಎರಡೂ ಡೀಫಾಲ್ಟ್‌ಗಳಿಂದ ಪ್ರಭಾವಿತವಾಗುವುದಿಲ್ಲ.

#### Describe output cap (`modalityBridgeVisionMaxChars`)

| ಕೀ                             | ಡೀಫಾಲ್ಟ್ | ಶ್ರೇಣೀ             |
| ------------------------------ | -------- | ------------------ |
| `modalityBridgeVisionMaxChars` | `0`      | `0` ಅಥವಾ 100–50000 |

`0` (ಡೀಫಾಲ್ಟ್) ಅಂದರೆ **ಯಾವುದೇ ಮಿತಿಯಿಲ್ಲ** — `callVisionModel()` ಮೂಲಕ
ಮರುಕಳಿಸಿದ ವಿವರಣೆ ಬದಲಾಯಿಸಲಾಗುವುದಿಲ್ಲ, ಇತ್ತೀಚಿನ ವರ್ತನೆಯನ್ನು ಉಳಿಸುತ್ತದೆ. 100–50000
ಶ್ರೇಣಿಯಲ್ಲಿನ ಯಾವುದೇ ಮೌಲ್ಯವು ವಿವರಣೆಯನ್ನು `…` ಉಪಸರ್ಗದೊಂದಿಗೆ ಕತ್ತರಿಸುತ್ತದೆ
ಮರುಕಳಿಸುವ ಮೊದಲು `[Image N]: <description>` ಆಗಿ
(`VisionBridgeGuardrail.preCall()` in `src/lib/guardrails/visionBridge.ts`).
ಈನ್ನು ವಿವರ-ಭಾರಿತ OCR ಕಾರ್ಯಗಳಿಗೆ ಹೆಚ್ಚಿಸಿ, ಅಲ್ಲಿ ಕೆಳಗಿನ ಮಾದರಿಯು ಸಂಪೂರ್ಣ
ಪಠ್ಯ-ಪರಿವರ್ತನೆಯ ಅಗತ್ಯವಿದೆ; ಚಾಟಿ ದೃಶ್ಯ ಮಾದರಿಗಳಲ್ಲಿ ಟೋಕನ್ ಬಳಕೆಯನ್ನು ನಿರ್ಬಂಧಿಸಲು
ಇದನ್ನು ಕಡಿಮೆ ಮಾಡಿ. ಡ್ಯಾಶ್‌ಬೋರ್ಡ್ ಕ್ಷೇತ್ರವು Vision ಟ್ಯಾಬ್‌ನ ಉನ್ನತ ಪ್ಯಾನೆಲ್‌ನಲ್ಲಿ
(`modality-bridge-max-chars` in `ModalityBridgeVisionTab.tsx`) ಇರುತ್ತದೆ ಮತ್ತು 1 ಮತ್ತು 99
ಮಧ್ಯೆ ಯಾವುದೇ ಮೌಲ್ಯವನ್ನು 100 ನೆಲಕ್ಕೆ ಕಟ್ಟಿ ಹಾಕುತ್ತದೆ, ಆದರೆ ಸ್ಪಷ್ಟ `0` ಅನ್ನು
ಅನಗಡವಾಗಿ ಬಿಡುತ್ತದೆ — `0` ತನ್ನದೇ ಆದ ಮಾನ್ಯ Zod ಮೌಲ್ಯವಾಗಿದೆ
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`), ಕೇವಲ
"ಸೆಟ್ನಿಲ್ಲದ" ಡೀಫಾಲ್ಟ್ ಅಲ್ಲ.

#### Describe cache (`modalityBridge/bridgeCache.ts`)

ವಿವರಣೆ ಔಟ್‌ಪುಟ್‌ಗಳಿಗೆ ಮೆಮೊರಿ LRU + TTL ಕ್ಯಾಶ್, ಹಂಚಿದ ಪ್ರಕ್ರಿಯೆ-ವಿಸ್ತಾರ.
ಕೀ = `sha256(imageRef + composedPrompt + configuredBridgeModel)` ದೀರ್ಘ-ಪೂರ್ವಕ
ಫ್ರೇಮಿಂಗ್ (ಯಾವುದೇ ಕ್ಷೇತ್ರ-ಬೌಂಡರಿ ಸಂಘರ್ಷಗಳಿಲ್ಲ). ಮಾದರಿ ಘಟಕವು
**ಕಾನ್‌ಫಿಗರ್‌ಡ್** ಬ್ರಿಡ್ಜ್ ಮಾದರಿಯಾಗಿದೆ, ವಾಸ್ತವದಲ್ಲಿ ಉತ್ತರಿಸಿದ ಮಾದರಿ ಅಲ್ಲ —
`callVisionModel` ಆಂತರಿಕವಾಗಿ ಹಿಂತಿರುಗಬಹುದು, ಮತ್ತು ಪ್ರತಿ ಪ್ರಯತ್ನಕ್ಕೆ ಕೀ ಹಾಕುವುದು
ಕ್ಯಾಶ್ ಅನ್ನು ತುಂಡು ಮಾಡುತ್ತದೆ. ವಿಫಲವಾದ ವಿವರಣೆಗಳನ್ನು ಎಂದಿಗೂ ಕ್ಯಾಶ್ ಮಾಡಲಾಗುವುದಿಲ್ಲ. ಸೆಟ್ಟಿಂಗ್‌ಗಳು:

| ಕೀ                              | ಡೀಫಾಲ್ಟ್ | ಶ್ರೇಣೀ  |
| ------------------------------- | -------- | ------- |
| `modalityBridgeCacheEnabled`    | `true`   | —       |
| `modalityBridgeCacheTtlMinutes` | `60`     | 1–1440  |
| `modalityBridgeCacheMaxEntries` | `200`    | 10–5000 |

#### Remote image normalization (self-loop describe/base64 fetch)

ಬ್ರಿಡ್ಜ್ **ದೂರದ** ಚಿತ್ರವನ್ನು ಸ್ವತಃ ಪಡೆಯುವಾಗ — Anthropic ವಿವರಣೆ
ಸ್ವತಃ-ಕೋಲ ಮತ್ತು ಕ್ಲೋಡ್-ವೈರ್-ಫಾರ್ಮಾಟ್ base64 ಪರಿವರ್ತನೆ
(`ensureBase64ImagesForClaudeWire`), ಎರಡೂ ಮೂಲಕ
`fetchRemoteImageAsDataUri()` in `visionBridgeHelpers.ts` — ಫಲಿತಾಂಶದ ಡೇಟಾ
URI ಅನ್ನು `normalizeDataUri()`
(`open-sse/utils/imageNormalize.ts`) ಮೂಲಕ ಹಾರಿಸುತ್ತಾರೆ, ನಂತರ ದೃಶ್ಯ-ಮಾದರಿ
ವಿನಂತಿಯಲ್ಲಿ ಅಳವಡಿಸಲಾಗುತ್ತದೆ. ದೊಡ್ಡ ಚಿತ್ರಗಳನ್ನು **2048px ದೀರ್ಘ ಅಂಚು** ಗೆ
ಕೀಳ್ಮಟ್ಟಕ್ಕೆ ಇಳಿಸಲಾಗುತ್ತದೆ (OpenAI/Anthropic ಈಗಾಗಲೇ ಸರ್ವರ್-ಪಕ್ಷದಲ್ಲಿ
ಅನ್ವಯಿಸುತ್ತಿರುವ ಪುನರ್-ಆಕಾರದ ಮಿತಿಯನ್ನು ಹೊಂದಿಸುತ್ತದೆ), ಇದು ಅಪ್ಲೋಡ್ ಬಿಟ್‌ಗಳನ್ನು/ವಿಲಂಬವನ್ನು
ಕತ್ತರಿಸುತ್ತದೆ, ಆದರೆ ದೃಶ್ಯ ಮಾದರಿ ಏನು ನೋಡುತ್ತದೆ ಎಂಬುದನ್ನು ಬದಲಾಯಿಸುವುದಿಲ್ಲ. ಪುನರ್-ಆಕಾರ
`sharp` ಅನ್ನು ಬಳಸುತ್ತದೆ, ಡೈನಾಮಿಕ್ ಇಂಪೋರ್ಟ್ ಮೂಲಕ ಲೋಡ್ ಮಾಡಲಾಗಿದೆ: ಅದರ ಸ್ವದೇಶಿ
ಬೈನರಿ ಲೋಡ್ ಮಾಡಲು ವಿಫಲವಾದ ವೇದಿಕೆಯ ಮೇಲೆ, `normalizeDataUri()` **ಎಂದಿಗೂ
ಹಾರಿಸುವುದಿಲ್ಲ** — ಇದು ಮೂಲ ಬಿಟ್‌ಗಳ ಪಾಸ್ತ್‌ಥ್ರೂಗೆ ಹಿಂತಿರುಗುತ್ತದೆ, ಆದ್ದರಿಂದ
ವಿವರಣೆ/base64-ಪರಿವರ್ತನೆಯ ಮಾರ್ಗವು ಯಾವಾಗಲೂ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತಿದೆ. ಚಿತ್ರವಲ್ಲದ ಬಿಟ್‌ಗಳು
(ಏಕೀಕೃತ ಚಿತ್ರವನ್ನು ಹಿಂತಿರುಗಿಸದ ಫೆಚ್) ಕೂಡ ಸ್ಪಷ್ಟವಾಗಿ ಪಾಸ್ತ್‌ಥ್ರೂಗೆ ಹೋಗುತ್ತವೆ.
ಈ ನಾರ್ಮಲೈಸೇಶನ್ ಬ್ರಿಡ್ಜ್ ತನ್ನ ಸ್ವಂತ ಸ್ವತಃ-ಕೋಲಿಗಾಗಿ ಪಡೆಯುವ ಚಿತ್ರಗಳಿಗೆ ಮಾತ್ರ
ಹೆಚ್ಚಾಗುತ್ತದೆ — ಇದು ಕರೆಗಾರನ ಕಚ್ಚಾ ಪಾಸ್ತ್‌ಥ್ರೂ ಪೇಲೋಡ್‌ಗೆ ಎಂದಿಗೂ ಅನ್ವಯಿಸಲಾಗುವುದಿಲ್ಲ,
ಆಪ್ಟ್-ಇನ್-ಮಾತ್ರ ಪರಿವರ್ತನೆಯ ತತ್ವದೊಂದಿಗೆ (ಹಾರ್ಡ್ ರೂಲ್ #20).

ವಿವರಣೆ-ಪರಿವರ್ತಿತ ಪ್ರತಿಸ್ಪಂದನೆಗಳು
`x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>`

`GET /api/modality-bridge/stats` (ನಿರ್ವಹಣಾ ಪ್ರಮಾಣೀಕರಣ, `GET /api/settings` ಗೆ
ಸಮಾನ ತೀರ್) ಮೆಮೊರಿ ಪ್ರತಿ-ಮೋಡಾಲಿಟಿ ಕೌಂಟರ್‌ಗಳನ್ನು
`{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs,
latencySamples, averageLatencyMs, lastUsedAt }` `vision`, `audio`, ಮತ್ತು
`video` ಗೆ ಹಿಂತಿರುಗಿಸುತ್ತದೆ. `averageLatencyMs` `latencySamples` ಅನ್ನು ಬಳಸುತ್ತದೆ,
ಎಲ್ಲಾ ಪ್ರಯತ್ನಗಳನ್ನು ಅಲ್ಲ, ಅದರ ಹಂಚಿಕೆದಾರರಾಗಿ; ಸಮಯವಿಲ್ಲದ ಕಾರ್ಯವು ಶೂನ್ಯ-ಮಿಲಿಸೆಕೆಂಡು
ನಮೂನೆಯು ತಯಾರಿಸುವುದಿಲ್ಲ. `bridged` ಯಶಸ್ವಿ ಪರಿವರ್ತನೆಗಳಿಗೆ ಹಿಂಬಾಲಿಸುವ
ಅಲಿಯಾಸ್ ಆಗಿರುತ್ತದೆ; ವಿಫಲ ಪ್ರಯತ್ನಗಳು ಇದನ್ನು ಹೆಚ್ಚಿಸುವುದಿಲ್ಲ.
ಕೌಂಟರ್‌ಗಳು ಪ್ರಕ್ರಿಯೆ ಪುನಾರಂಭದ ಮೇಲೆ ವಿನ್ಯಾಸದಂತೆ ಪುನರಾರಂಭವಾಗುತ್ತವೆ
(ಟೆಲೆಮೆಟ್ರಿ, ಲೆಕ್ಕಹಾಕುವುದು ಅಲ್ಲ).

ದೊಡ್ಡ ಡ್ಯಾಶ್‌ಬೋರ್ಡ್ ಪುಟವು
`/dashboard/settings/modality-bridge` ಆಗಿದೆ. ಇದರ URL-ಗೆ ಲಭ್ಯವಿರುವ `Vision`, `Audio`,
ಮತ್ತು `Video` ಟ್ಯಾಬ್‌ಗಳು `tab` ಮೌಲ್ಯವನ್ನು ಬದಲಾಯಿಸುವಾಗ ಕ್ವೇರಿ ಪ್ಯಾರಾಮೀಟರ್‌ಗಳನ್ನು ಉಳಿಸುತ್ತವೆ.
Vision ಟ್ಯಾಬ್ ಸಕ್ರಿಯತೆ, ಮೋಡ್, ಮಾದರಿ ಆಯ್ಕೆ (ಸ್ವಾಯತ್ತ ಡೀಫಾಲ್ಟ್ ಅನ್ನು ಒಳಗೊಂಡಂತೆ), ಕಾರ್ಯ-ಜ್ಞಾನ ಪ್ರಾಂಪ್ಟಿಂಗ್, ಉನ್ನತ ಟೈಮ್‌ಔಟ್/ಚಿತ್ರ/ವಿವರಣೆ-ಅಗಲ/ಕ್ಯಾಶ್
ಮಿತಿಗಳನ್ನು, ಕಾರ್ಯಾಚರಣೆಯ
ಗಣಕಗಳನ್ನು ಮತ್ತು ರಕ್ಷಿತ ಮಾದರಿ ವಿನಂತಿಯನ್ನು ಬಹಿರಂಗಪಡಿಸುತ್ತದೆ. Audio ಟ್ಯಾಬ್ ಸಹ ಜೀವಂತವಾಗಿದೆ: ಇದು
ಸಕ್ರಿಯತೆ, STT-ಮಾತ್ರ ಮಾದರಿ ಆಯ್ಕೆಗಾರವನ್ನು Auto, ಟೈಮ್‌ಔಟ್/ಅತ್ಯುತ್ತಮ-ಕ್ಲಿಪ್ ಮಿತಿಗಳು, ಆಡಿಯೋ
ಗಣಕಗಳು ಮತ್ತು `input_audio` ಮಾದರಿ ಪರೀಕ್ಷೆಯನ್ನು ಬಹಿರಂಗಪಡಿಸುತ್ತದೆ. Video ಟ್ಯಾಬ್ ಕಾರ್ಯಾತ್ಮಕವಾಗಿದೆ: ಇದು FFmpeg/ffprobe ಕಾರ್ಯಾಚರಣೆಯ ಸ್ಥಿತಿಯನ್ನು ವರದಿ ಮಾಡುತ್ತದೆ — ನಾಲ್ಕು ಸ್ಪಷ್ಟ UI ಸ್ಥಿತಿಗಳಲ್ಲಿ ಒಂದಾಗಿದೆ (`unknown` probe ಹಾರುವಾಗ ಅಥವಾ ಪೂರ್ಣಗೊಳ್ಳಲು ಸಾಧ್ಯವಾಗದಾಗ, `restricted` ಲೂಪ್‌ಬ್ಯಾಕ್ ಡ್ಯಾಶ್‌ಬೋರ್ಡ್ ಹೋಸ್ಟ್‌ನಲ್ಲಿ ಕ್ಲೈಂಟ್-ಪಕ್ಷದಲ್ಲಿ ಪ್ರೋಬ್ ಬಿಟ್ಟುಹೋಗುವಾಗ, `unavailable` ಪ್ರೋಬ್ ಮಾಡಿದ ನಂತರ ಮತ್ತು ಖಚಿತವಾಗಿ ಕೊರತೆಯಾದಾಗ, ಅಥವಾ `available` FFmpeg/ffprobe ಆವೃತ್ತಿಗಳೊಂದಿಗೆ) — ಸಕ್ರಿಯ/ಮಾದರಿ/ಫ್ರೇಮ್/ವೀಡಿಯೋ/ಟೈಮ್‌ಔಟ್ ಮಿತಿಗಳನ್ನು ಉಳಿಸುತ್ತದೆ, ಮಾದರಿ ಆಯ್ಕೆಗಾರವನ್ನು ದೃಷ್ಟಿ-ಸಾಧ್ಯ ಮಾದರಿಗಳಿಗೆ ಶೋಧಿಸುತ್ತದೆ ಮತ್ತು ವೀಡಿಯೋ ಗಣಕಗಳನ್ನು ಬಹಿರಂಗಪಡಿಸುತ್ತದೆ.

AI ಸೆಟಿಂಗ್‌ಗಳ ಅಡಿಯಲ್ಲಿ ಹಳೆಯ Vision Bridge ಕಾರ್ಡ್ ಹೊಸ ಪುಟಕ್ಕೆ ಹೊಂದಾಣಿಕೆಯ ಲಿಂಕ್ ಆಗಿದೆ; ಇದು ಫಾರ್ಮ್‌ನ ಎರಡನೇ ಪ್ರತಿಯನ್ನು ಹೊಂದಿಲ್ಲ. ಮೀಡಿಯಾ ಪೂರೈಕೆದಾರರು ಇಮೇಜ್-ಟು-ಟೆಕ್ಸ್ಟ್ ಮತ್ತು ಸ್ಪೀಚ್-ಟು-ಟೆಕ್ಸ್ಟ್ ಕಾರ್ಯವಿಧಾನಗಳನ್ನು ಸಂಬಂಧಿತ ಮೋಡಾಲಿಟಿ ಬ್ರಿಡ್ಜ್ ಟ್ಯಾಬ್‌ಗಳಿಗೆ ಲಿಂಕ್ ಮಾಡುತ್ತವೆ, ಇತ್ತೀಚಿನ ಸ್ಪೀಚ್-ಟು-ಟೆಕ್ಸ್ಟ್ ಆಟದ ಮೈದಾನವನ್ನು ತೆಗೆದು ಹಾಕದೆ.

**ಸ್ವಯಂ-ಲೂಪ್ ಪ್ರವೇಶ ಬಾಯ್‌ಪಾಸ್:** ವಿವರಣೆ ಕರೆ OmniRoute ನ ಸ್ವಂತ `/v1` ಸ್ವಯಂ-ಲೂಪ್ (ಅನಿಯಮಿತ ಪೂರೈಕೆದಾರ ಮಾದರಿ) ಮೂಲಕ ಮಾರ್ಗದರ್ಶನ ಮಾಡಿದಾಗ, ಉಪ-ವಿನಂತಿ `x-omniroute-admission-bypass: internal` ಅನ್ನು ಕಳುಹಿಸುತ್ತದೆ ಮತ್ತು ಪರಿಹರಿತ ಸ್ವಯಂ-ಲೂಪ್ ಕ್ರೆಡೆನ್ಷಿಯಲ್‌ನೊಂದಿಗೆ ಪ್ರಮಾಣೀಕರಿಸಲಾಗುತ್ತದೆ — ಸ್ಥಳೀಯ `sk_omniroute` ಸ್ಥಳೀಯ ಮೋಡ್‌ನಲ್ಲಿ, ಅಥವಾ ಕಾರ್ಯನಿರ್ವಹಕ-ಕೋಷ್ಟಕ `OMNIROUTE_API_KEY` / `ROUTER_API_KEY` env ಕೀ (#1350) ಆದ್ದರಿಂದ `REQUIRE_API_KEY=true` ನಿಯೋಜನೆಗಳು ಇನ್ನೂ ವಿವರಣೆ ಕರೆ ನಡೆಸಬಹುದು. ಈ ಬಾಯ್‌ಪಾಸ್ ಮಾತ್ರ ಆ ಖಾತರಿಯಾದ ಕ್ರೆಡೆನ್ಷಿಯಲ್‌ಗಳಿಗೆ ಗೌರವಿಸಲಾಗುತ್ತದೆ, ಆದ್ದರಿಂದ ಹೊರಗಿನ ಕ್ಲೈಂಟ್‌ಗಳು ಪ್ರವೇಶವನ್ನು ಬಿಟ್ಟುಹೋಗಲು ಹೆಡರ್ ಅನ್ನು ಬಳಸಲು ಸಾಧ್ಯವಿಲ್ಲ.

ಹಳೆಯ ಡೀಫಾಲ್ಟ್‌ಗಳು `src/shared/constants/visionBridgeDefaults.ts` ನಲ್ಲಿ ಇವೆ; ಹೊಸ ಮೋಡ್/ಕಾರ್ಯ-ಜ್ಞಾನ/ಕ್ಯಾಶ್ ಡೀಫಾಲ್ಟ್‌ಗಳು ಮತ್ತು ಸೆಟಿಂಗ್‌ಗಳ ಪರಿಹಾರವು `src/shared/constants/modalityBridgeDefaults.ts` ನಲ್ಲಿ ಇವೆ. ಗಾರ್ಡ್‌ರೈಲ್ `deps` ನಿರ್ಮಾಪಕ ಆಯ್ಕೆಯನ್ನು ಬಹಿರಂಗಪಡಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ ಪರೀಕ್ಷೆಗಳು ನಕಲಿ `getSettings` ಮತ್ತು `callVisionModel` ಕಾರ್ಯಗತಗೊಳಣೆಗಳನ್ನು ಇಂಜೆಕ್ಟ್ ಮಾಡಬಹುದು.

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

ಆಡಿಯೋ ಹೊಂದಿರುವ ಚಾಟ್ ವಿನಂತಿಗಳನ್ನು ಗುರಿಯ ಕಡೆಗೆ ತಲುಪುವ ಮೊದಲು ಅಡ್ಡಗೊಳ್ಳುತ್ತದೆ, ಅದು ಆಡಿಯೋ ಇನ್ಪುಟ್ ಅನ್ನು ಸ್ವೀಕರಿಸಲು ತಿಳಿದಿಲ್ಲ. ಇದು ಚಾಟ್ ವಿನಂತಿಯನ್ನು ಪುನರ್‌ಮಾರ್ಗಗೊಳಿಸುವುದಿಲ್ಲ: ಆಡಿಯೋ ಭಾಗಗಳನ್ನು ಇತ್ತೀಚಿನ OpenAI-ಅನುಕೂಲವಾದ ಬಹುಭಾಗದ ಎಂಡ್ಪಾಯಿಂಟ್ ಮೂಲಕ ಲಿಖಿತಗೊಳಿಸಲಾಗುತ್ತದೆ ಮತ್ತು ಆಯ್ಕೆ ಮಾಡಿದ ಚಾಟ್ ಮಾದರಿ ಪಠ್ಯ ಲಿಖಿತಗಳೊಂದಿಗೆ ಮುಂದುವರಿಯುತ್ತದೆ.

ಹರಿವು:

1. `getResolvedModelCapabilities()` ಮೂಲಕ `supportsAudio` ಅನ್ನು ಪರಿಹರಿಸಿ. ಸ್ಪಷ್ಟ ಪೂರೈಕೆದಾರ-ರಿಜಿಸ್ಟ್ರಿ ಮೆಟಾಡೇಟಾ ಗೆಲ್ಲುತ್ತದೆ, ನಂತರ ಸ್ಥಿರ ಮಾದರಿ ಮೆಟಾಡೇಟಾ, ನಂತರ ಸಮನ್ವಯಿತ `modalities_input`. `audio` ಇಲ್ಲದ ಘೋಷಿತ ಇನ್ಪುಟ್ ಪಟ್ಟಿಯು `false` ಆಗಿದೆ; ಯಾವುದೇ ಸಾಮರ್ಥ್ಯದ ಸಾಕ್ಷ್ಯವು `null` ಉಳಿಯುತ್ತದೆ. `false` ಮತ್ತು `null` ಎರಡೂ ಸಂರಕ್ಷಣಾತ್ಮಕ ಬ್ರಿಡ್ಜ್ ಅನ್ನು ಸಕ್ರಿಯಗೊಳಿಸುತ್ತವೆ, ಆದರೆ `true` ಇದನ್ನು ಬಾಯ್‌ಪಾಸ್ ಮಾಡುತ್ತದೆ.
2. `modalityBridgeAudio*` ಸೆಟಿಂಗ್‌ಗಳನ್ನು ಪರಿಹರಿಸಿ ಮತ್ತು ಹಂಚಿದ `detectMediaParts()`
   ಡಿಟೆಕ್ಟರ್ ಮೂಲಕ ಪ್ರತಿಯೊಂದು ಸಂದೇಶದಿಂದ ಸ್ಪ್ಲೈಸಬಲ್ ಟಾಪ್-ಲೆವೆಲ್ ಆಡಿಯೋ ಭಾಗಗಳನ್ನು ತೆಗೆದುಕೊಳ್ಳಿ. ಬೆಂಬಲಿತ ವೈರ್ ಶೇಪ್ಗಳು OpenAI `input_audio`, `audio_url`, ಮತ್ತು
   `source.media_type: "audio/*"` ಆಗಿವೆ. ನೆಸ್ಟೆಡ್ ಆಡಿಯೋ ಮಾರ್ಗದರ್ಶನಕ್ಕಾಗಿ ಗುರುತಿಸಲಾಗುತ್ತದೆ ಆದರೆ ಸ್ಪ್ಲೈಸಿಂಗ್ ಮಾರ್ಗದಿಂದ ತೆಗೆದು ಹಾಕಲಾಗುವುದಿಲ್ಲ. ಕೆಲಸವು `modalityBridgeAudioMaxClips` ಮೂಲಕ ಮಿತಿಯಲ್ಲಿದೆ; ನಂತರದ ಭಾಗಗಳು ಅಸ್ಪಷ್ಟವಾಗಿರುತ್ತವೆ.
3. ಕಾನ್ಫಿಗರ್ ಮಾಡಿದ `provider/model` ಅನ್ನು ಗೌರವಿಸಿ, ಅಥವಾ `selectAudioBridgeModel()` ಅನ್ನು `AUDIO_TRANSCRIPTION_PROVIDERS` ಅನ್ನು ಸ್ಥಿರ ಕ್ಯಾಟಲಾಗ್ ಕ್ರಮದಲ್ಲಿ ನಡೆಯಲು ಬಿಡಿ ಮತ್ತು ಬಳಸಬಹುದಾದ ಸಕ್ರಿಯ ಪೂರೈಕೆದಾರ ಕ್ರೆಡೆನ್ಷಿಯಲ್‌ಗಳೊಂದಿಗೆ ಮೊದಲ ಮಾದರಿಯನ್ನು ಆಯ್ಕೆ ಮಾಡಿ.
4. `callAudioTranscription()` base64/data-URI ಆಡಿಯೋವನ್ನು ಬಹುಭಾಗದ `file` ಗೆ ಪರಿವರ್ತಿಸುತ್ತದೆ, ಅಥವಾ ಸಾರ್ವಜನಿಕ-ಮಾತ್ರದ ಹೊರಗಿನ ಗಾರ್ಡ್ ಮೂಲಕ DNS ಪಿನ್ನಿಂಗ್ ಮತ್ತು 25 MB ಮಿತಿಯೊಂದಿಗೆ ದೂರದ `audio_url` ಅನ್ನು ಡೌನ್‌ಲೋಡ್ ಮಾಡುತ್ತದೆ. ನಂತರ ಇದು ಫೈಲ್ ಮತ್ತು ಆಯ್ಕೆ ಮಾಡಿದ ಮಾದರಿಯನ್ನು ಸ್ಥಳೀಯ `/v1/audio/transcriptions` ಸ್ವಯಂ-ಲೂಪ್ ಗೆ POST ಮಾಡುತ್ತದೆ, `resolveSelfLoopBearer()` ಮೂಲಕ ಪ್ರಮಾಣೀಕರಿಸಲಾಗಿದೆ. ಇತ್ತೀಚಿನ ಲಿಖಿತ ಮಾರ್ಗವು ಸಾಮಾನ್ಯ ಕ್ರೆಡೆನ್ಷಿಯಲ್ ಹುಡುಕಾಟ, ಶೀತಲ/ರೇಟ್-ಮಿತಿಯ ನಿರ್ವಹಣೆ ಮತ್ತು ಪೂರೈಕೆದಾರ ವಿತರಣೆಯನ್ನು ನಿರ್ವಹಿಸುತ್ತದೆ.
5. ಯಶಸ್ವಿ ಕರೆಗಳು ತಮ್ಮ ಭಾಗಗಳನ್ನು `[Audio N]: <transcript>` ಮೂಲಕ ಬದಲಾಯಿಸುತ್ತವೆ. ಕರೆಗಳು `Promise.allSettled` ಮೂಲಕ ನಡೆಯುತ್ತವೆ: ವೈಯಕ್ತಿಕ ವಿಫಲತೆ ಮೂಲ ಆಡಿಯೋ ಭಾಗವನ್ನು ಉಳಿಸುತ್ತದೆ (#4012 ಒಪ್ಪಂದ). ಪ್ರತಿಯೊಂದು ಕರೆ ವಿಫಲವಾದರೆ ಮತ್ತು ಗುರಿಯು `supportsAudio === false` ಎಂದು ತೋರಿಸಿದರೆ, ಭಾಗಗಳು
   `[Audio N]: (unavailable — no STT provider connected)` (#8430 ಒಪ್ಪಂದ) ಆಗುತ್ತವೆ. ಅಜ್ಞಾತ ಗುರಿಯು (`null`) ಎಲ್ಲಾ-ವಿಫಲ ಫಲಿತಾಂಶವು ಅಸ್ಪಷ್ಟವಾಗಿರುತ್ತದೆ. ಬಳಸಬಹುದಾದ STT ಕ್ರೆಡೆನ್ಷಿಯಲ್ ಇಲ್ಲದ ಪ್ರಮಾಣಿತ ಪಠ್ಯ-ಮಾತ್ರ ಗುರಿಯು ನೆಟ್‌ವರ್ಕ್ ಕರೆ ನೀಡದೆ ಅದೇ ಸ್ಪಷ್ಟ ಸ್ಟಬ್ ಅನ್ನು ಪಡೆಯುತ್ತದೆ.

ಯಶಸ್ವಿ ಲಿಖಿತಗಳು ಪ್ರಕ್ರಿಯೆ-ವಿಸ್ತೃತ ಮೋಡಾಲಿಟಿ ಬ್ರಿಡ್ಜ್ LRU/TTL ಕ್ಯಾಶ್ ಅನ್ನು ಬಳಸುತ್ತವೆ. ಕೀ ಆಡಿಯೋ ಉಲ್ಲೇಖ, ಸ್ಥಿರ `audio-transcription` ಕಾರ್ಯಾಚರಣೆಯ ಲೇಬಲ್ ಮತ್ತು ಆಯ್ಕೆ ಮಾಡಿದ STT ಮಾದರಿಯನ್ನು ಸಂಯೋಜಿಸುತ್ತದೆ; ವಿಫಲತೆಗಳನ್ನು ಎಂದಿಗೂ ಕ್ಯಾಶ್ ಮಾಡಲಾಗುವುದಿಲ್ಲ. ಆಡಿಯೋ ಪ್ರಯತ್ನಗಳು ಹಂಚಿದ `bridged`, `cacheHits`, `failures`, ಮತ್ತು `lastUsedAt` ಗಣಕಗಳನ್ನು ನವೀಕರಿಸುತ್ತವೆ. ಪರಿವರ್ತಿತ ಪ್ರತಿಸ್ಪಂದನೆಗಳು
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>` ಅನ್ನು ಹೊಂದಿಸುತ್ತವೆ; ಅಸ್ಪಷ್ಟ ವಿನಂತಿಗಳಿಗೆ ಆಡಿಯೋ ಬ್ರಿಡ್ಜ್ ವಿಭಾಗವನ್ನು ಪಡೆಯುವುದಿಲ್ಲ.

ಕಾರ್ಯಾಚರಣೆಯ ಸೆಟಿಂಗ್‌ಗಳು DB-ಆಧಾರಿತ ಮತ್ತು Zod-ಮಾನ್ಯಿತವಾಗಿವೆ:

| ಕೀ                            | ಡೀಫಾಲ್ಟ್ | ಶ್ರೇಣಿಯು         |
| ----------------------------- | -------- | ---------------- |
| `modalityBridgeAudioEnabled`  | `true`   | —                |
| `modalityBridgeAudioModel`    | `""`     | Auto ಅಥವಾ STT ID |
| `modalityBridgeAudioTimeout`  | `60000`  | 1000–300000      |
| `modalityBridgeAudioMaxClips` | `3`      | 1–10             |

ಹಂಚಿದ ಕ್ಯಾಶ್ `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes`, ಮತ್ತು `modalityBridgeCacheMaxEntries` ಮೂಲಕ ನಿಯಂತ್ರಿತವಾಗಿರುತ್ತದೆ.

### Video Bridge (`videoBridge.ts`, `videoBridgePipeline.ts`)

Chat Completions `messages` ಮತ್ತು Responses API `input` ಗೆ ಗುರಿಯಾಗಿರುವ ಸ್ಥಳೀಯ ವಿಡಿಯೋ ಬೆಂಬಲವನ್ನು ತಿಳಿಯದ ಮುನ್ನ, ಟಾಪ್-ಲೆವೆಲ್ ವಿಡಿಯೋ ಭಾಗಗಳನ್ನು ಹಸ್ತಕ್ಷೇಪಿಸುತ್ತದೆ. ಬೆಂಬಲಿತ ರೂಪಗಳು `input_video`, `video_url`, `video_source`, HTTPS URLs, ಮತ್ತು `data:video/*;base64,...` ಡೇಟಾ URI ಗಳಾಗಿವೆ. ಪ್ಲೇನ್ ಫೈಲ್ ಹೆಸರುಗಳನ್ನು ಪಠ್ಯದಲ್ಲಿ ವಿಡಿಯೋ ಎಂದು ಪರಿಗಣಿಸಲಾಗುವುದಿಲ್ಲ.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) ವಿನಂತಿಯ ಪ್ರವಾಸ, ಸಾಮರ್ಥ್ಯ/ನೀತಿ ಪರಿಶೀಲನೆ, ಪ್ರತಿ ವಿನಂತಿಯ ಒಟ್ಟುಗೂಡಿಸುವಿಕೆ, ಮತ್ತು ಪ್ರತಿಕ್ರಿಯೆ ಪೇಲೋಡ್ ಅನ್ನು ಹೊಂದಿದೆ. ಪ್ರತಿ ವಿಡಿಯೋ ಕಾರ್ಯ — ಸಂಪಾದನೆ, ಸಂಪೂರ್ಣ-ಫಲಿತಾಂಶ ಕ್ಯಾಶ್, ಫ್ರೇಮ್ ಕ್ರಮವನ್ನು ವಿವರಿಸುವುದು (ಯಾವುದೇ ಕರೆ ಮಾಡಿದವರು ಘೋಷಿಸಿದ ಧ್ವನಿ ಪಠ್ಯವನ್ನು ವಿಲೀನಗೊಳಿಸುತ್ತದೆ), ಮತ್ತು ಪ್ರತಿ ಪ್ರಯತ್ನದ ಮೆಟ್ರಿಕ್/ಅಬಾರ್ಟ್/ಕ್ಲೀನಪ್ — `processVideoPart` ನಲ್ಲಿ ಮರೆಮಾಚಲಾಗಿದೆ, ಇದು `videoBridgePipeline.ts` ನಲ್ಲಿ `preCall` ನ ಲೂಪ್ನಲ್ಲಿ ಪ್ರತಿ ವಿಡಿಯೋ ಭಾಗಕ್ಕೆ ಒಮ್ಮೆ ಕರೆ ಮಾಡುತ್ತದೆ. ಆ ಮೋಡ್ಯೂಲ್ ಸ್ಪಷ್ಟ ಪೋರ್ಟ್ ಗಡಿಗಳನ್ನು `VideoMediaBrokerPort` (ಬೈಟ್ಗಳನ್ನು ಪಡೆಯುವುದು ಮತ್ತು ಮಾದರಿಯ ಫ್ರೇಮ್‌ಗಳನ್ನು ತೆಗೆದುಹಾಕುವುದು), `VideoAudioTranscriptionPort` (ಕರೆ ಮಾಡಿದವರು ಘೋಷಿಸಿದ ಧ್ವನಿ ಪಠ್ಯವನ್ನು ಮಾದರಿಯ ಶೀರ್ಷಿಕೆಗಳೊಂದಿಗೆ ವಿಲೀನಗೊಳಿಸುವುದು), ಮತ್ತು `VideoDrilldownPort` (ಹಳೆಯ ಕಚ್ಚಾ-ಸ್ಟೋರ್ ರೂಪ) ಅನ್ನು ವ್ಯಾಖ್ಯಾನಿಸುತ್ತದೆ. ಉತ್ಪಾದನಾ STT ಮತ್ತು ಫ್ರೇಮ್ ಉಳಿಸುವಿಕೆ ವಿವರಿಸುವ ಪೋರ್ಟ್ ಮೂಲಕ `createVideoSttAdapter` ಮತ್ತು `createVideoDrilldownAdapter` ಅನ್ನು ಸಿದ್ಧಪಡಿಸಲಾಗಿದೆ; ನಂತರದವು ಹಂಚಿದ ಅಸ್ಪಷ್ಟ-ಹ್ಯಾಂಡಲ್ ಜೀವನಚರ್ಯೆಯನ್ನು ಬಳಸುತ್ತದೆ.

ಸಾರ್ವಜನಿಕ `/v1` ವಿನಂತಿ ಮಾರ್ಗವು ಎಂದಿಗೂ ಉಪಪ್ರಕ್ರಿಯೆಯನ್ನು ಆಮದು ಅಥವಾ ಕರೆ ಮಾಡುವುದಿಲ್ಲ. ದೂರದ ವಿಡಿಯೋಗಳು 50 MiB ಗಡಿಯಲ್ಲಿ ಡೌನ್‌ಲೋಡ್ ಮಾಡಲಾಗುತ್ತವೆ; ಇನ್‌ಲೈನ್ ಬೇಸ್64 ವಿಡಿಯೋಗಳಿಗೆ 36 MiB ಡಿಕೋಡ್ ಮಾಡಿದ ಪ್ರತಿ ವಿಡಿಯೋ ಗಡಿಯನ್ನು ಹೊಂದಿದ್ದು, ಮಾದರಿಯ/ಸಂದೇಶಗಳು/ಫ್ರೇಮಿಂಗ್ ಎನ್ವೆಲಪ್ ಸಾರ್ವಜನಿಕ JSON ವಿನಂತಿ ಪ್ರವೇಶ ಮಿತಿಯ 50 MiB ಒಳಗೆ ಉಳಿಯಬಹುದು. ಹಂಚಿಕೆ ಮುನ್ನ ಇನ್‌ಲೈನ್ ಉದ್ದ ಮತ್ತು ಡಿಕೋಡ್-ಗಾತ್ರದ ಅಂದಾಜುಗಳನ್ನು ಪರಿಶೀಲಿಸಲಾಗುತ್ತದೆ. ಪ್ರಾಥಮಿಕ ದೂರದ URL ಮತ್ತು ಪ್ರತಿಯೊಂದು ಪುನರ್‌ನಿರ್ದೇಶನದಲ್ಲಿ HTTPS ಅಗತ್ಯವಿದೆ, ಈಗಾಗಲೇ ಇರುವ ಸಾರ್ವಜನಿಕ-ಮಾತ್ರದ ಔಟ್‌ಬೌಂಡ್ ಗಾರ್ಡ್ ಅನ್ನು DNS ಪಿನ್ನಿಂಗ್ ಬಳಸುತ್ತದೆ. ನಂತರ ಬೈಟ್ಗಳು ಖಚಿತವಾದ ಆಂತರಿಕ `POST /api/modality-bridge/video/extract` ಬ್ರೋಕರ್ ಗಡಿಯನ್ನು ದಾಟುತ್ತವೆ. ಆ ಮಾರ್ಗವು `LOCAL_ONLY` ಮತ್ತು `SPAWN_CAPABLE` ಎರಡೂ ಆಗಿದ್ದು, ಪ್ರತಿ-ಪ್ರಕ್ರಿಯೆಯ ಪ್ರಮಾಣೀಕೃತ, ವಿಶ್ವಾಸಾರ್ಹ-ಲೂಬ್ಯಾಕ್ ವಿನಂತಿಯನ್ನು ಮಾತ್ರ ಒಪ್ಪಿಸುತ್ತದೆ, ಮತ್ತು URL, ಫೈಲ್ ವ್ಯವಸ್ಥೆಯ ಮಾರ್ಗ, ಕಾರ್ಯನಿರ್ವಹಣೀಯ ಅಥವಾ ಆರ್ಜುಮೆಂಟ್ ಪಟ್ಟಿಯನ್ನು ಎಂದಿಗೂ ಒಪ್ಪುವುದಿಲ್ಲ. API ಶರೀರ-ಗಾತ್ರದ ಪೈಪ್‌ಲೈನ್ ಮತ್ತು ಹ್ಯಾಂಡ್ಲರ್‌ನ ಹಂತ ಹಂತದ ಶರೀರ ಓದುಗರವು ಸ್ವಾಯತ್ತವಾಗಿ 50 MiB ಬ್ರೋಕರ್ ಇನ್ಪುಟ್ ಗಡಿಯನ್ನು ಜಾರಿಗೊಳಿಸುತ್ತವೆ. ಇದರ ಗಡಿತಾಲಿಕೆಯಲ್ಲಿ ಒಂದೇ ಸಮಯದಲ್ಲಿ ಒಂದು ನಿರ್ವಹಣೆ ನಡೆಯುತ್ತದೆ, ನಾಲ್ಕು ಬಾಕಿ ಕೆಲಸಗಳನ್ನು ಅನುಮತಿಸುತ್ತದೆ, ಮತ್ತು ಬಾಕಿ ಇನ್ಪುಟ್ ಅನ್ನು 100 MiB ಗೆ ಗಡಿಬಿಡಿಸುತ್ತದೆ.

ಬ್ರೋಕರ್ ಒಳಗೆ, `ffprobe` ಖಾಸಗಿ ಸ್ಥಳೀಯ ಫೈಲ್ ಅನ್ನು ಓದುತ್ತದೆ; ಸ್ಥಿರ ರೂಪವನ್ನು ಅನುಮತಿಸುವ ಪಟ್ಟಿಯಲ್ಲಿ ಪ್ಲೇಲಿಸ್ಟ್ ಮತ್ತು ಮ್ಯಾನಿಫೆಸ್ಟ್ ರೂಪಗಳನ್ನು ಹೊರತುಪಡಿಸಲಾಗಿದೆ. ಅನುಮತಿತ MOV-ಕುಟುಂಬದ ಕಂಟೈನರ್‌ಗಳಿಗೆ, ಹೊರಗಿನ MOV ಡೇಟಾ ಉಲ್ಲೇಖಗಳು ಡೀಫಾಲ್ಟ್‌ನಲ್ಲಿ ನಿರ್ಬಂಧಿತವಾಗಿವೆ, ಮತ್ತು ಸ್ಥಿರ ಆದೇಶವು ಅವುಗಳಿಗೆ ಸೇರಲು ಆಯ್ಕೆ ಮಾಡುತ್ತಿಲ್ಲ. `ffprobe` ಮತ್ತು `ffmpeg` ಎರಡೂ `file`-ಮಾತ್ರದ ಪ್ರೋಟೋಕಾಲ್ ವೈಟ್‌ಲಿಸ್ಟ್, ಒಂದು ಥ್ರೆಡ್, ಸ್ಥಿರ ಆರ್ಜುಮೆಂಟ್ ಅರೆಗಳು, ಶೆಲ್ ಇಲ್ಲ, ಮತ್ತು `PATH` ನಿಂದ ಪರಿಹಾರಗೊಂಡ ಕಾರ್ಯನಿರ್ವಹಣೀಯಗಳನ್ನು ಬಳಸುತ್ತವೆ. ಅಟಾಚ್ಡ್-ಪಿಕ್ಚರ್ ಕವರ ಸ್ಟ್ರೀಮ್‌ಗಳನ್ನು ಆಡಲು ಸಾಧ್ಯವಿಲ್ಲ. ಎಲ್ಲಾ ಆಡಲು ಸಾಧ್ಯವಾದ ಸ್ಟ್ರೀಮ್‌ಗಳು ಗಡಿಗಳನ್ನು ಪೂರೈಸಬೇಕು, ಮತ್ತು ನಿರ್ಧಾರಾತ್ಮಕವಾಗಿ ಕಡಿಮೆ-ಅಂಕದ ಬಾಕಿ ಮೇಲೆ ಸ್ಪಷ್ಟ ಡೀಫಾಲ್ಟ್ ಸ್ಟ್ರೀಮ್ ಅನ್ನು ಆದ್ಯತೆಯೊಂದಿಗೆ ಬಳಸಲಾಗುತ್ತದೆ. ವಿಡಿಯೋಗಳು 600 ಸೆಕೆಂಡುಗಳು, 8,192 ಪಿಕ್ಸೆಲ್ ಪ್ರತಿ ಆಯಾಮ, ಮತ್ತು 33,554,432 ಮೂಲ ಪಿಕ್ಸೆಲ್‌ಗಳಿಗೆ ಮಿತಿಯಾಗಿವೆ. FFmpeg 1–16 ಮಧ್ಯದ JPEG ಫ್ರೇಮ್‌ಗಳನ್ನು ಮಾದರೀಕರಿಸುತ್ತದೆ, ದೀರ್ಘ ಅಂಚನ್ನು ಹೆಚ್ಚು ಹೆಚ್ಚು 1,024 ಪಿಕ್ಸೆಲ್‌ಗಳಿಗೆ ಕಡಿಮೆ ಮಾಡುತ್ತದೆ, ಸಣ್ಣ ಇನ್ಪುಟ್‌ಗಳನ್ನು ಅಪ್‌ಸ್ಕೇಲ್ ಮಾಡದೆ, ಮತ್ತು URL ಅನ್ನು ಎಂದಿಗೂ ಸ್ವೀಕರಿಸುವುದಿಲ್ಲ. ಮಾದರೀಕರಣವು ಡೀಫಾಲ್ಟ್‌ನಲ್ಲಿ `uniform` ಆಗಿದೆ. ಆಯ್ಕೆಯ `scene_aware` ಮತ್ತು ಪ್ರಯೋಗಾತ್ಮಕ `segment_aware` ನೀತಿಗಳು ಈಗಾಗಲೇ ಪರಿಶೀಲಿತ ಸ್ಥಳೀಯ ಸ್ಟ್ರೀಮ್‌ನಲ್ಲಿ ಒಂದು ಹೆಚ್ಚುವರಿ ಸ್ಥಿರ FFmpeg ಪಾಸ್ ಅನ್ನು ನಿರ್ವಹಿಸುತ್ತವೆ, ಗಡಿತ `showinfo` ದೃಶ್ಯ ಟೈಮ್‌ಸ್ಟ್ಯಾಂಪ್‌ಗಳನ್ನು ಆಯ್ಕೆ ಮಾಡುತ್ತವೆ, ಮತ್ತು ಡಿಟೆಕ್ಟರ್ ವಿಫಲವಾದಾಗ, ಟೈಮ್‌ಔಟ್, ಅಸಾಮಾನ್ಯ ಔಟ್‌ಪುಟ್, ಅಥವಾ ಖಾಲಿ ಅಭ್ಯರ್ಥಿ ಸೆಟ್‌ಗಳಿಗೆ ನಿರ್ಧಾರಾತ್ಮಕವಾಗಿ ಅದೇ ಸಮಾನ ಮಧ್ಯದ ಬಾಕಿಯ ಮೇಲೆ ಹಿಂತಿರುಗುತ್ತವೆ. ಸೆಗ್ಮೆಂಟ್-ಅವೇರ್ ಮೋಡ್ ಪರಿಶೀಲಿತ ದೃಶ್ಯ ಅಂತರಗಳಿಗೆ ಅನುಪಾತವಾಗಿ ಮಧ್ಯದ ಮಾದರಿಗಳನ್ನು ಹಂಚಿಸುತ್ತದೆ; ಸೆಗ್ಮೆಂಟ್-ಅವೇರ್ ಸಾಕ್ಷ್ಯ ಮತ್ತು ಹಿಂತಿರುಗುವ ವರ್ತನೆ ಕೆಳಗೆ ವಿವರಿಸಲಾಗಿದೆ. ಕಠಿಣ 16-ಫ್ರೇಮ್ ಗಡಿ ಪ್ರತಿ ನೀತಿಯಲ್ಲಿ ಆಯ್ಕೆ ಮಾಡಿದ ನಂತರ ಅನ್ವಯಿಸಲಾಗುತ್ತದೆ. ದೃಶ್ಯ-ಅವೇರ್ ವಿನಂತಿಯು ಕೇವಲ ಒಂದು-ಫ್ರೇಮ್ ಬಜೆಟ್ ಹೊಂದಿದಾಗ, ಇದು ಸಕ್ರಿಯ ಸಂಪೂರ್ಣ-ವಿಡಿಯೋ ಅಥವಾ ಫೋಕಸ್ ವಿಂಡೋನಿನ ಸಮಾನ ಮಧ್ಯದ ಬಾಕಿಯನ್ನು ಬಳಸುತ್ತದೆ ಮತ್ತು `policyEffective: uniform` ಅನ್ನು ವರದಿ ಮಾಡುತ್ತದೆ: ಒಬ್ಬ ಆಯ್ಕೆ ಮಾಡಿದ ದೃಶ್ಯ ಫ್ರೇಮ್ ಕಾಲಿಕ ಅಂತ್ಯಗಳನ್ನು ಉಳಿಸಲು ಸಾಧ್ಯವಿಲ್ಲ. ಕರೆ ಮಾಡಿದವರು ಆಯ್ಕೆಯಂತೆ ನಿರ್ದಿಷ್ಟ ಫೋಕಸ್ ವಿಂಡೋವನ್ನು ಒದಗಿಸಬಹುದು (`start`/`end` ಸೆಕೆಂಡುಗಳು); ಗಡಿಗಳು ಮಾಧ್ಯಮಾವಧಿಗೆ ಕ್ಲ್ಯಾಂಪ್ ಮಾಡಲಾಗುತ್ತದೆ, ಹಿಂತಿರುಗಿದ ಅಥವಾ ನಿರ್ದಿಷ್ಟವಲ್ಲದ ವಿಂಡೋಗಳನ್ನು ನಿರಾಕರಿಸಲಾಗುತ್ತದೆ, ಮತ್ತು ಎಲ್ಲಾ ಮಾದರೀಕರಣ ನೀತಿಗಳನ್ನು ಮಾತ್ರ ಸಾಮಾನ್ಯೀಕೃತ ಅಂತರದ ಒಳಗೆ ನಿರ್ವಹಿಸಲಾಗುತ್ತದೆ. ಫಲಿತಾಂಶ ವಿಂಡೋವನ್ನು ಮಾದರೀಕರಣ ಮೆಟಾಡೇಟಾದಲ್ಲಿ ಮತ್ತು ಅಪ್ರಾಮಾಣಿಕ ವಿವರಣಾ ಪ್ರೀಫಿಕ್ಸ್‌ನಲ್ಲಿ ಸೇರಿಸಲಾಗುತ್ತದೆ, ಆದ್ದರಿಂದ ಹಿಂಬಾಲಿಸುವ ಮಾದರಿಗಳು ಸಂಪೂರ್ಣ ಟೈಮ್‌ಲೈನ್‌ನಿಂದ ಫೋಕಸ್ ಮಾಡಿದ ಉಲ್ಲೇಖವನ್ನು ವಿಭಜಿತಗೊಳಿಸಬಹುದು.

ಅರ್ಥಶಾಸ್ತ್ರ ಶೀರ್ಷಿಕೆ ಫೋಕಸ್ ಒಂದು ಪ್ರತ್ಯೇಕ, ಸ್ಪಷ್ಟ ಸೆಟಿಂಗ್ ಆಗಿದೆ. ಡೀಫಾಲ್ಟ್ `full` ವಿಶ್ಲೇಷಣಾ ಮೋಡ್ ಈಗಾಗಲೇ ಇರುವ ಫ್ರೇಮ್ ಪ್ರಾಂಪ್ಟ್ ಅನ್ನು ಉಳಿಸುತ್ತದೆ ಮತ್ತು ಶೀರ್ಷಿಕೆ ಮಾದರಿಯೊಂದಿಗೆ ವಿನಂತಿ ಪಠ್ಯವನ್ನು ಎಂದಿಗೂ ಮುಂದುವರಿಸುತ್ತಿಲ್ಲ. `focused` ಮೋಡ್‌ನಲ್ಲಿ, ಬ್ರಿಡ್ಜ್ ಒಂದೇ ಚಾಟ್ ಅಥವಾ ಪ್ರತಿಕ್ರಿಯೆ ಕಂಟೈನರ್‌ನಿಂದ ಇತ್ತೀಚಿನ ಖಾಲಿ ಅಲ್ಲದ ಬಳಕೆದಾರ-ರಚಿತ `text`/`input_text` ಅನ್ನು ಮಾತ್ರ ಓದುತ್ತದೆ, ಇದನ್ನು NFC ಗೆ ಸಾಮಾನ್ಯೀಕರಿಸುತ್ತದೆ, ನಿಯಂತ್ರಣ ಅಕ್ಷರಗಳನ್ನು ಮತ್ತು ಖಾಲಿ ಸ್ಥಳವನ್ನು ಕುಗ್ಗಿಸುತ್ತದೆ, ಮತ್ತು ಇದನ್ನು 500 Unicode ಕೋಡ್ ಪಾಯಿಂಟ್‌ಗಳಿಗೆ ಮಿತಿಯಲ್ಲಿಡುತ್ತದೆ. ಖಾಲಿ ಫಲಿತಾಂಶವು ಖಚಿತ `full` ಪ್ರಾಂಪ್ಟ್ ಗೆ ಹಿಂತಿರುಗುತ್ತದೆ. ಬಳಸಬಹುದಾದ ಸೂಚನೆ JSON ನಲ್ಲಿ ಸಮರ್ಪಿತ ಅಪ್ರಾಮಾಣಿಕ-ಬಳಕೆದಾರ-ಸಂದರ್ಭ ಬ್ಲಾಕ್‌ನಲ್ಲಿ ಸರಣೀಬದ್ಧಗೊಳ್ಳುತ್ತದೆ ಮತ್ತು observable ವಿವರಗಳನ್ನು ಮಾತ್ರ ಆದ್ಯತೆಯಲ್ಲಿಡಬಹುದು; ಇದು ಮಾಧ್ಯಮದಲ್ಲಿ ದೃಶ್ಯ ಅಥವಾ ಶ್ರವಣೀಯವಾಗಿ ಕಾಣುವ ಸೂಚನೆಗಳನ್ನು ಅನುಸರಿಸಲು ಪ್ರತ್ಯೇಕ ಎಚ್ಚರಿಕೆಯನ್ನು ಮೀರಿಸಲು ಸಾಧ್ಯವಿಲ್ಲ. ಪಠ್ಯ ಫೋಕಸ್ ಎಂದಿಗೂ `start`/`end` ಅನ್ನು ಊಹಿಸುವುದಿಲ್ಲ ಅಥವಾ ಕಾಲಿಕ ಮಾದರಿಕರ್ತನೆಯನ್ನು ಬದಲಾಯಿಸುವುದಿಲ್ಲ.

#### FU-07 ರಚನಾತ್ಮಕ ಸೆಗ್ಮೆಂಟ್ ಸಾಕ್ಷ್ಯ

`segment_aware` ಈಗಾಗಲೇ ಪರಿಶೀಲಿತ ಸ್ಥಳೀಯ ವಿಡಿಯೋ ಸ್ಟ್ರೀಮ್‌ನಲ್ಲಿ ಒಂದು ಗಡಿತ ಪೂರ್ವ-ವಿಶ್ಲೇಷಣಾ ಪಾಸ್ ಅನ್ನು ಬಳಸುತ್ತದೆ. ಸ್ಥಿರ ಫಿಲ್ಟರ್ ಸರಣಿ ಮೊದಲಿಗೆ ಹೆಚ್ಚು ಹೆಚ್ಚು 320 ಪಿಕ್ಸೆಲ್ ಅಗಲಕ್ಕೆ ಪ್ರಮಾಣೀಕರಿಸುತ್ತದೆ, ದೃಶ್ಯ ಬದಲಾವಣೆಗಳನ್ನು ಮತ್ತು ಹಿಮ್ಮೆಟ್ಟಿದ ಅಂತರಗಳನ್ನು ಗುರುತಿಸುತ್ತದೆ, ನಂತರ ಮಂಜು, ಸರಾಸರಿ ಲ್ಯೂಮಾ, ಮತ್ತು ಸ್ಥಳೀಯ/ಕಾಲಿಕ ಮಾಹಿತಿಗಾಗಿ 1 ಫ್ರೇಮ್ ಪ್ರತಿ ಸೆಕೆಂಡಿಗೆ ಮಾದರೀಕರಿಸುತ್ತದೆ. ಪಾಸ್ 600 ರಚನಾತ್ಮಕ ಮಾದರಿಗಳಿಗೆ, ಒಂದು FFmpeg/ಫಿಲ್ಟರ್ ಥ್ರೆಡ್, ಅದೇ `file`-ಮಾತ್ರದ ಪ್ರೋಟೋಕಾಲ್ ಮತ್ತು ಕಂಟೈನರ್ ಅನುಮತಿಸುವ ಪಟ್ಟಿಗಳಿಗೆ, 1 MiB ಪ್ರಕ್ರಿಯೆ-ಔಟ್‌ಪುಟ್ ಗಡಿಗೆ, ಮತ್ತು ಬ್ರೋಕರ್‌ನ ಹಂಚಿದ ಅಬಾರ್ಟ್/ಡೆಡ್‌ಲೈನ್ ಒಳಗೆ ಹೆಚ್ಚು ಹೆಚ್ಚು 30 ಸೆಕೆಂಡುಗಳಿಗೆ ಮಿತಿಯಲ್ಲಿದೆ. ಇದು ವಿನಂತಿಯಿಂದ ಆದೇಶ, ಫಿಲ್ಟರ್, ಮಾರ್ಗ, ಅಥವಾ URL ಅನ್ನು ಎಂದಿಗೂ ಒಪ್ಪುವುದಿಲ್ಲ.

ಸಂರಚನಾ ಮೌಲ್ಯಗಳು ನಿರ್ಧಾರಾತ್ಮಕ ಮಾದರಿ ಸಾಕ್ಷ್ಯವಾಗಿವೆ, ಅರ್ಥಾತ್ಮಕ ವೀಡಿಯೋ ಅರ್ಥಮಾಡಿಕೊಳ್ಳುವಿಕೆ ಅಲ್ಲ. ಇವು ವಿಷಯಗಳು, ಕ್ರಿಯೆಗಳು, ಶೀರ್ಷಿಕೆಗಳು, ಭಾಷಣ ಅಥವಾ ಬಳಕೆದಾರ ಉದ್ದೇಶವನ್ನು ಊಹಿಸುವುದಿಲ್ಲ. ದೃಶ್ಯ ಮತ್ತು ಸ್ಥಗಿತ ಗಡಿಗಳು ವಿಭಾಗಗಳನ್ನು ರೂಪಿಸುತ್ತವೆ; ಸ್ಥಗಿತ ವ್ಯಾಪ್ತಿ, ಮಸುಕಾಗು, ಬೆಳಕು, ಸ್ಥಳೀಯ ವಿವರ ಮತ್ತು ಕಾಲಿಕ ಬದಲಾವಣೆ ಮಾತ್ರ ಇತ್ತೀಚಿನ 1–16 ಫ್ರೇಮ್ ಬಜೆಟ್ ಹೇಗೆ ಹಂಚಿಕೊಳ್ಳಲಾಗಿದೆ ಎಂಬುದನ್ನು ಪ್ರಭಾವಿತ ಮಾಡುತ್ತವೆ. ಸಂಪೂರ್ಣವಾಗಿ ಸ್ಥಗಿತಗೊಂಡ ವಿಭಾಗವು ಒಂದು ಫ್ರೇಮ್‌ನಲ್ಲಿ ಮಿತಿಯಲ್ಲಿದೆ, ಆದರೆ ಸ್ಥಗಿತಗೊಂಡಿಲ್ಲದ ವಿಭಾಗಗಳು ಉಳಿದ ಬಜೆಟ್‌ಗಾಗಿ ಸ್ಪರ್ಧಿಸುತ್ತವೆ. ಗಡಿಗಳು ಫ್ರೇಮ್‌ಗಳನ್ನು ಮೀರಿಸಿದಾಗ, ಸಮಾನ ಕಾಲರೇಖೆ ವ್ಯಾಪ್ತಿ ಉಳಿಯುತ್ತದೆ, ಆದ್ದರಿಂದ ವೇಗವಾದ ಪ್ರಾರಂಭದ ಕಟ್‌ಗಳು ದೀರ್ಘ ಹಿಂಬಾಲಿಸುವ ವಿಭಾಗವನ್ನು ಮರೆಮಾಡಲು ಸಾಧ್ಯವಿಲ್ಲ. ಸ್ಥಗಿತ ಗಡಿಯ 1-ಸೆಕೆಂಡು ವಿಶ್ಲೇಷಣಾ ನಿರ್ಧಾರದಲ್ಲಿ ದೃಶ್ಯ ಗಡಿಗಳನ್ನು ಒಗ್ಗೂಡಿಸಲಾಗುತ್ತದೆ.

ಕಡಿವಾಣದ ಕೊರತೆಯು, ತಪ್ಪಾದ/ಖಾಲಿ ಸಾಕ್ಷ್ಯ, ಡಿಟೆಕ್ಟರ್ ದೋಷ, ಅಥವಾ ಬೌಂಡೆಡ್ ಪೂರ್ವ-ವಿಶ್ಲೇಷಣಾ ಟೈಮ್‌ಔಟ್ ಖಚಿತ ಸಮಾನ ಮಧ್ಯದ ನೀತಿಗೆ ವಿಫಲವಾಗುತ್ತದೆ. ಕರೆ ಮಾಡುವವರು ಬಾರ್ಟ್ ಅಥವಾ ಬ್ರೋಕರ್ ಡೆಡ್‌ಲೈನ್ ವಿಫಲವಾಗುವುದಿಲ್ಲ: ಇದು ಹಾರುವ ಉಪಪ್ರಕ್ರಿಯೆಯನ್ನು ಕೊನೆಗೊಳಿಸುತ್ತದೆ, ನಂತರದ ಫ್ರೇಮ್ ನಿರ್ವಹಣೆಯನ್ನು ತಡೆಯುತ್ತದೆ, ಮತ್ತು ಖಾಸಗಿ ತಾತ್ಕಾಲಿಕ ಮರವನ್ನು `finally` ನಲ್ಲಿ ತೆಗೆದುಹಾಕುತ್ತದೆ.

`scripts/perf/video-bridge-fu07-eval.ts` ಪೋಸ್ಟ್-ಡಿಡುಪ್ ಶೀರ್ಷಿಕೆ-ಕೋಲ್ ಉಳಿತಾಯ, ಘನ-ಚಲನೆ ಬಜೆಟ್ ಹಂಚಿಕೆ, ಮಸುಕಾಗು/ಬೆಳಕು/SI-TI ಸಾಕ್ಷ್ಯ, ದೀರ್ಘ ತಲೆಯೊಂದಿಗೆ ವೇಗವಾದ ಕಟ್‌ಗಳು ಮತ್ತು ಹಂತ ಹೀನಾಯ ತಪ್ಪು ಸಕಾರಾತ್ಮಕಗಳನ್ನು ಉತ್ಪಾದಿಸುತ್ತದೆ. ಇದು ಪೂರ್ವ-ವಿಶ್ಲೇಷಣಾ ಗೋಡೆ ಸಮಯವನ್ನು ದಾಖಲಿಸುತ್ತದೆ ಮತ್ತು `/usr/bin/time` ಲಭ್ಯವಿರುವಾಗ, ಮಕ್ಕಳ CPU ಮತ್ತು ಶ್ರೇಷ್ಟ RSS ಅನ್ನು ದಾಖಲಿಸುತ್ತದೆ. ಇದರ ಗುಣಮಟ್ಟದ ಪರಿಶೀಲನೆಗಳು ಶ್ರೇಣೀಬದ್ಧ oracle‌ಗಳಾಗಿವೆ ಮಾತ್ರ. ವಾಸ್ತವ ಶೀರ್ಷಿಕೆ-ಮಾದರಿ ಗುಣಮಟ್ಟವು `HOLD` ನಲ್ಲಿ ಉಳಿಯುತ್ತದೆ ಏಕೆಂದರೆ ಈ ಹಾರ್ನೆಸ್‌ಗೆ ಯಾವುದೇ ಅಧಿಕಾರಿತ ಅಂತಿಮ ಬಿಂದುವಿಲ್ಲ ಅಥವಾ ಸ್ಥಗಿತ ನ್ಯಾಯಾಧೀಶವಿಲ್ಲ. ಹಣಕಾಸಿನ ಉಳಿತಾಯವು `HOLD` ನಲ್ಲಿ ಉಳಿಯುತ್ತದೆ, ಏಕೆಂದರೆ `--caption-cost-per-call-usd` ಸ್ಪಷ್ಟ ಸಕಾರಾತ್ಮಕ ಪ್ರತಿ-ಕೋಲ್ ಅಂದಾಜು ಒದಗಿಸುತ್ತಿಲ್ಲ; ಸ್ಕ್ರಿಪ್ಟ್ ಯಾವಾಗಲೂ ಫಲಿತಾಂಶವನ್ನು ತಯಾರಿಸುತ್ತಿಲ್ಲ.

ಪ್ರತಿ ಫ್ರೇಮ್ 4 MiB ಗೆ ಮಿತಿಯಲ್ಲಿದೆ, ಎಲ್ಲಾ ಕಚ್ಚಾ ಫ್ರೇಮ್‌ಗಳನ್ನು ಒಟ್ಟಾಗಿ 23 MiB ಗೆ, ಮತ್ತು ಸರಣೀಬದ್ಧ ಬ್ರೋಕರ್ ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು 32 MiB ಗೆ ಮಿತಿಯಲ್ಲಿದೆ. ಖಾಸಗಿ ತಾತ್ಕಾಲಿಕ ಡೈರೆಕ್ಟರಿ `finally` ನಲ್ಲಿ ತೆಗೆದುಹಾಕುತ್ತದೆ. OmniRoute FFmpeg ಅನ್ನು ಒಟ್ಟುಗೂಡಿಸುವುದಿಲ್ಲ ಮತ್ತು ಕಸ್ಟಮ್ ಕಾರ್ಯನಿರ್ವಹಣಾ ಪಥವನ್ನು ಒಪ್ಪುವುದಿಲ್ಲ. ಶೀರ್ಷಿಕೆ ಹಾಕುವ ಮೊದಲು, ಬ್ರಿಡ್ಜ್ ಸಂರಕ್ಷಣಾತ್ಮಕ ದೃಶ್ಯ ಡಿಡುಪ್ಲಿಕೇಶನ್ ಪಾಸ್ ಅನ್ನು ಅನ್ವಯಿಸುತ್ತದೆ: ಪ್ರತಿ JPEG ಅನ್ನು 16×16 ಗ್ರೇಸ್ಕೇಲ್ ಬಫರ್ ಗೆ ಕಡಿಮೆ ಮಾಡಲಾಗುತ್ತದೆ ಮತ್ತು ಇದು ಕೇವಲ ಕೊನೆಯ ಫ್ರೇಮ್‌ಗಾಗಿ ಹೋಲಿಸಲಾಗುತ್ತದೆ. ಒಂದು ಫ್ರೇಮ್‌ಗಿಂತ ಹೆಚ್ಚು ಶೀರ್ಷಿಕೆ ಬಜೆಟ್ ಕೇಳಿದಾಗ, ನಿರ್ವಹಣೆಯು ಬಜೆಟ್‌ಗಿಂತ ಎರಡು ಪಟ್ಟು ಹೆಚ್ಚು ಬೌಂಡೆಡ್ ಅಭ್ಯರ್ಥಿ ತೋಳವನ್ನು ಒದಗಿಸುತ್ತದೆ ಮತ್ತು 16 ಫ್ರೇಮ್‌ಗಿಂತ ಹೆಚ್ಚು ಎಂದಾದರೂ ಇಲ್ಲ. ಕೇಳಿದ ಮಿತಿಯನ್ನು ಡಿಡುಪ್ಲಿಕೇಶನ್ ನಂತರ ಮಾತ್ರ ಅನ್ವಯಿಸಲಾಗುತ್ತದೆ, ಮೊದಲ ಮತ್ತು ಅಂತಿಮ ಆಯ್ಕೆಯಾದ ಅಭ್ಯರ್ಥಿಗಳನ್ನು ಅಂತಿಮ ತೂಕದಲ್ಲಿ ಉಳಿಸಲಾಗುತ್ತದೆ, ಬಜೆಟ್ ಕನಿಷ್ಠ ಎರಡು ಇದ್ದಾಗ. ಆವೃತ್ತಿಯ `grayscale-16x16-mean-cells-v2` ನೀತಿ ಲೂಮಾ ಡೆಲ್ಟಾ ಮತ್ತು ನಾರ್ಮಲೈಜ್ಡ್ ಡೆಲ್ಟಾ ಕನಿಷ್ಠ 0.05 ಇರುವ ಥಂಬ್ನೈಲ್ ಸೆಲ್‌ಗಳ ಅನುಪಾತದ ದೊಡ್ಡದಾದದನ್ನು ಬಳಸುತ್ತದೆ. ನಕಲಿ ತೀವ್ರತೆ ನಿರ್ಧಾರವು ನಿರೀಕ್ಷಿತವಾಗಿರುವುದರಿಂದ 0.04 ಎಂಬ ಸ್ಥಿರ ಸಂಖ್ಯೆಯಾಗಿದೆ, ಇದು ಕಾರ್ಯನಿರ್ವಹಣಾ ಸೆಟಿಂಗ್ ಎಂದು ಬಹಿರಂಗಪಡಿಸಲಾಗುವುದಿಲ್ಲ. ಈ ದ್ವಿತೀಯ ಉನ್ನತ-ಕಾಂಟ್ರಾಸ್ಟ್ ಸಂಕೇತವು ಸಣ್ಣ ಚಲನೆ ಮತ್ತು ದೃಶ್ಯ-ಪಠ್ಯ ಬದಲಾವಣೆಗಳನ್ನು ಉಳಿಸುತ್ತದೆ, ಏಕೆಂದರೆ ಕೇವಲ ಅರ್ಥಮಾಡಿಕೊಳ್ಳುವ ಹೋಲಣೆ ಇದನ್ನು ಮರೆಮಾಡಬಹುದು. ಹೋಲಿಸುವ ಅಥವಾ ಡಿಕೋಡರ್ ದೋಷಗಳು ವಿಫಲವಾಗುತ್ತವೆ ಮತ್ತು ವ್ಯಾಪ್ತಿಯನ್ನು ಉಳಿಸುತ್ತವೆ. ಔಟ್‌ಪುಟ್ ಮೆಟಾಡೇಟಾ ಆಯ್ಕೆ ಮಾಡಿದ ಅಭ್ಯರ್ಥಿಗಳನ್ನು, ಯಶಸ್ವಿಯಾಗಿ ಬಳಸಿದ ಫ್ರೇಮ್‌ಗಳನ್ನು ಮತ್ತು ದೃಶ್ಯ ನಕಲುಗಳನ್ನು ಬಿಟ್ಟುಹೋಗುತ್ತದೆ.

ಸ್ಪಷ್ಟವಾಗಿ ಗುರುತಿಸಲಾದ ವೀಡಿಯೋ ಭಾಗವು ಟೈಮ್‌ಸ್ಟ್ಯಾಂಪ್ಡ್ ಸಂಪರ್ಕ ಶೀಟ್ ಅನ್ನು ಕೇಳಬಹುದು. ಬ್ರಿಡ್ಜ್ ಗರಿಷ್ಠ 4-ಕೋಷ್ಟಕ, 16-ಫ್ರೇಮ್ JPEG ಗ್ರಿಡ್ ಅನ್ನು ನಿರ್ಮಿಸುತ್ತದೆ. ಪ್ರತಿ 512-ಪಿಕ್ಸೆಲ್ ಸೆಲ್ ತನ್ನ ಮೂಲ ಟೈಮ್‌ಸ್ಟ್ಯಾಂಪ್ ಅನ್ನು ಉನ್ನತ-ಕಾಂಟ್ರಾಸ್ಟ್ ಕೆಳಗಿನ ಬ್ಯಾಂಡ್‌ನಲ್ಲಿ ಬೆಂಕಿ ಹಾಕುತ್ತದೆ, ಮತ್ತು ಅದೇ ಟೈಮ್‌ಸ್ಟ್ಯಾಂಪ್‌ಗಳನ್ನು ಹೀಗೆ ಬಳಸುವ ಸಂಬಂಧ ಮತ್ತು ಪರಿಶೀಲನೆಗಾಗಿ ಪಠ್ಯ ಮೆಟಾಡೇಟಾದಲ್ಲಿ ಉಳಿಯುತ್ತವೆ. ಸಂಪೂರ್ಣ JPEG 32 MiB ಗೆ ಮಿತಿಯಲ್ಲಿದೆ. `sharp` ಗ್ರಿಡ್ ಅನ್ನು ಡಿಕೋಡ್ ಅಥವಾ ರಚಿಸಲು ಸಾಧ್ಯವಾಗದರೆ, ಬ್ರಿಡ್ಜ್ ವೈಯಕ್ತಿಕ JPEG ಫ್ರೇಮ್‌ಗಳಿಗೆ ಹಿಂತಿರುಗುತ್ತದೆ; ಕ್ಲೈಂಟ್ ಬಾರ್ಟ್ ಶೀಟ್ ಕಾರ್ಯಾಚರಣೆಯ ಮೂಲಕ ಇನ್ನೂ ಹರಡುತ್ತದೆ.

ಪ್ರೋಮೋಶನ್ ಸಾಕ್ಷ್ಯವು ಕೃತಕ ಸಂಯೋಜನೆಯ ಮೈಕ್ರೋಬೆಂಚ್‌ಗಿಂತ ಉಲ್ಲೇಖಿತವಾಗಿ ಪ್ರತ್ಯೇಕವಾಗಿದೆ. `scripts/perf/video-bridge-contact-sheet-eval.ts` ವಾಸ್ತವ OpenAI-ಸಂಗತ ದೃಶ್ಯ ಮಾದರಿಗಳಿಗಾಗಿ schema-versioned A/B ಹಾರ್ನೆಸ್ ಅನ್ನು ವ್ಯಾಖ್ಯಾನಿಸುತ್ತದೆ. ಇದು ಒದಗಿಸುವವರ ವರದಿಯ ಟೋಕನ್‌ಗಳನ್ನು, ಅಂತ್ಯ-ತಂತು ಗೋಡೆ ವಿಳಂಬವನ್ನು (ಶೀಟ್ ಸಂಯೋಜನೆಯು ಒಳಗೊಂಡಂತೆ), ಮಾದರಿ-ಕೋಲ್ ಸಂಖ್ಯೆಯನ್ನು ಮತ್ತು ಮ್ಯಾನಿಫೆಸ್ಟ್-ನಿರ್ಧಾರಿತ ವಾಸ್ತವವನ್ನು ಅಳೆಯುತ್ತದೆ. ಕಚ್ಚಾ ಮಾದರಿ ಪ್ರತಿಕ್ರಿಯೆಗಳು ವರದಿಗೆ ಬರೆಯಲಾಗುವುದಿಲ್ಲ; ಕೇವಲ SHA-256 ಡಿಜೆಸ್ಟ್‌ಗಳು ಮತ್ತು ಹೊಂದಾಣಿಕೆಯ ವಾಸ್ತವ IDಗಳನ್ನು ಮಾತ್ರ ಉಳಿಸಲಾಗುತ್ತದೆ. ಹಾರ್ನೆಸ್ ಯಾವುದೇ ನೆಟ್ವರ್ಕ್ ಅಥವಾ ಪಾವತಿತ ಮಾದರಿ ಕರೆ ಮಾಡುತ್ತಿಲ್ಲ, ಏಕೆಂದರೆ `--execute-real` ಅನ್ನು ಒದಗಿಸಲಾಗುತ್ತದೆ ಮತ್ತು `--model`, `OMNIROUTE_BASE_URL`, ಮತ್ತು `OMNIROUTE_API_KEY` ಅನ್ನು ಕಾನ್ಫಿಗರ್ ಮಾಡಲಾಗಿದೆ. ಆ ಸ್ಪಷ್ಟ ವಾಸ್ತವ ಓಡಾಟವಿಲ್ಲದೆ, ಇದರ ಯಂತ್ರ-ಊಹಿತ ತೀರ್ಪು `HOLD` ನಲ್ಲಿ ಉಳಿಯುತ್ತದೆ; ಕೃತಕ ಪೇಲೋಡ್/ಕೋಲ್-ಗಣನೆ ಮಾತ್ರ ಪ್ರೋಮೋಶನ್ ಸಾಕ್ಷ್ಯವಲ್ಲ.

ಬೇರೆ `scripts/perf/video-bridge-promotion-eval.ts` FU-07 ಅಥವಾ FU-09 ಗಮನಗಳನ್ನು ಬಳಸುತ್ತದೆ. ಪ್ರೋಮೋಶನ್ ಪ್ರವೇಶವು ಎಲ್ಲಾ ಎಂಟು ಕೃತಕ ದೃಶ್ಯ ಪರಿಕಲ್ಪನೆಗಳ ಪ್ರಕಾರಗಳನ್ನು ಮತ್ತು ಶುದ್ಧವಾದ ವಾಸ್ತವ ಕ್ಲಿಪ್ ಅನ್ನು, ಪ್ರತಿ ಪಾತ್ರ ಮತ್ತು ಪ್ರಕರಣಕ್ಕೆ ಕನಿಷ್ಠ ಮೂರು ಅಳೆಯಲ್ಪಟ್ಟ ಪುನರಾವೃತ್ತಗಳನ್ನು, ಎಲ್ಲಾ ಹತ್ತು ಘೋಷಿತ ಮೆಟ್ರಿಕ್‌ಗಳನ್ನು, ಸ್ಥಗಿತ ಮಾಧ್ಯಮ/ಪ್ರಾಂಪ್ಟ್/ನಿರೀಕ್ಷಿತ-ವಾಸ್ತವ/ಸೆಟಿಂಗ್‌ಗಳ ಡಿಜೆಸ್ಟ್‌ಗಳನ್ನು, ವಿಶಿಷ್ಟ ಗಮನ IDಗಳನ್ನು ಮತ್ತು ಪರಿಶೀಲಿತ ಬೀಜಿತ A/B ಕ್ರಮವನ್ನು ಅಗತ್ಯವಿದೆ. ಕಾರ್ಯಾಚರಣೆಯ ರಸೀದಿಯು ಕಾರ್ಪಸ್ ಡಿಜೆಸ್ಟ್, ಖಚಿತ ಅಭ್ಯರ್ಥಿ SHA ಮತ್ತು ಮಾದರಿ ಪರಿಷ್ಕರಣೆಗಳನ್ನು ಬಂಧಿಸುತ್ತದೆ. ಕೊರತೆಯಾದ ಅಥವಾ ಅಮಾನ್ಯ ಅಳೆಯುವಿಕೆಗಳು `HOLD` ನಲ್ಲಿ ಉಳಿಯುತ್ತವೆ, 30 ಸೆಕೆಂಡುಗಳ ಮೇಲಿನ CPU, 512 MiB ಕ್ಕಿಂತ ಹೆಚ್ಚು ಶ್ರೇಷ್ಟ RSS ಅಥವಾ 30 ಸೆಕೆಂಡುಗಳ ಮೇಲಿನ ಪೂರ್ವ-ವಿಶ್ಲೇಷಣೆಯನ್ನು ಒಳಗೊಂಡಂತೆ. ಇವು ಸಾಕ್ಷ್ಯ-ಪ್ರವೇಶ ಮಿತಿಗಳು, ಹೊಸ ಕಾರ್ಯನಿರ್ವಹಣಾ RSS enforcement ಖಾತರಿಯಲ್ಲ.

FU-07 ಕನಿಷ್ಠ 98% ಗುಣಮಟ್ಟದ ಉಳಿವನ್ನು ಮತ್ತು p95 ವಿಳಂಬವನ್ನು 1.2x ಮೂಲಕ್ಕಿಂತ ಹೆಚ್ಚು ಇರಬೇಕಾಗಿದೆ, ಅಥವಾ ಸಮಾನ ಶೀರ್ಷಿಕೆ ಕರೆಗಳಲ್ಲಿ 0.05 ಶ್ರೇಷ್ಟವಾದ ಪ್ರಕರಣ-ಸಮತೋಲನ ಅರ್ಥಮಾಡಿಕೊಳ್ಳುವಿಕೆ ಸುಧಾರಣೆ, ಅಥವಾ ಕನಿಷ್ಠ 10% ಕಡಿಮೆ ಶ್ರೇಷ್ಟ ಶೀರ್ಷಿಕೆ-ಕೋಲ್‌ಗಳನ್ನು ಅಗತ್ಯವಿದೆ. FU-09 ಕನಿಷ್ಠ 0.85 ಗುಣಮಟ್ಟ, 95% ಉಳಿವು, 20% p95 ವಿಳಂಬ ಕಡಿತ ಮತ್ತು 10% ಟೋಕನ್ ಕಡಿತವನ್ನು ಅಗತ್ಯವಿದೆ. ಪ್ರಮುಖ ವಾಸ್ತವ ನಷ್ಟ, ಇಂಜೆಕ್ಷನ್ ಅನುಕೂಲತೆ ಅಥವಾ ಕೊರತೆಯಾದ ಬಳಕೆ ಪ್ರೋಮೋಶನನ್ನು ತಡೆಯುತ್ತದೆ. ಒಂದು ಕಾರ್ಯಾಚರಣೆ ಏನನ್ನೂ ಪ್ರೋಮೋಟ್ ಮಾಡಲಾರದು: `--previous-report` ಒಂದೇ ನೀತಿ/ಮಾದರಿ ಪರಿಷ್ಕರಣೆ/ಅಭ್ಯರ್ಥಿ/ಕಾರ್ಪಸ್‌ನ ಎರಡು ವಿಭಿನ್ನ, ಪರಸ್ಪರ ಬಾಹ್ಯ, ಕ್ರಮಬದ್ಧವಾಗಿ ಅರ್ಹ ಕಾರ್ಯಾಚರಣೆಗಳನ್ನು ದೃಢೀಕರಿಸುತ್ತದೆ. ಮಾದರಿ ಪ್ರಯೋಗವು ಸಂಪರ್ಕ-ಶೀಟ್ ಪ್ರಯೋಗವನ್ನು ದೃಢೀಕರಿಸಲು ಸಾಧ್ಯವಿಲ್ಲ.

ಕಲೆಕ್ಟರ್‌ಗಳು ಪ್ರತಿಕ್ರಿಯೆಗಳನ್ನು ಮೆಮೊರಿಯಲ್ಲಿ ಅಂಕಿತಗೊಳಿಸಬೇಕು ಮತ್ತು `responseDigest` ಜೊತೆಗೆ ಮೆಟ್ರಿಕ್‌ಗಳು ಮತ್ತು ವೀಕ್ಷಣಾ ಬಾಂಧವ್ಯಗಳನ್ನು ಉಳಿಸಬೇಕು, ಪ್ರತಿಕ್ರಿಯೆ ಪಠ್ಯವನ್ನು ಎಂದಿಗೂ ಉಳಿಸಬಾರದು. ಗ್ರಾಹಕವು ಹಳೆಯ ಕಚ್ಚಾ ವೀಕ್ಷಣೆಗಳನ್ನು ಓದುತ್ತದೆ ಆದರೆ ಆ ಪಠ್ಯವನ್ನು ತನ್ನ ವರದಿಗಳಲ್ಲಿ ನಕಲಿಸುವುದಿಲ್ಲ. ಪ್ರತಿಯೊಂದು ವೀಕ್ಷಣೆಗೆ `responseDigest` ಅಥವಾ `rawResponseText` ನಿಖರವಾಗಿ ಒಂದೇ ಒಪ್ಪಿಗೆಯಾಗಿದೆ. ಆವೃತ್ತಿಯ ಅನುಮತಿತ ಪಟ್ಟಿಯು ಶೂನ್ಯವಾಗಿರುತ್ತದೆ ಮತ್ತು ಬದಲಾಯಿಸಲಾಗದ `hold` ಡೀಫಾಲ್ಟ್ ಅನ್ನು ಹೊಂದಿದೆ. ಅರ್ಹ ಎಂಟ್ರಿಯು ಅದರ ಸಾಕ್ಷ್ಯ ಉಲ್ಲೇಖ, ನೀತಿ, ಮಾದರಿ ಪರಿಷ್ಕರಣೆ, ನಿಖರ ಅಭ್ಯರ್ಥಿ SHA, ಮ್ಯಾನಿಫೆಸ್ಟ್ ಡೈಜೆಸ್ಟ್ ಮತ್ತು ಎರಡು ವಿಭಿನ್ನ ಓಡಿಸುವ IDಗಳನ್ನು ಅಗತ್ಯವಿದೆ; ವಿರೋಧಾಭಾಸದ ಪರಿಕರಗಳನ್ನು ನಿರಾಕರಿಸಲಾಗುತ್ತದೆ. ಈ ಮೆಟಾಡೇಟಾ ಒಂದು ಆಡಿಟ್ ಒಪ್ಪಂದವಾಗಿದೆ, ಉಲ್ಲೇಖಿತ ಫೈಲ್ ನಿಜವಾದ ಅಳೆಯುವಿಕೆಗಳನ್ನು ಒಳಗೊಂಡಿದೆ ಎಂಬುದಕ್ಕೆ ಸಾಕ್ಷಿಯಲ್ಲ. ಯಾವುದೇ ಎಂಟ್ರಿಯನ್ನು ಸೇರಿಸುವ ಮೊದಲು ವಾಸ್ತವಿಕ ರಸೀದಿಗಳನ್ನು ಪರಿಶೀಲಿಸಿ. ನಿರ್ವಹಣಾ ಅಂಕಿ ಎಂಡ್ಪಾಯಿಂಟ್ ಮತ್ತು ವೀಡಿಯೋ ಡ್ಯಾಶ್‌ಬೋರ್ಡ್ ಸಂರಕ್ಷಿತ ತಯಾರಿತೆಯನ್ನು ಬಹಿರಂಗಪಡಿಸುತ್ತವೆ. ಕಾನ್ಫಿಗರ್ ಮಾಡಿದ ಮಾದರಿ ಉಪನಾಮವು ಮಾತ್ರ ಅದರ ಪರಿಷ್ಕರಣೆ ಅಥವಾ ಓಡುತ್ತಿರುವ ಅಭ್ಯರ್ಥಿ SHA ಅನ್ನು ಸ್ಥಾಪಿಸುವುದಿಲ್ಲ, ಆದ್ದರಿಂದ ಪ್ರಸ್ತುತ ಡ್ಯಾಶ್‌ಬೋರ್ಡ್ `HOLD` ಅನ್ನು ವರದಿ ಮಾಡುತ್ತದೆ, ಇತರ ಕಾರ್ಯಾಚರಣಾ ಪರಿಕರದಿಂದ ಅರ್ಹತೆಯನ್ನು ಪುನಃ ಬಳಸುವುದಿಲ್ಲ. ಸ್ಪಷ್ಟ ಪ್ರಯೋಗಾತ್ಮಕ ಆಯ್ಕೆ ಉತ್ತೇಜನದಿಂದ ಪ್ರತ್ಯೇಕವಾಗಿರುತ್ತದೆ; ಯಾವುದೇ ಡೀಫಾಲ್ಟ್ ಸ್ವಯಂಚಾಲಿತವಾಗಿ ಬದಲಾಯಿಸಲಾಗುವುದಿಲ್ಲ.

ಕೋಲರ್‌ಗಳು ಈಗಾಗಲೇ ಹೊಂದಾಣಿಕೆಯಾಗಿರುವ ಪಠ್ಯವನ್ನು ಹೊಂದಿರುವ ಬೆಂಬಲಿತ ವೀಡಿಯೋ ಭಾಗಕ್ಕೆ ಆಯ್ಕೆಯಾದ `transcript.cues` ಅರೆವನ್ನು ಜೋಡಿಸಬಹುದು. ಪ್ರತಿ ಕ್ಯೂಗೆ `text`, ಪರೀಕ್ಷಿತ ಅವಧಿಯ ಒಳಗೆ ನಿರ್ಧಿಷ್ಟ `start`/`end` ಅಂತರ ಮತ್ತು ಶ್ರೇಣೀಬದ್ಧ `source` (`client`, `embedded`, ಅಥವಾ `audio-bridge`) ಅನ್ನು ಹೊಂದಿರಬೇಕು; `confidence` ಡೀಫಾಲ್ಟ್‌ ಆಗಿ `1` ಆಗಿರುತ್ತದೆ ಮತ್ತು `0` ಮತ್ತು `1` ನಡುವಿನಲ್ಲಿಯೇ ಇರಬೇಕು. ನಿಖರ ನಕಲಿ ಕ್ಯೂಗಳನ್ನು ಒಗ್ಗರಿಸಲಾಗುತ್ತದೆ. OmniRoute ಈ ಮೆಟಾಡೇಟಾದಿಂದ ವರ್ಣನೆಯನ್ನು ಪ್ರಾರಂಭಿಸುವುದಿಲ್ಲ: ದೃಢೀಕೃತ ಕ್ಯೂಗಳನ್ನು ಮೂಲ, ವಿಶ್ವಾಸ ಮತ್ತು ಅಂತರದೊಂದಿಗೆ ವಿವರಿಸಿದ ಫಲಿತಾಂಶದಲ್ಲಿ ನಕಲಿಸಲಾಗುತ್ತದೆ ಮತ್ತು ಫ್ರೇಮ್ ಶೀರ್ಷಿಕೆಗಳೊಂದಿಗೆ ಅಸಂಬದ್ಧ ವೀಕ್ಷಣೆಯಂತೆ ಪ್ರದರ್ಶಿಸಲಾಗುತ್ತದೆ. ಅಮಾನ್ಯ, ವ್ಯಾಪ್ತಿಯ ಹೊರಗೊಮ್ಮಲು ಅಥವಾ ಮೂಲವಿಲ್ಲದ ಪಠ್ಯವನ್ನು ಶೀರ್ಷಿಕೆ ಹರಿವಿನಲ್ಲಿ ಮಿಶ್ರಿತಗೊಳಿಸುವ ಬದಲು ನಿರಾಕರಿಸಲಾಗುತ್ತದೆ. ಎರಡೂ ವಿನಂತಿ-ಶರೀರ ವರ್ಣನ ಚಾನೆಲ್‌ಗಳು ಒದಗಿಸಿದ ಮೂಲವನ್ನು `client` ಗೆ ಸಾಮಾನ್ಯೀಕರಿಸುತ್ತವೆ, ಸ್ವಯಂ-ದಾಖಲಿತ `embedded` ಅಥವಾ `audio-bridge` ಲೇಬಲ್‌ಗಳನ್ನು ಒಳಗೊಂಡಂತೆ. ವಿಶ್ವಾಸಾರ್ಹ ಲೇಬಲ್‌ಗಳನ್ನು ಕೇವಲ ಸರ್ವರ್-ಮಾಲೀಕದ ಅಡಾಪ್ಟರ್ ಮಾತ್ರ `trustedSource` ಆರ್ಗ್ಯುಮೆಂಟ್ ಮೂಲಕ ನಿಯೋಜಿಸಬಹುದು; ವಿನಂತಿ JSON ಕ್ಷೇತ್ರವು ಆ ಆರ್ಗ್ಯುಮೆಂಟ್‌ಗೆ ತಲುಪಲು ಸಾಧ್ಯವಿಲ್ಲ. ವರ್ಣನ ಪಠ್ಯವು ಮೂಲದಿಂದ ಪಡೆದ ಅಸಂಬದ್ಧ ಮಾಧ್ಯಮ-ಆಧಾರಿತ ವಿಷಯವಾಗಿರುತ್ತದೆ, ಅದರ ಮೂಲವನ್ನು ಪರಿಗಣಿಸದೇ, ಮತ್ತು ಎಂದಿಗೂ ಅಧಿಕಾರವನ್ನು ನಿರ್ಧರಿಸಬಾರದು.

ಒಂದು ಉನ್ನತ ಕೋಲರ್ ಒಂದೇ ವೀಡಿಯೋಗೆ `audioTranscript` ಪಠ್ಯವನ್ನು ಒದಗಿಸಬಹುದು; ಇದು ಸರ್ವರ್ ವರ್ಣನೆಯ ಸಾಕ್ಷಿಯಲ್ಲ, ಗ್ರಾಹಕ-ಒದಗಿಸಿದ ಪಠ್ಯವಾಗಿ ಪರಿಗಣಿಸಲಾಗುತ್ತದೆ. ಫ್ಯೂಷನ್ ಸೀಮ್ ದೃಶ್ಯ ಮತ್ತು ಧ್ವನಿ ವೀಕ್ಷಣಗಳನ್ನು ಒಂದೇ ಸಮಯದ ಮಿತಿಯ ಅಡಿಯಲ್ಲಿ ಮತ್ತು ನಿಲ್ಲಿಸುವ ಸಂಕೇತದ ಅಡಿಯಲ್ಲಿ ನಡೆಸುತ್ತದೆ, ಅವುಗಳನ್ನು ಸಾಮಾನ್ಯ ಕಾಲರೇಖೆಯ ಮೇಲೆ ಆದೇಶಿಸುತ್ತದೆ, ನಿಖರ ನಕಲನ್ನು ಒಗ್ಗರಿಸುತ್ತದೆ, ಮತ್ತು ಒಂದೇ ಬದಿಯು ಯಶಸ್ವಿಯಾಗುವಾಗ ಭಾಗಶಃ ಫಲಿತಾಂಶವನ್ನು ವರದಿ ಮಾಡುತ್ತದೆ. ಅಮಾನ್ಯ `audioTranscript` ಆ ಭಾಗಶಃ ಫಲಿತಾಂಶಕ್ಕೆ ಕುಸಿತಗೊಳ್ಳುತ್ತದೆ - ದೃಶ್ಯ ವಿವರಣೆ ಉಳಿಯುತ್ತದೆ ಮತ್ತು ಧ್ವನಿ ಶಾಖೆ ಶುದ್ಧೀಕೃತ ವಿಫಲ ಕೋಡ್ ಅನ್ನು ದಾಖಲಿಸುತ್ತದೆ - ಸಂಪೂರ್ಣ ವೀಡಿಯೋವನ್ನು ವಿಫಲಗೊಳಿಸುವ ಬದಲು. ಪ್ರತಿ ಶಾಖೆಯ ಲಭ್ಯತೆ, ಭಾಗಶಃ ಧ್ವಜ ಮತ್ತು ಶುದ್ಧೀಕೃತ ವಿಫಲ ಕೋಡ್‌ಗಳನ್ನು ವಿವರಿಸಿದ ಫಲಿತಾಂಶದಲ್ಲಿ, ಗಾರ್ಡ್‌ರೇಲ್ ಮೆಟಾಡೇಟಾದಲ್ಲಿ (`audioFusionRuns`/`audioFusionPartials`/`audioFusionFailureCodes`), ಫಲಿತಾಂಶ-ಕ್ಯಾಶ್ ಮೆಟಾಡೇಟಾದಲ್ಲಿ ಮತ್ತು ಬ್ರಿಡ್ಜ್ ಫ್ಯೂಷನ್ ಕೌಂಟರ್‌ಗಳಲ್ಲಿ ಉಳಿಸಲಾಗುತ್ತದೆ. ಡೀಫಾಲ್ಟ್ ವೀಡಿಯೋ ಬ್ರಿಡ್ಜ್ ಮಾರ್ಗವು ಮಾತು-ಟೆಕ್ಸ್ಟ್ ಅನ್ನು ಕರೆದು ಅಥವಾ ಎರಡನೇ ಮಾಧ್ಯಮ ನಕಲನ್ನು ಡೌನ್‌ಲೋಡ್ ಮಾಡುವುದಿಲ್ಲ; ಆ ಸ್ಪಷ್ಟ ಪಠ್ಯವಿಲ್ಲದೆ, ಇದು ವೀಡಿಯೋ ಮಾತ್ರವಾಗಿರುತ್ತದೆ.

**ವರ್ಣನ ಉಳಿವಿನುಡಿ (#12150 P1).** ಇದು ಸ್ವಯಂಚಾಲಿತವಾಗಿ ಅನ್ವಯಿಸುತ್ತದೆ ಯಾವಾಗಲಾದರೂ ವೀಡಿಯೋ ಬ್ರಿಡ್ಜ್ (ಅದು ಸ್ವಯಂ-ಆಪ್ಟ್-ಇನ್) ವರ್ಣನ ಕ್ಯೂ ಅನ್ನು ನಿರ್ವಹಿಸುತ್ತದೆ - ಪ್ರತ್ಯೇಕ ಉಳಿವಿನ ಧ್ವಜವಿಲ್ಲ. ಒಂದು ವಿನಂತಿ ಯಾವುದೇ ವರ್ಣನ ಕ್ಯೂ ಅನ್ನು ನಿರ್ವಹಿಸಿದಾಗ (ಕೋಲರ್-ಘೋಷಿತ `transcript` ಅಥವಾ ಫ್ಯೂಸ್ ಮಾಡಿದ `audioTranscript`), ಗಾರ್ಡ್‌ರೇಲ್ ಅದನ್ನು `videoBridgeObserved` ಎಂದು ಗುರುತಿಸುತ್ತದೆ ಮತ್ತು ವೀಡಿಯೋ ವಿವರಣೆಯ ಒಂದು ಸಂಪಾದಿತ ಛಾಯೆಯನ್ನು ಉತ್ಪಾದಿಸುತ್ತದೆ - ಪ್ರತಿಯೊಂದು ಕ್ಯೂನ ಉಚಿತ-ಪಠ್ಯದ ಶರೀರವನ್ನು `[redacted-video-transcript]` ಮೂಲಕ ಬದಲಾಯಿಸುವ ಸಮಾನವಾದ ವರ್ಣನ, ಶ್ರೇಣೀಬದ್ಧ ಕ್ಯೂ ಕ್ಷೇತ್ರವನ್ನು ಬದಲಾಯಿಸುವ ಮೂಲಕ ನಿರ್ಮಿತವಾಗುತ್ತದೆ (ಹೆಚ್ಚುFlattened ಪಠ್ಯವನ್ನು ಪಾರ್ಸ್ ಮಾಡುವ ಮೂಲಕ ಅಲ್ಲ, ಆದ್ದರಿಂದ ಯಾವುದೇ ಕ್ಯೂ ವಿಷಯ - ಶತ್ರು ಅಥವಾ ಸಾಮಾನ್ಯ, `]` ಅನ್ನು ಒಳಗೊಂಡ ಶರೀರಗಳನ್ನು ಒಳಗೊಂಡಂತೆ ` [inaudible]`/`[music]` - ಉಳಿಯಲು ಸಾಧ್ಯವಿಲ್ಲ). ಉಳಿಸಿದ ಕಾಲ್-ಲಾಗ್ ವಿನಂತಿ ಶರೀರವು ಪ್ರತಿಯೊಂದು ವೀಡಿಯೋ-ಆಧಾರಿತ ಪಠ್ಯ ಭಾಗವನ್ನು ಆ ಸಂಪಾದಿತ ಛಾಯೆಯೊಂದಿಗೆ ಬದಲಾಯಿಸುತ್ತದೆ, ವಿಷಯ ಸಮಾನತೆಗೆ ಹೊಂದಿಸಲಾಗಿದೆ; `fullText` ಆಂಕರ್ ಪೂರ್ಣಗೊಂಡ ಪೂರ್ವ-ಕಾಲ್ ಗಾರ್ಡ್‌ರೇಲ್ ಪೇಲೋಡ್‌ನಿಂದ ಪುನಃ ಓದಲಾಗುತ್ತದೆ, ಆದ್ದರಿಂದ ನಂತರದ ಶ್ರೇಣೀಬದ್ಧ ಗಾರ್ಡ್‌ರೇಲ್‌ಗಳ ನಂತರವೂ ಹೊಂದಾಣಿಕೆ ಯಶಸ್ವಿಯಾಗುತ್ತದೆ (PII ಮತ್ತು ಪ್ರಮಾಣಪತ್ರ ಮಾಸ್ಕರ್‌ಗಳು, ಆದ್ಯತೆ 10/95) ವಿವರಣಾ ಪಠ್ಯವನ್ನು ಸ್ಥಳದಲ್ಲಿ ಪುನರ್-ಲೇಖನ ಮಾಡುತ್ತದೆ ಮತ್ತು ನಂತರದ ವ್ಯವಸ್ಥೆ-ಪ್ರಾಂಪ್ಟ್/ಹ್ಯಾಂಡಾಫ್/ಮೆಮೊರಿ ಇಂಜೆಕ್ಷನ್ ಸಂದೇಶ ಶ್ರೇಣಿಯನ್ನು ಪುನರ್-ರೂಪಾಂತರಗೊಳಿಸುತ್ತದೆ. ಮಾದರಿಗೆ ಕಳುಹಿಸಲಾದ ಶರೀರವು ಬದಲಾಯಿತಿಲ್ಲ. ಗಮನಿಸಿದ ವಿನಂತಿಯು ಯಾವುದೇ ಶಾಶ್ವತ ಮೆಮೊರಿಯನ್ನು ಕೂಡ ತುಂಬಿಸುವುದಿಲ್ಲ (ವಿನಂತಿ ಮತ್ತು ಪ್ರತಿಕ್ರಿಯೆ-ಆಧಾರಿತ ನಿರ್ವಹಣೆಯನ್ನು ಬಿಟ್ಟು), ಆದ್ದರಿಂದ ಮಾದರಿಯ ಸ್ವಂತ ಉತ್ತರವು ಮೆಮೊರಿಯಲ್ಲಿನ ವರ್ಣನ ಪಠ್ಯವನ್ನು ಪ್ರತಿಬಿಂಬಿಸಲು ಸಾಧ್ಯವಿಲ್ಲ.

**ಕಚ್ಚಾ ವೀಡಿಯೋ ಕ್ಷೇತ್ರಗಳು (#12430).** ಬ್ರಿಡ್ಜ್ ಸಕ್ರಿಯಗೊಳ್ಳುವಾಗ ಮತ್ತು ಸ್ಥಳೀಯ ವೀಡಿಯೋ ಬೆಂಬಲ ತಿಳಿದಿಲ್ಲ ಅಥವಾ ಇಲ್ಲದಾಗ, ವ್ಯಾಖ್ಯಾನಿತ `transcript`/`audioTranscript` ಕ್ಷೇತ್ರಗಳು `videoBridgeObserved` ಅನ್ನು ಸಕ್ರಿಯಗೊಳಿಸುತ್ತವೆ, ವಿವರಣಾ ವಿಫಲತೆಯ ನಂತರ ಅಥವಾ `maxVideos` ಮಿತಿಯ ನಂತರವೂ. `null` ಮತ್ತು ಖಾಲಿ ಶ್ರೇಣಿಗಳು ಲೆಕ್ಕಹಾಕುತ್ತವೆ; ಇಲ್ಲದ ಕ್ಷೇತ್ರಗಳು ಮತ್ತು ವೀಡಿಯೋ ಹೊರಗಿನ ಮೆಟಾಡೇಟಾ ಲೆಕ್ಕಹಾಕುವುದಿಲ್ಲ. ಉಳಿಸಲಾದ ನಕಲುಗಳು ಈ ಕ್ಷೇತ್ರಗಳನ್ನು ಸಂಪಾದಿಸುತ್ತವೆ ಅಥವಾ ವಿನಂತಿಯನ್ನು ಬಿಟ್ಟುಹೋಗುತ್ತವೆ, ಮತ್ತು ಕ್ಯಾಶ್/ಮೆಮೊರಿ ಮೀರಿಸಲಾಗುತ್ತದೆ. ಒದಗಿಸುವ ಪೇಲೋಡ್ ಬದಲಾಯಿತಿಲ್ಲ.

ಹೆಚ್ಚುವರಿ ಉಳಿಸಲಾದ ನಕಲುಗಳು ಒಂದೇ ಗಮನಿಸಿದ-ವಿನಂತಿ ಸಂಕೇತವನ್ನು ಬಳಸುತ್ತವೆ. ಕಚ್ಚಾ ಪೂರ್ವ-ಗಾರ್ಡ್‌ರೇಲ್ ಕ್ಲೈಂಟ್-ವಿನಂತಿ ಸ್ನಾಪ್‌ಶಾಟ್, ಮೆಮೊರಿಯಲ್ಲಿನ ನಿರೀಕ್ಷಿತ ವಿನಂತಿ ಮತ್ತು ಮುಂಚಿನ ನಿರಾಕೃತ-ವಿನಂತಿ ಲಾಗ್ ಶ್ರೇಣೀಬದ್ಧ ಕ್ಷೇತ್ರಗಳನ್ನು ವೀಡಿಯೋ ಭಾಗಗಳಲ್ಲಿ ರಚನಾತ್ಮಕವಾಗಿ ಬದಲಾಯಿಸುತ್ತವೆ; ಪೈಪ್‌ಲೈನ್ ಹಂತಗಳು ಮತ್ತು ಪರಿಕರ ಹ್ಯಾಂಡಾಫ್ ಮೂಲಕ ಸಿಂಥೆಸೈಸ್ ಮಾಡಿದ ಶ್ರೇಣೀಬದ್ಧ ಪ್ರಾಂಪ್ಟ್‌ಗಳನ್ನು ಉಳಿಸಿದ-ವಿನಂತಿ-ಶರೀರದ ನದಿಯಲ್ಲಿ ಸಂಪಾದಿಸಲಾಗುತ್ತದೆ. ಉಳಿಸಿದ `video_content_removed` ಗುರುತಿಸುವಿಕೆ `previous_response_id` ಮುಂದುವರಿಯುವಿಕೆ ವಿಫಲವಾಗುತ್ತದೆ, ಬದಲಾಯಿತ ಪಠ್ಯವನ್ನು ಪುನರ್-ರಚಿಸಲು ಬದಲಾಗಿ, ಉದ್ದೇಶಿತವಾಗಿ ತ್ಯಜಿಸಲಾದ. ಗಮನಿಸಿದ ವಿನಂತಿಯು ಲಾಗ್ ಮಾಡುವ ಮೊದಲು ಅದರ ಪ್ರತಿ ಭಾಗದ ಸಂಪಾದಿತ ಛಾಯೆಯನ್ನು ಕಳೆದುಕೊಳ್ಳುತ್ತದೆ ಅಥವಾ ನಂತರದ ವಿನಂತಿ ಪರಿವರ್ತನೆಗಳ ನಂತರ ಹಲವಾರು ವೀಡಿಯೋ ಛಾಯೆಗಳಲ್ಲಿ ಒಂದೂ ಹೊಂದಾಣಿಕೆಯಾಗದಿದ್ದರೆ, ಉಳಿಸಲಾದ ವಿನಂತಿ ಶರೀರವನ್ನು ಸಂಪೂರ್ಣವಾಗಿ ಬಿಟ್ಟುಹೋಗುತ್ತದೆ, ಭಾಗಶಃ ಸಂಪಾದಿತ ವರ್ಣನವನ್ನು ಉಳಿಸುವ ಬದಲು.

ಹಂಚಿದ ಅಂಗಸಾಧನ ಪ್ರಕ್ರಿಯೆ-ಸ್ಥಳೀಯವಾಗಿದೆ: ಹ್ಯಾಂಡಲ್‌ಗಳು ಪುನರಾರಂಭದಾಗ ಮುಗಿಯುತ್ತವೆ ಮತ್ತು
ಸ್ವಾಯತ್ತ ಓಮ್ನಿರೌಟ್ ಪ್ರಕ್ರಿಯೆಗಳ ನಡುವೆ ವರ್ಗಾಯಿಸಲಾಗುವುದಿಲ್ಲ. ನಿರ್ವಹಣಾ ಅಂಕಿಅಂಶಗಳು ಪರಿಣಾಮಕಾರಿ ಉಳಿಸುವಿಕೆ/
ದೂರದ ನೀತಿಯನ್ನು ಮತ್ತು ಒಟ್ಟಾರೆ ಉಳಿಸಲಾದ ಎಂಟ್ರಿಗಳು/ಬೈಟ್ಸ್ ಅನ್ನು ಮಾತ್ರ ಬಹಿರಂಗಪಡಿಸುತ್ತವೆ, ಮಾಧ್ಯಮ, ಉಲ್ಲೇಖಗಳು,
ಪ್ರಿನ್ಸಿಪಲ್ IDಗಳು ಅಥವಾ ಹ್ಯಾಂಡಲ್‌ಗಳನ್ನು ಎಂದಿಗೂ ಅಲ್ಲ. ವಿಡಿಯೋ ಸೆಟಿಂಗ್‌ಗಳ ಪ್ಯಾನೆಲ್ ಆ ಮೌಲ್ಯಗಳನ್ನು ತೋರಿಸುತ್ತದೆ
ಮತ್ತು ಎರಡೂ ಒಪ್ಪಿಗೆಯ ಸ್ವಿಚ್‌ಗಳನ್ನು ಶಾಶ್ವತಗೊಳಿಸಲು ಸಾಧ್ಯವಾಗುತ್ತದೆ. ಈ ಕಾರ್ಯಗತ ದಾಖಲೆಗಳು ನೇರ ನಿಯೋಜನೆ ಅಥವಾ
ಪ್ರಚಾರದ ಸಾಕ್ಷ್ಯವಲ್ಲ; ವಾಸ್ತವ ಮಾದರಿಯ ಒಪ್ಪಿಗೆಯನ್ನು ಪ್ರತ್ಯೇಕವಾಗಿ ಹಂಚಿಕೊಳ್ಳಲಾಗುತ್ತದೆ.

ಫ್ರೇಮ್‌ಗಳನ್ನು ಕಾನ್ಫಿಗರ್ ಮಾಡಿದ ವಿಡಿಯೋ ಮಾದರಿಯೊಂದಿಗೆ ಕ್ರಮಬದ್ಧವಾಗಿ ಶೀರ್ಷಿಕೆಯನ್ನು ನೀಡಲಾಗುತ್ತದೆ. ಖಾಲಿ ವಿಡಿಯೋ ಓವರೈಡ್ ದೃಷ್ಟಿ ಸೆಟಿಂಗ್ ಅನ್ನು ಪರಿಗಣಿಸುತ್ತದೆ; ಎರಡೂ ಖಾಲಿಯಾಗಿದ್ದರೆ, ದೃಷ್ಟಿ ಸ್ವಯಂಚಾಲಿತ-ರೌಟರ್ ಪರಿಣಾಮಕಾರಿ ದೃಷ್ಟಿ-ಸಾಧ್ಯ ಮಾದರಿಯನ್ನು ಆಯ್ಕೆ ಮಾಡುತ್ತದೆ. ಯಶಸ್ವೀ ಶೀರ್ಷಿಕೆಗಳು ಮೂಲ ಭಾಗವನ್ನು ಸ್ಥಿರ `[Video description:` ಪೂರ್ವಭಾವಿಯೊಂದಿಗೆ ಬದಲಾಯಿಸುತ್ತವೆ, ಇದು ಪಠ್ಯವನ್ನು ಅಪ್ರಮಾಣಿತ ಮಾಧ್ಯಮ-ಆಧಾರಿತ ಗಮನಾರ್ಹವಾಗಿ ಗುರುತಿಸುತ್ತದೆ ಮತ್ತು ಕೆಳಗಿನ ಮಾದರಿಗಳಿಗೆ ಮಾಧ್ಯಮದಲ್ಲಿ ಕಂಡುಬರುವ ಸೂಚನೆಗಳನ್ನು ಅನುಸರಿಸಲು ಹೇಳುತ್ತದೆ. ಫ್ರೇಮ್-ಶೀರ್ಷಿಕೆ ಕ್ಯಾಶ್ ಕೀಗಳಲ್ಲಿ JPEG ಬೈಟ್ಸ್, ಪ್ರಾಂಪ್ಟ್, ಟೈಮ್‌ಸ್ಟ್ಯಾಂಪ್ ಮತ್ತು ಪರಿಣಾಮಕಾರಿ ಮಾದರಿ ಸೇರಿವೆ; ಕೇವಲ ಯಶಸ್ವೀ ಶೀರ್ಷಿಕೆಗಳನ್ನು ಮಾತ್ರ ಕ್ಯಾಶ್ ಮಾಡಲಾಗುತ್ತದೆ. ಕ್ಯಾಶ್ ಎಂಟ್ರಿಗಳು ವಾಸ್ತವ ಯಶಸ್ವೀ ಉತ್ಪಾದಕ ಮಾದರಿಯನ್ನು, ಫಾಲ್ಬ್ಯಾಕ್ ಮಾದರಿಯನ್ನು ಒಳಗೊಂಡಂತೆ, ಉಳಿಸುತ್ತದೆ; ಬ್ರಿಡ್ಜ್ ವಿಭಿನ್ನ ಮಾದರಿಗಳಿಂದ ಉತ್ಪಾದಿತ ವಿಭಿನ್ನ ಫ್ರೇಮ್‌ಗಳಿಗೆ `mixed` ಅನ್ನು ವರದಿ ಮಾಡುತ್ತದೆ. ಕ್ಯಾಶ್ ಹಿಟ್ ಆ ಉತ್ಪಾದಕ ಗುರುತನ್ನು ಪುನಃ ಬಳಸುತ್ತದೆ, ಅದನ್ನು ಕೇಳಿದ ರೌಟಿಂಗ್ ಯೋಜನೆಯಂತೆ ಪುನಃ ಲೇಬಲ್ ಮಾಡುವ ಬದಲು. ಸಂಪೂರ್ಣ-ವಿಡಿಯೋ ಫಲಿತಾಂಶ ಕ್ಯಾಶ್ ಪ್ರತಿಯೊಂದು ಇನ್ಪುಟ್‌ನಲ್ಲಿ ಕೀಡಾಗುತ್ತದೆ, ಅದು ಔಟ್‌ಪುಟ್ ಅನ್ನು ಬದಲಾಯಿಸುತ್ತದೆ — ಪ್ರಾಂಪ್ಟ್, ಪರಿಣಾಮಕಾರಿ ಮಾದರಿ, ಮಾದರೀಕರಣ ನೀತಿ, ಫ್ರೇಮ್ ಸಂಖ್ಯಾ, ಅರ್ಥಶಾಸ್ತ್ರ ವಿಶ್ಲೇಷಣಾ ಮೋಡ್, ನಾರ್ಮಲೈಜ್ಡ್ ಫೋಕಸ್ ಹಿಂಟ್ನ SHA-256 ಫಿಂಗರ್‌ಪ್ರಿಂಟ್, ಫೋಕಸ್ ವಿಂಡೋ, `transcript`, `audioTranscript`, ಮತ್ತು ಸಂಪರ್ಕ-ಶೀಟ್ ಧ್ವಜ — ಆದ್ದರಿಂದ ಆ ಆಯಾಮಗಳಲ್ಲಿ ಯಾವುದೇ ಬದಲಾವಣೆ ಕ್ಯಾಶ್ ಮಿಸ್, ಎಂದಿಗೂ ಹಳೆಯ ಪುನಃ ಬಳಸುವುದಿಲ್ಲ. ದೃಶ್ಯ ಡಿಡುಪ ನೀತಿ ಆವೃತ್ತಿ, ಥ್ರೆಶೋಲ್ಡ್ ಮತ್ತು ಬೌಂಡೆಡ್ ಕ್ಯಾಂಡಿಡೇಟ್-ಫ್ರೇಮ್ ಸಂಖ್ಯೆಯು ಫಲಿತಾಂಶ-ಕ್ಯಾಶ್ ಕೀ ಮತ್ತು ಮೆಟಾಡೇಟಾದಲ್ಲಿ ಸ್ಪಷ್ಟವಾಗಿದೆ; ಆದ್ದರಿಂದ ನೀತಿ ಬದಲಾವಣೆ ಹಳೆಯ ಸಂಪೂರ್ಣ-ವಿಡಿಯೋ ವಿವರಣೆಯನ್ನು ಪುನಃ ಬಳಸಲು ಸಾಧ್ಯವಿಲ್ಲ. ಫಲಿತಾಂಶ-ಕ್ಯಾಶ್ v4 ಮೆಟಾಡೇಟಾ ಮೋಡ್ ಮತ್ತು ಫಿಂಗರ್‌ಪ್ರಿಂಟ್ ಅನ್ನು ಉಳಿಸುತ್ತದೆ, ಎಂದಿಗೂ ಕಚ್ಚಾ ಬಳಕೆದಾರ ಕಾರ್ಯವನ್ನು ಅಲ್ಲ. ಗಾರ್ಡ್‌ರೇಲ್ ಮೆಟಾಡೇಟಾ ಕೇಳಿದ ಮತ್ತು ಪರಿಣಾಮಕಾರಿ ವಿಶ್ಲೇಷಣಾ ಮೋಡ್‌ಗಳನ್ನು ವರದಿ ಮಾಡುತ್ತದೆ; ಬಳಸಬಹುದಾದ ಬಳಕೆದಾರ ಪಠ್ಯವಿಲ್ಲದ ಕೇಳಿದ `focused` ಮೋಡ್ ಪರಿಣಾಮಕಾರಿಯಾಗಿ `full` ಎಂದು ವರದಿ ಮಾಡುತ್ತದೆ.

ಗಾರ್ಡ್‌ರೇಲ್ ಬೆಂಬಲಿತ ವಿಡಿಯೋ ಭಾಗಗಳನ್ನು ಎಲ್ಲವನ್ನು ತೆಗೆದುಹಾಕುತ್ತದೆ ಆದರೆ `modalityBridgeVideoMaxVideos` ಕ್ಕಿಂತ ಹೆಚ್ಚು ವಿವರಿಸುತ್ತಿಲ್ಲ. `supportsVideo === false` ಹೊಂದಿರುವ ಗುರಿಯು, ವಿಫಲ ಮತ್ತು ಮಿತಿಯ ಮೀರಿಸಿದ ವಿಡಿಯೋಗಳು ಸ್ಪಷ್ಟ ಸುರಕ್ಷಿತ ಪಠ್ಯ ಗುರುತಿಗಳಾಗುತ್ತವೆ, ಆದ್ದರಿಂದ ಯಾವುದೇ ಕಚ್ಚಾ ವಿಡಿಯೋ ಉಳಿಯುವುದಿಲ್ಲ. ಸಾಮರ್ಥ್ಯ ತಿಳಿದಿಲ್ಲದಾಗ, ಆ ಭಾಗಗಳು ಅಚಲವಾಗಿರುತ್ತವೆ. `supportsVideo === true` ಹೊಂದಿರುವ ಗುರಿಗಳು ಬ್ರಿಡ್ಜ್ ಅನ್ನು ಬypass ಮಾಡುತ್ತವೆ. ಕ್ಲೈಂಟ್ ವಿನಂತಿ ನಿಲ್ಲಿಸುವ ಸಂಕೇತವು ಡೌನ್‌ಲೋಡ್, ಬ್ರೋಕರ್ ಕ್ಯೂ, ಉಪಪ್ರಕ್ರಿಯೆಗಳು ಮತ್ತು ಶೀರ್ಷಿಕೆ ಕರೆಗಳ ಮೂಲಕ ಹರಡುತ್ತದೆ; ನಿಲ್ಲಿಸುವುದು ವಿಡಿಯೋಗಳ ನಡುವಿನಲ್ಲಿದೆ ಮತ್ತು ಕಚ್ಚಾ ಮಾಧ್ಯಮಕ್ಕೆ ಎಂದಿಗೂ ವಿಫಲವಾಗುವುದಿಲ್ಲ.

### PII ಮಾಸ್ಕರ್ (`piiMasker.ts`)

**ಎರಡು** ಹಂತಗಳಲ್ಲಿ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತದೆ.

- **`preCall`** ಪೇಲೋಡ್ ಅನ್ನು ಕ್ಲೋನ್ ಮಾಡುತ್ತದೆ, `system`, `messages`, `input`, ಮತ್ತು `prompt` (ಸರಳ ಸ್ಟ್ರಿಂಗ್ ಐಟಮ್‌ಗಳನ್ನು ಒಳಗೊಂಡಂತೆ) ಅನ್ನು ಸಾಗಿಸುತ್ತದೆ ಮತ್ತು `processPII()` ( `@/shared/utils/inputSanitizer` ನಿಂದ) ಅನ್ನು ಸ್ಟ್ರಿಂಗ್ `content`/`text` ಕ್ಷೇತ್ರಗಳಿಗೆ ಅನ್ವಯಿಸುತ್ತದೆ. `PII_REDACTION_ENABLED=true` ಆಗಿದ್ದಾಗ, ಪತ್ತೆಯಾದ PII ಔಟ್‌ಬೌಂಡ್ ಪೇಲೋಡ್‌ನಲ್ಲಿ ಅಡಗಿಸಲಾಗುತ್ತದೆ. ಇದು `INPUT_SANITIZER_MODE` (ಯಾವುದೇ ಪ್ರಾಂಪ್ಟ್-ಇಂಜೆಕ್ಷನ್ ನೀತಿಯನ್ನು ಮಾತ್ರ ನಿಯಂತ್ರಿಸುತ್ತದೆ) ಗೆ ಸ್ವಾಯತ್ತವಾಗಿದೆ. ಅಡಗಿಸುವಿಕೆ выключಿತವಾಗಿದ್ದಾಗ, ಕರೆ ಪತ್ತೆಗೊಳ್ಳುವ ಸಂಖ್ಯೆಯನ್ನು ದಾಖಲಿಸುತ್ತದೆ, ವಿಷಯವನ್ನು ಪುನಃ ಬರೆಯುವುದಿಲ್ಲ.
- **`postCall`** ಪ್ರತಿಸ್ಪಂದನವನ್ನು ಡೀಪ್-ಕ್ಲೋನ್ ಮಾಡುತ್ತದೆ, `sanitizePIIResponse()` ಅನ್ನು ಓಡಿಸುತ್ತದೆ ಮತ್ತು ಪ್ರತಿಸ್ಪಂದನೆ-API-ಆಕೃತಿಯ ಮಾಸ್ಕರ್ (`maskResponsesOutput` — `output_text` ಮತ್ತು `output[].content[].text` ಅನ್ನು ಒಳಗೊಂಡಿದೆ). ಯಾವುದೇ ಅಡಗಿಸುವಿಕೆ ಸಂಭವಿಸಿದರೆ, ಪರಿಷ್ಕೃತ ಪ್ರತಿಸ್ಪಂದನೆ ಮೂಲವನ್ನು ಬದಲಾಯಿಸುತ್ತದೆ.

ಗಾರ್ಡ್‌ರೇಲ್ ಎಂದಿಗೂ ಅಡ್ಡಗಟ್ಟುವುದಿಲ್ಲ; ಇದು ಕೇವಲ ಟಿಪ್ಪಣಿಗಳನ್ನು ನೀಡುತ್ತದೆ (`meta.detections`, `meta.redacted`) ಅಥವಾ ಪುನಃ ಬರೆಯುತ್ತದೆ.

### ಪ್ರಾಂಪ್ಟ್ ಇಂಜೆಕ್ಷನ್ (`promptInjection.ts`)

ಬಳಕೆದಾರ-ನೀಡಿದ ವಿಷಯದಲ್ಲಿ ಶತ್ರು ಶ್ರೇಣಿಗಳನ್ನು ಪತ್ತೆಹಚ್ಚುತ್ತದೆ ಮತ್ತು ಕಾನ್ಫಿಗರ್ ಮಾಡಿದ ನೀತಿಯನ್ನು ಜಾರಿಗೆ ತರುತ್ತದೆ. ವರ್ತನೆ ಪರಿಸರ ಚರಗಳು ಮತ್ತು ನಿರ್ಮಾಪಕ ಆಯ್ಕೆಗಳ ಮೂಲಕ ನಿರ್ಧಾರವಾಗುತ್ತದೆ:

| ಸೆಟಿಂಗ್           | ಪರಿಸರ ಚರ                                                                                             | ಡೀಫಾಲ್ಟ್ | ಪರಿಣಾಮ                                                                                                                                                                                                            |
| ----------------- | ---------------------------------------------------------------------------------------------------- | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ಸಕ್ರಿಯ            | `INPUT_SANITIZER_ENABLED`                                                                            | `true`   | `false` ಆಗಿರುವಾಗ, ಗಾರ್ಡ್‌ರೇಲ್ ಶಾರ್ಟ್-ಸರ್ಕಿಟ್ ಆಗುತ್ತದೆ.                                                                                                                                                            |
| ಮೋಡ್              | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                      | `warn`   | ಇಂಜೆಕ್ಷನ್ ನೀತಿ: `block`, `warn`, ಅಥವಾ `log`. (`redact` ಹಿಂದಿನ-ಸಂಗತಕ್ಕಾಗಿ ಒಪ್ಪಿಗೆಯಾಗಿದೆ ಆದರೆ ಇಂಜೆಕ್ಷನ್ ಪಠ್ಯವನ್ನು **ಅಳಿಸುವುದಿಲ್ಲ**; PII ಪುನರ್-ಲೇಖನವನ್ನು ವಿನಂತಿಸುವುದು `PII_REDACTION_ENABLED` ಮೂಲಕ ನಿಯಂತ್ರಿತವಾಗಿದೆ.) |
| ಬ್ಲಾಕ್ ಥ್ರೆಶೋಲ್ಡ್ | `blockThreshold` ಆಯ್ಕೆ / `INPUT_SANITIZER_BLOCK_THRESHOLD` (ಉಪನಾಮ `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`   | ಬ್ಲಾಕ್ ಮಾಡಲು ಅಗತ್ಯವಿರುವ ಕನಿಷ್ಠ ತೀವ್ರತೆ. ಮಧ್ಯಮವು ಡೀಫಾಲ್ಟ್‌ನಲ್ಲಿobserve-only ಆಗಿದೆ.                                                                                                                                 |

**ಮೋಡ್ ಆದ್ಯತೆ** (`getMode`): ಕರೆದಾರ `options.mode` →
`INJECTION_GUARD_MODE` **ಡಿಬಿ ವೈಶಿಷ್ಟ್ಯ-ಫ್ಲಾಗ್ ಓವರೈಡ್** (ಡ್ಯಾಶ್‌ಬೋರ್ಡ್ → ಸೆಟಿಂಗ್‌ಗಳು →
ಫೀಚರ್ ಫ್ಲಾಗ್‌ಗಳು) → `INJECTION_GUARD_MODE` ಪರಿಸರ → `INPUT_SANITIZER_MODE` ಪರಿಸರ →
`warn`. ಆದ್ದರಿಂದ ಡ್ಯಾಶ್‌ಬೋರ್ಡ್ ಓವರೈಡ್ ಪರಿಸರ ಚರಗಳಿಗೆ ಮೆಲುಕು ಹಾಕುತ್ತದೆ, ಆದ್ದರಿಂದ ಫೀಚರ್
ಫ್ಲಾಗ್‌ಗಳು UI ನಡಿಸುತ್ತಿರುವ ಗಾರ್ಡ್ ಅನ್ನು ನೇರವಾಗಿ ನಿಯಂತ್ರಿಸುತ್ತವೆ (ಮರುಪ್ರಾರಂಭವಿಲ್ಲ). ಡಿಬಿ ಓದು ವಿಫಲ-ಸುರಕ್ಷಿತವಾಗಿದೆ:
ಇದು ದೋಷವಾಗಿದ್ದರೆ, ಗಾರ್ಡ್ ಪರಿಸರಾಧಾರಿತ ವರ್ತನೆಗೆ ಹಿಂತಿರುಗುತ್ತದೆ, ಮತ್ತು ಯಾವುದೇ
ಓವರೈಡ್ ಹೊಂದಿಲ್ಲದಾಗ ವರ್ತನೆ ಪರಿಸರ-ಮಾತ್ರದ ನಿರ್ಧಾರಕ್ಕೆ ಸಮಾನವಾಗಿದೆ.

ಹುಡುಕಾಟ ಮೂಲಗಳು:

1. `sanitizeRequest()` from `@/shared/utils/inputSanitizer` (ಪೈಪ್‌ಲೈನ್‌ನಲ್ಲಿ ಇತರ ಸ್ಥಳಗಳಲ್ಲಿ ಬಳಸುವ ಹಂಚಿದ ಡಿಟೆಕ್ಟರ್ ಸೆಟ್).
2. ನಿರ್ಮಿತ `DEFAULT_GUARD_PATTERNS` (ಪ್ರಸ್ತುತ `system_override_inline` ಮತ್ತು
   `markdown_system_block`, ಎರಡೂ `high` ತೀವ್ರತೆ).
3. ಕಸ್ಟಮ್ ಆಯ್ಕೆಗಳು ಮೂಲಕ ಕಾನ್ಸ್ಟ್ರಕ್ಟರ್ ಆಯ್ಕೆಗಳ ಮೂಲಕ ಪಾಸ್ ಮಾಡಿದ ಆಯ್ಕೆಯ `customPatterns` (ಸ್ಟ್ರಿಂಗ್‌ಗಳು, regex,
   ಅಥವಾ `{ name, pattern, severity }` ದಾಖಲೆಗಳು).

`mode === "block"` **ಮತ್ತು** ಕನಿಷ್ಠ ಒಂದು ಪತ್ತೆ ತೀವ್ರತೆ ಥ್ರೆಶೋಲ್ಡ್ ಅನ್ನು ಪೂರೈಸಿದಾಗ, `preCall` `{ block: true, message: "Request rejected:
suspicious content detected" }` ಅನ್ನು ಹಿಂತಿರುಗಿಸುತ್ತದೆ. `warn`/`log` ಮೋಡ್‌ಗಳಲ್ಲಿ ಗಾರ್ಡ್‌ರೇಲ್ ಲಾಗ್‌ಗಳನ್ನು ಮಾಡುತ್ತದೆ ಆದರೆ
ಕೋಲೆಯನ್ನು ಅನುಮತಿಸುತ್ತದೆ. ಹಂಚಿದ ಸಹಾಯಕ `evaluatePromptInjection()` ಅನ್ನು ಸಹ ಕರೆದಾರರಿಗೆ
ರಿಜಿಸ್ಟ್ರಿ ಮೂಲಕ ಹೋಗದೆ ಪ್ರಾಂಪ್ಟ್‌ಗಳನ್ನು ಮೌಲ್ಯಮಾಪನ ಮಾಡಲು ರಫ್ತು ಮಾಡಲಾಗಿದೆ.

**ಸ್ಕಾನ್ ಬೌಂಡ್ (v3.8.20):** ಡಿಟೆಕ್ಟರ್ ಕೇವಲ **ಮೊದಲ 16 KB** ಅನ್ನು ಪರಿಶೀಲಿಸುತ್ತದೆ
ಜೋಡಿಸಲಾದ ಪ್ರಾಂಪ್ಟ್ ಪಠ್ಯ — `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 ಬೈಟ್ಸ್) in
`src/shared/utils/inputSanitizer.ts`. `detectInjection()` ಮತ್ತು
`evaluatePromptInjection()` `slice(0, MAX_INJECTION_SCAN_BYTES)` ಅನ್ನು pattern ಲೂಪ್ ಅನ್ನು ನಿರ್ವಹಿಸುವ ಮೊದಲು. ಇಂಜೆಕ್ಷನ್ ನಿರ್ದೇಶನಗಳು ಇನ್ಪುಟ್‌ನ ಶ್ರೇಣಿಯ ಹತ್ತಿರವಿವೆ, ಆದ್ದರಿಂದ ಇದು
ಬಹು-ಶತ-ಕೆಬಿ ಪೇಲೋಡ್‌ಗಳಲ್ಲಿ regex CPU/GC ಅನ್ನು ಕಡಿಮೆ ಮಾಡುತ್ತದೆ ಮತ್ತು ಪತ್ತೆ ಮಾಡುವುದನ್ನು ದುರ್ಬಲಗೊಳಿಸುವುದಿಲ್ಲ (cf.
#3932, #4041).

### ಕ್ರೆಡೆನ್ಷಿಯಲ್ ಮಾಸ್ಕರ್ (`credentialMasker.ts`)

**ಎಲ್ಲಾ** ಹಂತಗಳಲ್ಲಿ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತದೆ, ಡೀಫಾಲ್ಟ್ ಶ್ರೇಣಿಯಲ್ಲಿ ಕೊನೆಯದು (ಆಗತ್ಯ `95`). ಹೊರಗಿನ ಪೇಲೋಡ್‌ಗಳಿಂದ (ಸಂದೇಶ
ಪಠ್ಯ, ಸಾಧನ-ಕೋಲ್ ವಾದಗಳು, ಸಾಧನ ಫಲಿತಾಂಶಗಳು) ಪ್ರಸಿದ್ಧ API-ಕೀ / ರಹಸ್ಯ-ಟೋಕನ್ ಮಾದರಿಗಳನ್ನು ಅಳಿಸುತ್ತದೆ **ಮತ್ತು** ಒದಗಿಸುವ ಪ್ರತಿಕ್ರಿಯೆ, ಆದ್ದರಿಂದ ಪ್ರಾಂಪ್ಟ್‌ನಲ್ಲಿ ಅಂಟಿಸಿದ ಕ್ರೆಡೆನ್ಷಿಯಲ್ (ಅಥವಾ ಸಾಧನ ಫಲಿತಾಂಶದಿಂದ ಹಿಂತಿರುಗಿಸಿದ) ಮೇಲ್ಮಟ್ಟ ಒದಗಿಸುವವರಿಗೆ ಅಥವಾ ಕ್ಲೈಂಟ್‌ಗೆ ಲೀಕ್ ಆಗುವುದಿಲ್ಲ.

- **ಆಪ್ಟ್-ಇನ್ ಮಾತ್ರ**, PII ಪುನರ್-ಲೇಖನದಂತೆ ಒಂದೇ ನಿಯಮ (ಹಾರ್ಡ್ ರೂಲ್ #20-ಅಡ್ಜಸೆಂಟ್):
  `settings.credentialRedactionEnabled === true` **ಅಥವಾ**
  `CREDENTIAL_REDACTION_ENABLED=true` ಇಲ್ಲದಿದ್ದರೆ ನಿಷ್ಕ್ರಿಯವಾಗಿದೆ. ಇದನ್ನು ಆಫ್ ಮಾಡಿದಾಗ, ಗಾರ್ಡ್‌ರೇಲ್ ನೊ-ಆಪ್ ಆಗಿದೆ —
  ಇದು ಎಂದಿಗೂ ಬ್ಲಾಕ್ ಆಗುವುದಿಲ್ಲ ಮತ್ತು ಎಂದಿಗೂ ಪುನರ್-ಲೇಖನ ಮಾಡುವುದಿಲ್ಲ.
- `redactCredentials()` ಸಂಪೂರ್ಣ ಪೇಲೋಡ್/ಪ್ರತಿಕ್ರಿಯೆ ಮರವನ್ನು ಸಾಗಿಸುತ್ತದೆ (`walkValue()`,
  ಪ್ರೋಟೋಟೈಪ್-ಪಾಲ್ಯೂಷನ್-ಸುರಕ್ಷಿತ, ಚಕ್ರ-ಸುರಕ್ಷಿತ `WeakSet` ಮೂಲಕ) ಮತ್ತು ಹೊಂದಾಣಿಕೆಗಳನ್ನು
  `[REDACTED:<type>]` ಪ್ಲೇಸ್‌ಹೋಲ್ಡರ್‌ಗಳೊಂದಿಗೆ ಬದಲಾಯಿಸುತ್ತದೆ, ವಾಸ್ತವವಾಗಿ ಬದಲಾಯಿಸಿದ ಶಾಖೆಗಳನ್ನು ಮಾತ್ರ ಕ್ಲೋನ್ ಮಾಡುತ್ತದೆ.
- `CREDENTIAL_PATTERNS` LLM ಒದಗಿಸುವ ಕೀಗಳನ್ನು ಒಳಗೊಂಡಿದೆ (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), VCS/SaaS ಟೋಕನ್‌ಗಳು (GitHub, Slack,
  ಲೀನಿಯರ್, ನೋಟಿಯನ್, npm, ಪೋಸ್ಟ್‌ಮನ್, ಡಿಸ್ಕೋರ್ಡ್), ಪಾವತಿ ಕೀಗಳು (Stripe, Square), ಕ್ಲೌಡ್
  ಕೀಗಳು (AWS ಪ್ರವೇಶ ಕೀ, Twilio, SendGrid, Mailgun), ಖಾಸಗಿ ಕೀಗಳು / JWTಗಳು,
  ಕ್ರೆಡೆನ್ಷಿಯಲ್-ಬೇರುವ ಸಂಪರ್ಕ ಶ್ರೇಣಿಗಳು (`mongodb://user:pass@...`, ಇತ್ಯಾದಿ), ಮತ್ತು
  ಸಾಮಾನ್ಯ `Authorization`/`x-api-key`/`api-key`/`apikey` ಹೆಡರ್-ಮೌಲ್ಯ
  ಮಾದರಿಯು. ಹೆಡರ್-ಆಕಾರದ ಕೀಗಳು (`authorization`, `x-api-key`, `api-key`,
  `apikey`) ರಚನಾತ್ಮಕವಾಗಿ ಅಳಿಸಲಾಗುತ್ತದೆ (ಮೌಲ್ಯ ಮಾತ್ರ, ಯೋಜನೆ ಪೂರ್ವಭಾವಿ `Bearer `/`Basic ` ಉಳಿಸಲಾಗಿದೆ) ಸಾಮಾನ್ಯ ಪಠ್ಯ regex ಮೂಲಕ ಅಲ್ಲ.
- ಗಾರ್ಡ್‌ರೇಲ್ ಎಂದಿಗೂ ಬ್ಲಾಕ್ ಮಾಡುವುದಿಲ್ಲ; ಇದು ಕೇವಲ ಪುನರ್-ಲೇಖನ ಮಾಡುತ್ತದೆ (`modifiedPayload` /
  `modifiedResponse`) ಮತ್ತು ಟ್ಯಾಗ್ ಮಾಡುತ್ತದೆ (`meta.credentialsRedacted`, `meta.count`).

ಪುನರಾವೃತ್ತ ಗಾರ್ಡ್: `tests/unit/credential-masker-guardrail.test.ts`.

## ಮೂಲ ಒಪ್ಪಂದ (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true ಸರಪಳಿಯನ್ನು ತಕ್ಷಣವೇ ಸ್ಥಗಿತಗೊಳಿಸುತ್ತದೆ
  message?: string; // ನಿರ್ಬಂಧಿಸುವಾಗ ಪ್ರದರ್ಶಿಸಲಾಗುತ್ತದೆ
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // ವಿನಂತಿಯನ್ನು ಮರುಬರೆಯಲು preCall ಮೂಲಕ ಹಿಂತಿರುಗಿಸಲಾಗುತ್ತದೆ
  modifiedResponse?: TValue; // ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು ಮರುಬರೆಯಲು postCall ಮೂಲಕ ಹಿಂತಿರುಗಿಸಲಾಗುತ್ತದೆ
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

`void`, `{}`, ಅಥವಾ `{ block: false }` ಇವುಗಳಲ್ಲಿ ಯಾವುದನ್ನಾದರೂ ಹಿಂತಿರುಗಿಸುವ ಮೂಲಕ guardrail "ಯಾವುದೇ ಬದಲಾವಣೆ ಇಲ್ಲ" ಎಂದು ಸೂಚಿಸುತ್ತದೆ. `modifiedPayload`/`modifiedResponse` ಅನ್ನು ಹಿಂತಿರುಗಿಸುವುದರಿಂದ, ನಂತರದ guardrailಗಳಿಗಾಗಿ ಸರಪಳಿಯ ಮೂಲಕ ಹರಿಯುವ ಮೌಲ್ಯವನ್ನು ಅದು ಬದಲಿಸುತ್ತದೆ.
`signal?: AbortSignal` ಕಾಲರ್ನ ಜೀವನಚಕ್ರವನ್ನು guardrailಗಳಿಗೆ ಒಯ್ಯುತ್ತದೆ. ವಿನಂತಿಯ ರದ್ದತಿಯು ಉದ್ದೇಶಪೂರ್ವಕ fail-open ಅಪವಾದವಾಗಿದೆ: media bridgeಗಳು ಕೆಲಸವನ್ನು ನಿಲ್ಲಿಸಿ cleanup ಮಾಡುತ್ತವೆ ಮತ್ತು ಅದನ್ನು ಬೆಂಬಲಿಸುವುದಿಲ್ಲ ಎಂದು ತಿಳಿದಿರುವ ಗುರಿಗೆ raw media ಅನ್ನು ಮರುಸ್ಥಾಪಿಸುವುದಿಲ್ಲ.

## ರಿಜಿಸ್ಟ್ರಿ (`registry.ts`)

singleton `guardrailRegistry` ಈ ಕೆಳಗಿನವುಗಳನ್ನು ಒದಗಿಸುತ್ತದೆ:

- `register(guardrail)` — guardrail ಅನ್ನು ಸೇರಿಸುತ್ತದೆ (ಅಥವಾ normalized name ಆಧಾರದಲ್ಲಿ ಬದಲಿಸುತ್ತದೆ) ಮತ್ತು ಏರಿಕೆ ಕ್ರಮದ `priority` ಪ್ರಕಾರ ಮರು-ವಿಂಗಡಿಸುತ್ತದೆ.
- `clear()` / `list()` — ಆಡಳಿತಾತ್ಮಕ ಸಹಾಯಕಗಳು.
- `runPreCallHooks(payload, context)` — ಸಕ್ರಿಯ guardrailಗಳ ಮೂಲಕ ಪುನರಾವರ್ತಿಸುತ್ತದೆ, `modifiedPayload` ಮೂಲಕ payload ಅನ್ನು ಮುಂದಕ್ಕೆ ಕೊಂಡೊಯ್ಯುತ್ತದೆ ಮತ್ತು ಮೊದಲ `block: true` ದೊರೆತಾಗ ನಿಲ್ಲುತ್ತದೆ.
- `runPostCallHooks(response, context)` — response ಭಾಗದಲ್ಲಿಯೂ ಇದೇ ಹರಿವನ್ನು ಅನುಸರಿಸುತ್ತದೆ.
- `resetGuardrailsForTests({ registerDefaults })` — ಸ್ಥಿತಿಯನ್ನು ತೆರವುಗೊಳಿಸುತ್ತದೆ ಮತ್ತು ಸ್ವಚ್ಛ test isolationಗಾಗಿ ಐಚ್ಛಿಕವಾಗಿ defaults ಅನ್ನು ಮರು-ನೋಂದಾಯಿಸುತ್ತದೆ.

ಎರಡೂ runnerಗಳು `{ blocked, payload|response, results, guardrail?, message? }` ಅನ್ನು ಹಿಂತಿರುಗಿಸುತ್ತವೆ, ಇಲ್ಲಿ `results` ಎಂಬುದು ಪ್ರತಿಯೊಂದು guardrailಗೆ ಸಂಬಂಧಿಸಿದ `blocked`, `skipped`, `modified`, `error`, ಮತ್ತು `meta` ಕ್ಷೇತ್ರಗಳನ್ನು ಒಳಗೊಂಡಿರುವ `GuardrailExecutionResult` recordಗಳ array ಆಗಿದ್ದು, tracingಗೆ ಉಪಯುಕ್ತವಾಗಿದೆ.

### ಪ್ರತಿ ವಿನಂತಿಗೆ Guardrailಗಳನ್ನು ನಿಷ್ಕ್ರಿಯಗೊಳಿಸುವುದು

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` ಪ್ರಸ್ತುತ ವಿನಂತಿಗಾಗಿ ಬಿಟ್ಟುಬಿಡಬೇಕಾದ guardrail ಹೆಸರುಗಳ duplicate ತೆಗೆದುಹಾಕಿದ ಪಟ್ಟಿಯನ್ನು ಒಟ್ಟುಗೂಡಿಸುತ್ತದೆ. ಮೂಲಗಳು (ಎಲ್ಲವೂ ಐಚ್ಛಿಕ, ಎಲ್ಲವನ್ನೂ ವಿಲೀನಗೊಳಿಸಲಾಗುತ್ತದೆ):

- `apiKeyInfo.disabledGuardrails`
- ವಿನಂತಿಯ bodyಯಲ್ಲಿನ `disabledGuardrails` (top-level)
- ವಿನಂತಿಯ bodyಯಲ್ಲಿನ `metadata.disabledGuardrails`
- Header `x-omniroute-disabled-guardrails` (ಅಥವಾ ಹಳೆಯ
  `x-disabled-guardrails`)

ಮೌಲ್ಯಗಳು stringಗಳ array ಆಗಿರಬಹುದು ಅಥವಾ comma-separated string ಆಗಿರಬಹುದು; ಹೆಸರುಗಳನ್ನು lowercase kebab-caseಗೆ normalize ಮಾಡಲಾಗುತ್ತದೆ (`pii_masker` → `pii-masker`). ಫಲಿತಾಂಶವನ್ನು `context.disabledGuardrails` ಮೂಲಕ registryಗೆ ರವಾನಿಸಲಾಗುತ್ತದೆ, ಅದು ಹೊಂದಿಕೆಯಾಗುವ guardrailಗಳನ್ನು ಬಿಟ್ಟುಬಿಡುತ್ತದೆ (`results` ನಲ್ಲಿ `skipped: true`).

## ಕಾರ್ಯಗತಗೊಳಿಸುವ ಕ್ರಮ

`src/sse/handlers/chat.ts` ಮತ್ತು
`open-sse/handlers/chatCore.ts` ಮೂಲಕ ಹರಿಯುವ ಪ್ರತಿ ವಿನಂತಿಗಾಗಿ:

1. `resolveDisabledGuardrails(...)` API ಕೀ, ಬಾಡಿ ಮತ್ತು ಹೆಡರ್ಗಳಿಂದ ಬಿಟ್ಟುಬಿಡುವ ಪಟ್ಟಿಯನ್ನು ರಚಿಸುತ್ತದೆ.
2. `guardrailRegistry.runPreCallHooks(body, ctx)` ಗಾರ್ಡ್ರೇಲ್ಗಳನ್ನು ಆದ್ಯತೆಯ ಆರೋಹಣ ಕ್ರಮದಲ್ಲಿ ಚಲಾಯಿಸುತ್ತದೆ:
   - ನಿಷ್ಕ್ರಿಯಗೊಳಿಸಲಾದ ಗಾರ್ಡ್ರೇಲ್ಗಳನ್ನು `skipped` ಎಂದು ದಾಖಲಿಸಲಾಗುತ್ತದೆ.
   - ಪ್ರತಿ ಗಾರ್ಡ್ರೇಲ್ನ `preCall`, `modifiedPayload` ಮೂಲಕ ಪೇಲೋಡ್ ಅನ್ನು ಮರುಬರೆಯಬಹುದು.
   - ಮೊದಲ `block: true` ಸರಪಳಿಯನ್ನು ಅಲ್ಲಿಯೇ ನಿಲ್ಲಿಸುತ್ತದೆ ಮತ್ತು ಹ್ಯಾಂಡ್ಲರ್ ಗಾರ್ಡ್ರೇಲ್ ನಿರಾಕರಣೆಯ ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು ಹಿಂತಿರುಗಿಸುತ್ತದೆ.
3. (ಸಂಭಾವ್ಯವಾಗಿ ಮರುಬರೆಯಲಾದ) ಪೇಲೋಡ್ ಕಾಂಬೊ ರೂಟಿಂಗ್ ಮತ್ತು ಅಪ್ಸ್ಟ್ರೀಮ್ ಡಿಸ್ಪ್ಯಾಚ್ಗೆ ಹರಿಯುತ್ತದೆ.
4. ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು ಜೋಡಿಸಿದ ನಂತರ, `guardrailRegistry.runPostCallHooks(...)` ಪ್ರತಿಕ್ರಿಯೆಯ ಮೇಲೆ ಅದೇ ಸರಪಳಿಯನ್ನು ಚಲಾಯಿಸುತ್ತದೆ. ಇಲ್ಲಿ `block: true` ಅಪ್ಸ್ಟ್ರೀಮ್ ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು ಕೈಬಿಡುತ್ತದೆ.

ದೋಷ ಎಸೆಯುವ ಗಾರ್ಡ್ರೇಲ್ಗಳನ್ನು `error: <message>` ಜೊತೆಗೆ ದಾಖಲಿಸಲಾಗುತ್ತದೆ ಮತ್ತು
`logger.warn` ಮೂಲಕ ಲಾಗ್ ಮಾಡಲಾಗುತ್ತದೆ, ಆದರೆ ಸರಪಳಿ ಮುಂದುವರಿಯುತ್ತದೆ — ವಿನ್ಯಾಸದ ಪ್ರಕಾರ ದೋಷ ಸಂಭವಿಸಿದಾಗಲೂ ಅನುಮತಿಸಲಾಗುತ್ತದೆ.

## ಕಸ್ಟಮ್ ಗಾರ್ಡ್ರೈಲ್ಗಳು

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

ಹಂತಗಳು:

1. `BaseGuardrail` ಅನ್ನು ವಿಸ್ತರಿಸುವ `src/lib/guardrails/myGuardrail.ts` ಅನ್ನು ರಚಿಸಿ.
2. `preCall` ಮತ್ತು/ಅಥವಾ `postCall` ಅನ್ನು ಅನುಷ್ಠಾನಗೊಳಿಸಿ.
3. ಇಂಪೋರ್ಟ್ ಸಮಯದಲ್ಲಿಯೇ ನೋಂದಾಯಿಸಿ (`registerDefaultGuardrails` ನಿಂದ ಪುಶ್ ಮಾಡಿ) ಅಥವಾ
   ರನ್ಟೈಮ್ನಲ್ಲಿ `guardrailRegistry.register(...)` ಅನ್ನು ಕರೆ ಮಾಡಿ — ಅದೇ ಸಾಮಾನ್ಯೀಕರಿಸಿದ
   ಹೆಸರನ್ನು ಹೊಂದಿರುವ ಯಾವುದೇ ಹಿಂದಿನ ಗಾರ್ಡ್ರೈಲ್ ಅನ್ನು ರಿಜಿಸ್ಟ್ರಿ ಬದಲಿಸುತ್ತದೆ.
4. `tests/unit/` ಅಡಿಯಲ್ಲಿ ಪರೀಕ್ಷೆಗಳನ್ನು ಸೇರಿಸಿ (ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಉದಾಹರಣೆಗಳು:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`).

## ಪರೀಕ್ಷೆ

ತಿಳಿದಿರುವ ಸ್ಥಿತಿಯಿಂದ ಪ್ರಾರಂಭಿಸಲು ಪರೀಕ್ಷೆಗಳ ನಡುವೆ `resetGuardrailsForTests()` ಅನ್ನು ಬಳಸಿ.
ಖಾಲಿ ರಿಜಿಸ್ಟ್ರಿಯೊಂದಿಗೆ ಪ್ರಾರಂಭಿಸಲು `{ registerDefaults: false }` ಅನ್ನು ಪಾಸ್ ಮಾಡಿ ಮತ್ತು
ಪರೀಕ್ಷೆಯಲ್ಲಿರುವ ಗಾರ್ಡ್ರೈಲ್ಗಳನ್ನು ಮಾತ್ರ ನೋಂದಾಯಿಸಿ. Vision Bridge ಡಿಪೆಂಡೆನ್ಸಿ
ಇಂಜೆಕ್ಷನ್ ಅನ್ನು ಸ್ವೀಕರಿಸುತ್ತದೆ (`deps.getSettings`, `deps.callVisionModel`); Audio Bridge,
ಸೆಟ್ಟಿಂಗ್ಗಳು, ಸಾಮರ್ಥ್ಯಗಳು, STT ಮಾದರಿ ಆಯ್ಕೆ, ಕ್ರೆಡೆನ್ಶಿಯಲ್ ಪರಿಶೀಲನೆಗಳು ಮತ್ತು
ಟ್ರಾನ್ಸ್ಕ್ರಿಪ್ಷನ್ಗಾಗಿ ಸಮಾನವಾದ ಸೀಮ್ಗಳನ್ನು ಒದಗಿಸುತ್ತದೆ. ಆದ್ದರಿಂದ ಪರೀಕ್ಷೆಗಳು DB
ಅಥವಾ ನೆಟ್ವರ್ಕ್ ಪ್ರವೇಶವಿಲ್ಲದೆಯೇ ಎರಡೂ ಫ್ಲೋಗಳನ್ನು ಪರೀಕ್ಷಿಸಬಹುದು.

## ಇಂಜೆಕ್ಷನ್-ಗಾರ್ಡ್ ರೂಟ್ ವ್ಯಾಪ್ತಿ ಮತ್ತು ರೆಡ್-ಟೀಮ್ (ಹಂತ 8 · ಬ್ಲಾಕ್ D)

ಇಂಜೆಕ್ಷನ್-ಗಾರ್ಡ್ (`createInjectionGuard` / `withInjectionGuard`) ಬಳಕೆದಾರರ
ಪ್ರಾಂಪ್ಟ್ಗಳನ್ನು ಸ್ವೀಕರಿಸುವ ಎಲ್ಲಾ ರೂಟ್ಗಳನ್ನು ಒಳಗೊಳ್ಳುತ್ತದೆ. ಇದು `INJECTION_GUARD_MODE`
ಅನ್ನು ಗೌರವಿಸುತ್ತದೆ (ಡೀಫಾಲ್ಟ್ `warn` = ಲಾಗ್ ಮಾತ್ರ; `block` = HTTP 400 `SECURITY_001` ಅನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ).

| ಪ್ರಕಾರ                     | ರೂಟ್ಗಳು                                                                                                                                              | ಡೀಫಾಲ್ಟ್ ಮೋಡ್ |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------- |
| ಪಠ್ಯ (ಅಸ್ತಿತ್ವದಲ್ಲಿರುವುದು) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn          |
| ಜನರೇಟಿವ್                   | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn          |
| ಡೇಟಾ                       | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn          |

ಪಠ್ಯ ಹೊರತೆಗೆಯುವಿಕೆ (`extractMessageContents`) `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` ಅನ್ನು ಒಳಗೊಳ್ಳುತ್ತದೆ.

**ರೆಡ್-ಟೀಮ್ (ಪ್ರತಿ ರಾತ್ರಿ, `nightly-llm-security.yml`):** `INJECTION_GUARD_MODE=block`
ನಲ್ಲಿ ಪ್ರತಿಯೊಂದು ರೂಟ್, `OWASP-LLM` ಕಾರ್ಪಸ್ ಅನ್ನು ನಿರ್ಬಂಧಿಸುತ್ತದೆ ಎಂಬುದನ್ನು promptfoo
ಮೌಲ್ಯೀಕರಿಸುತ್ತದೆ; garak ಪ್ರೋಬ್ಗಳನ್ನು ಚಲಾಯಿಸುತ್ತದೆ (ಸೀಕ್ರೆಟ್ ಇಲ್ಲದಿದ್ದರೆ ಬಿಟ್ಟುಬಿಡುತ್ತದೆ).
ಸ್ಥಿರತೆಗಾಗಿ `moderations` ಅನ್ನು ಸೇರಿಸಲಾಗಿದೆ — ಬ್ಲಾಕ್-ಮೋಡ್ನಲ್ಲಿರುವ ಆಪರೇಟರ್ಗಳು
`resolveDisabledGuardrails` ಮೂಲಕ ಅದಕ್ಕೆ ವಿನಾಯಿತಿ ನೀಡಬಹುದು.

ಪ್ರತಿ ರಾತ್ರಿಯ ವರ್ಕ್ಫ್ಲೋ (`.github/workflows/nightly-llm-security.yml`, cron + ಮ್ಯಾನುಯಲ್
ಡಿಸ್ಪ್ಯಾಚ್) ಎರಡು ಜಾಬ್ಗಳನ್ನು ಹೊಂದಿದೆ:

- **`promptfoo-guard` (ನಿರ್ಬಂಧಿಸುವುದು)** — `INJECTION_GUARD_MODE=block` ಜೊತೆಗೆ
  `promptfoo eval -c promptfooconfig.yaml` ಅನ್ನು ಚಲಾಯಿಸುತ್ತದೆ. ಪ್ರತಿಯೊಂದು ಪ್ರತಿಕೂಲ
  ಪ್ರಕರಣವು (ಉದಾ. "ಹಿಂದಿನ ಎಲ್ಲಾ ಸೂಚನೆಗಳನ್ನು ನಿರ್ಲಕ್ಷಿಸಿ…", DAN-ಶೈಲಿಯ ಜೈಲ್ಬ್ರೇಕ್ಗಳು)
  ಪ್ರತಿಕ್ರಿಯೆಯು `error.code === "SECURITY_001"` ಅನ್ನು ಹೊಂದಿದೆ ಎಂದು ದೃಢೀಕರಿಸುತ್ತದೆ,
  ಅಂದರೆ ಗಾರ್ಡ್ ನಿಜವಾಗಿಯೂ ವಿನಂತಿಯನ್ನು ತಿರಸ್ಕರಿಸಿದೆ.
- **`garak` (ಸಲಹಾತ್ಮಕ)** — ಸ್ಥಳೀಯ OmniRoute ಇನ್ಸ್ಟನ್ಸ್
  (`http://localhost:20128/v1`) ವಿರುದ್ಧ garak `--probes promptinject,dan,leakreplay`
  ಅನ್ನು ಚಲಾಯಿಸುತ್ತದೆ. ಇದು ಪ್ರೊವೈಡರ್ ಸೀಕ್ರೆಟ್ (`PROMPTFOO_PROVIDER_KEY`) ಮೇಲೆ
  ಅವಲಂಬಿತವಾಗಿದೆ; ಸೀಕ್ರೆಟ್ ಇಲ್ಲದಿದ್ದರೆ ಸರಾಗವಾಗಿ ಬಿಟ್ಟುಬಿಡುತ್ತದೆ ಮತ್ತು `|| true`
  ಪ್ರತ್ಯಯವನ್ನು ಹೊಂದಿರುತ್ತದೆ, ಆದ್ದರಿಂದ CI ವಿಫಲಗೊಳಿಸದೆಯೇ ವರದಿ ಮಾಡುತ್ತದೆ.

ಗಾರ್ಡ್ ಹೆಲ್ಪರ್ನ (`createInjectionGuard` / `withInjectionGuard`) ವ್ಯಾಪ್ತಿಯು ಪ್ರಾಂಪ್ಟ್
ಹೊಂದಿರುವ ಪ್ರತಿಯೊಂದು `/v1` ರೂಟ್ಗೆ ವಿಸ್ತರಿಸುತ್ತದೆ; ಪ್ರಾಂಪ್ಟ್ ಪಠ್ಯವನ್ನು
`src/shared/utils/inputSanitizer.ts` ನಲ್ಲಿರುವ `extractMessageContents()` ಮೂಲಕ
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` ನಿಂದ
ಪಡೆಯಲಾಗುತ್ತದೆ.
