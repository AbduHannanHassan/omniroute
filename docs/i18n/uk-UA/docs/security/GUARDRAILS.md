> **Джерело істини:** `src/lib/guardrails/`
> **Останнє оновлення:** 2026-08-29 — v3.8.51 (Походження стенограми Video Bridge оголошується абонентом,
> ще не перевірено сервером — уточнено згідно з #11661)

Захисні механізми забезпечують безпеку, політику та трансформації вмісту на межі між OmniRoute та вищестоящими провайдерами. Кожен захисний механізм може перевіряти (та за бажанням відхиляти, трансформувати або анотувати) корисні навантаження запитів (`preCall`) та відповіді вищестоящих систем (`postCall`).

Система є **відкритою при збої**: якщо захисний механізм видає помилку під час виконання, реєстр записує помилку та продовжує роботу з наступним захисним механізмом, замість того, щоб відхиляти запит. Блокування є явним рішенням (`block: true`), а не випадковістю.

## Вбудовані захисні механізми

Реєстр автоматично завантажує шість захисних механізмів у порядку пріоритету під час імпорту
(див. `registry.ts` → `registerDefaultGuardrails()`):

| Пріоритет | Назва               | Стадія(ї)      | Файл                  |
| --------- | ------------------- | -------------- | --------------------- |
| `5`       | `vision-bridge`     | `preCall`      | `visionBridge.ts`     |
| `6`       | `audio-bridge`      | `preCall`      | `audioBridge.ts`      |
| `7`       | `video-bridge`      | `preCall`      | `videoBridge.ts`      |
| `10`      | `pii-masker`        | `pre` + `post` | `piiMasker.ts`        |
| `20`      | `prompt-injection`  | `preCall`      | `promptInjection.ts`  |
| `95`      | `credential-masker` | `pre` + `post` | `credentialMasker.ts` |

Механізми з нижчими номерами пріоритету виконуються **першими**.

### Vision Bridge (`visionBridge.ts`) — Міст модальностей PR-1

Перехоплює запити з зображеннями, спрямовані на **немодель зору**, і або
перенаправляє весь запит на модель, що підтримує зір, або замінює частини зображення
текстовими описами, створеними налаштовуваною моделлю зору, перед
викликом на upstream. Це дозволяє постачальникам, що працюють лише з текстом, прозоро обробляти
мультимодальні навантаження.

Процес:

1. Пропустити, якщо цільова модель вже підтримує зір (якщо тільки вона не входить до
   списку примусових мостів `isVisionBridgeForcedModel`).
2. Витягти частини зображення за допомогою `extractImageParts(messages)`
   (`visionBridgeHelpers.ts`), яка делегує до **уніфікованого медіа
   детектора** `detectMediaParts()` у `open-sse/utils/mediaParts.ts` — єдиного джерела
   істини, спільного з фільтром сумісності комбінацій.
   Витягнення дозволено лише для верхніх частин форм, які
   `replaceImageParts` може вставити назад (контракт extract↔replace): OpenAI
   `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL
   `source.type:"url"`, і Responses API `input_image`. Вкладені попадання та
   форми лише з індикаторами є матеріалом для фільтра комбінацій і ніколи не витягуються.
   Пропустити, якщо нічого не знайдено.
3. Визначити налаштування часу виконання за допомогою `resolveVisionBridgeRuntimeSettings()`
   (`src/shared/constants/modalityBridgeDefaults.ts`): нові ключі налаштувань `modalityBridge*`
   виграють; застарілі ключі `visionBridge*` залишаються **однократним
   резервним варіантом** (вікно відкату). Пропустити перед будь-яким проходженням медіа, коли
   міст вимкнено.
4. Вибір режиму (`modalityBridgeVisionMode`, див. таблицю нижче) вирішує
   перенаправлення чи опис. Перенаправлення повертає `modifiedPayload` з лише
   зміненим `model`, плюс мета `{ rerouted, fromModel, toModel, imagesKept }`.
5. Шлях опису: обмежити зображення до `maxImages`, скласти завдання-обізнаний запит,
   проконсультуватися з кешем опису, викликати модель зору **паралельно**
   (`Promise.allSettled`), і вставити текстові частини `[Image N]: <description>` на
   їх місце. Невдалий опис повертає `null`, і оригінальна частина зображення
   **зберігається** (#4012) — за винятком шляху опису комбінацій, коли кожен
   опис не вдався, де підтверджений не-зоряний upstream отримує
   `(unavailable — no vision-capable provider connected)` замість (#8430).
6. Повернути `modifiedPayload` + мета (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`).

#### Вибір режиму (`modalityBridgeVisionMode`)

| Режим      | За замовчуванням | Поведінка                                                                                                                                                                                                                                                                               |
| ---------- | ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔                | Спадкова евристика, не змінена (#6640/#7204): немоделі/`auto/` перенаправляються на найкращу модель зору, якщо оригінальна модель вже має придатні облікові дані (тоді опис); цілі комбінацій завжди описують.                                                                          |
| `describe` |                  | Завжди описувати — блок перенаправлення повністю пропускається; обрана користувачем модель завжди відповідає.                                                                                                                                                                           |
| `reroute`  |                  | Примусове перенаправлення: захист моделі з обліковими даними обходиться. Захист облікових даних для **цілі** перенаправлення все ще застосовується — коли не існує придатної цілі зору, запит переходить до опису, тому сирі зображення ніколи не досягають текстового бекенду (#8430). |

Примусові режими короткочасно **перед** запуском автоевристики; поведінка `auto`
є байтово ідентичною до захисного механізму до PR-1.

#### Завдання-обізнаний опис запиту (`modalityBridgeVisionTaskAware`)

За замовчуванням **true**. `composeVisionPrompt()` (`visionBridgeHelpers.ts`) додає
текст **останнього повідомлення користувача** (обрізаного до 500 символів) до базового
опису запиту, спрямовуючи опис на те, що насправді запитав користувач
(шаблон codex-vision-proxy) і просячи модель зору транскрибувати видимий
текст. Якщо прапор вимкнено — або немає тексту користувача — використовується незмінений базовий запит.

Опис запиту самопетлі, сумісного з OpenAI (`callVisionModelSingle()` в `visionBridgeHelpers.ts`), завжди запитує `image_url.detail: "high"` — безумовно, для кожного виклику/постачальника, не залежно від сигналу клієнта. Вибірка з низькою деталізацією погіршує точність OCR для саме тієї задачі транскрипції тексту, для якої запитує цей запит, тому виклик опису завжди запитує високу деталізацію, незалежно від того, який рівень деталізації використовувався в оригінальному вхідному запиті. Це впливає лише на внутрішнє тіло запиту опису; це не змінює те, як OmniRoute пересилає власне `image_url.detail` виклику в основному запиті — це значення за замовчуванням застосовується окремо, і лише для виявлених клієнтів OpenCode, в `defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`). Гілка формату передачі Anthropic для самопетлі опису не має поля `detail` і не підлягає жодному з цих значень за замовчуванням.

#### Обмеження виходу опису (`modalityBridgeVisionMaxChars`)

| Ключ                           | За замовчуванням | Діапазон          |
| ------------------------------ | ---------------- | ----------------- |
| `modalityBridgeVisionMaxChars` | `0`              | `0` або 100–50000 |

`0` (за замовчуванням) означає **без обмежень** — опис, повернутий `callVisionModel()`, передається без змін, зберігаючи існуючу поведінку. Будь-яке значення в діапазоні 100–50000 скорочує опис з суфіксом `…` перед тим, як його знову вставити як `[Image N]: <description>` (`VisionBridgeGuardrail.preCall()` в `src/lib/guardrails/visionBridge.ts`). Підвищте це для завдань OCR з великою деталізацією, де наступна модель потребує повної транскрипції; зменшіть його, щоб обмежити використання токенів на балакучих візуальних моделях. Поле інформаційної панелі знаходиться на вкладці Vision в розширеній панелі (`modality-bridge-max-chars` в `ModalityBridgeVisionTab.tsx`) і обмежує будь-яке значення між 1 і 99 до 100, залишаючи явне `0` незмінним — `0` є дійсним значенням Zod саме по собі (`z.union([z.literal(0), z.number().int().min(100).max(50000)])`), а не просто "не встановленим" значенням за замовчуванням.

#### Кеш опису (`modalityBridge/bridgeCache.ts`)

Кеш LRU + TTL в пам'яті для виходів опису, спільний для всього процесу. Ключ = `sha256(imageRef + composedPrompt + configuredBridgeModel)` з фреймуванням за довжиною префікса (без колізій межі полів). Компонент моделі є **налаштованою** моделлю мосту, а не моделлю, яка насправді відповіла — `callVisionModel` може внутрішньо повертатися до резервної моделі, і ключування за спробами фрагментувало б кеш. Неуспішні описи ніколи не кешуються. Налаштування:

| Ключ                            | За замовчуванням | Діапазон |
| ------------------------------- | ---------------- | -------- |
| `modalityBridgeCacheEnabled`    | `true`           | —        |
| `modalityBridgeCacheTtlMinutes` | `60`             | 1–1440   |
| `modalityBridgeCacheMaxEntries` | `200`            | 10–5000  |

#### Нормалізація віддалених зображень (самопетля опису/base64 отримання)

Коли міст отримує **віддалене** зображення самостійно — самозапит Anthropic опису та конвертація формату claude-wire в base64 (`ensureBase64ImagesForClaudeWire`), обидва через `fetchRemoteImageAsDataUri()` в `visionBridgeHelpers.ts` — отриманий URI даних проходить через `normalizeDataUri()` (`open-sse/utils/imageNormalize.ts`) перед тим, як бути вбудованим у запит моделі зору. Зображення, що перевищують розмір, зменшуються до **2048px довгої сторони** (відповідає обмеженню зміни розміру, яке OpenAI/Anthropic вже застосовують на сервері), що зменшує байти/затримку завантаження, не змінюючи те, що бачить модель зору. Зміна розміру використовує `sharp`, завантажений через динамічний імпорт: на платформі, де його рідний бінарний файл не вдається завантажити, `normalizeDataUri()` **ніколи не викидає** помилок — він повертається до передачі оригінальних байтів, тому шлях опису/конвертації base64 завжди залишається працездатним. Небайтові дані (отримання, яке не повернуло декодуване зображення) також передаються без змін. Ця нормалізація обмежена зображеннями, які міст отримує для свого власного самозапиту — вона ніколи не застосовується до сирого вантажу передачі виклику, відповідно до принципу мутації лише за згодою (Жорстке правило #20).

#### Схема налаштувань + міграція

Нові ключі `modalityBridge*` перевіряються Zod у `updateSettingsSchema` (`src/shared/validation/settingsSchemas.ts`): `modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`, `modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`, тріо `modalityBridgeCache*` та група `modalityBridgeAudio*`, що використовується Мостом Аудіо. Міграція `141_modality_bridge_settings.sql` копіює існуючі значення старої версії `visionBridge*` до відповідних нових ключів (ідемпотентно, ніколи не перезаписуючи значення `modalityBridge*`, встановлене оператором); старі ключі залишаються прийнятими як резервне читання протягом одного циклу випуску.

#### Заголовок прозорості + статистика

Відповіді, перетворені описом, містять `x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>` (створено `buildModalityBridgeHeader()` в `modalityBridge/bridgeStats.ts`, штамповано `withModalityBridgeHeader()` в `src/sse/handlers/chatHelpers.ts`). Перенаправлені запити не отримують **жодного** заголовка — вантаж залишався незмінним, і заміна моделі вже видна в полі `model` тіла відповіді.

`GET /api/modality-bridge/stats` (управлінська авторизація, той же рівень, що й `GET /api/settings`) повертає в пам'яті лічильники за модальностями `{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs, latencySamples, averageLatencyMs, lastUsedAt }` для `vision`, `audio` та `video`. `averageLatencyMs` використовує `latencySamples`, а не всі спроби, як свій знаменник; операція без вимірювання не створює зразок нульової мілісекунди. `bridged` залишається зворотно сумісним псевдонімом для успішних перетворень; невдалі спроби не збільшують його. Лічильники скидаються при перезапуску процесу за дизайном (телеметрія, а не облік).

#### Налаштування інформаційної панелі

Сторінка спеціалізованої панелі управління знаходиться за адресою
`/dashboard/settings/modality-bridge`. Її URL-адресовані вкладки `Vision`, `Audio`
та `Video` зберігають параметри запиту під час зміни значення `tab`.
Вкладка Vision надає можливості активації, режиму, вибору моделі (включаючи автоматичне
значення за замовчуванням), підказки, що враховують завдання, розширені обмеження
на таймаут/довжину зображення/опису/кеш, лічильники
виконання та захищений запит зразка. Вкладка Audio також активна: вона надає
можливості активації, вибір моделі лише для STT з Auto, обмеження таймауту/максимальної
дліни кліпу, лічильники аудіо та тест зразка `input_audio`. Вкладка Video є функціональною: вона повідомляє
про стан виконання FFmpeg/ffprobe — один з чотирьох явних станів UI (`unknown`, коли
пробник у процесі або не зміг завершити, `restricted` на хості панелі управління, що не є
петлею, де пробник пропускається на стороні клієнта, `unavailable`, коли пробник
проведений і підтверджено, що відсутній, або `available` з версіями FFmpeg/ffprobe) — зберігає
обмеження на активацію/модель/кадр/відео/таймаут, фільтрує вибір моделі до моделей,
які підтримують зір, та надає лічильники відео.

Колишня картка Vision Bridge у налаштуваннях AI є посиланням на
нову сторінку; вона більше не має другої копії форми. Постачальники медіа також
посилають робочі процеси Image-to-Text та Speech-to-Text до відповідних вкладок Modality
Bridge, не видаляючи існуючий майданчик Speech-to-Text.

**Обхід допуску самопетлі:** коли виклик опису проходить через власну
самопетлю OmniRoute `/v1` (нестандартна модель постачальника), підзапит надсилає
`x-omniroute-admission-bypass: internal` і аутентифікується з використанням
вирішеної облікової інформації самопетлі — локальний `sk_omniroute` у локальному режимі або
конфігурований оператором ключ `OMNIROUTE_API_KEY` / `ROUTER_API_KEY` (#1350), щоб
впровадження з `REQUIRE_API_KEY=true` все ще могли виконувати виклик опису. Обхід
вшановується лише для цих точних облікових даних, тому зовнішні клієнти не можуть
використовувати заголовок для пропуску допуску.

Спадкові значення зберігаються в `src/shared/constants/visionBridgeDefaults.ts`; нові
значення за замовчуванням для режиму/завдання/кешу та резолвер налаштувань
зберігаються в `src/shared/constants/modalityBridgeDefaults.ts`. Захисна смуга надає
опцію конструктора `deps`, щоб тести могли впроваджувати підроблені реалізації
`getSettings` та `callVisionModel`.

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

Перехоплює запити чату з аудіо до того, як вони досягнуть цілі, яка не
відомо, що приймає аудіо-вхід. Він ніколи не перенаправляє запит чату: аудіо-частини
транскрибуються через існуючу точку входу multipart, сумісну з OpenAI, і
обраний чат-модель продовжує з текстовими транскрипціями.

Процес:

1. Визначте `supportsAudio` через `getResolvedModelCapabilities()`. Явні
   метадані реєстру постачальників переважають, потім статичні метадані моделі, потім
   синхронізовані `modalities_input`. Заявлений список входів без `audio` є `false`; жодних
   доказів можливостей залишається `null`. Як `false`, так і `null` активують
   консервативний міст, тоді як `true` обходить його.
2. Визначте налаштування `modalityBridgeAudio*` та витягніть сплітовані верхні
   аудіо-частини з кожного повідомлення через спільний детектор `detectMediaParts()`.
   Підтримувані форми проводів — це OpenAI `input_audio`, `audio_url` та
   `source.media_type: "audio/*"`. Вкладене аудіо виявляється для маршрутизації, але не
   видаляється спліт-процесом. Робота обмежена `modalityBridgeAudioMaxClips`;
   пізні частини залишаються незайманими.
3. Вшануйте налаштований `provider/model`, або дозвольте `selectAudioBridgeModel()`
   пройти через `AUDIO_TRANSCRIPTION_PROVIDERS` у стабільному порядку каталогу та вибрати першу
   модель з використаною активною обліковою інформацією постачальника.
4. `callAudioTranscription()` перетворює аудіо base64/data-URI на multipart
   `file`, або завантажує віддалений `audio_url` через публічний лише вихідний
   захист з прив'язкою DNS та обмеженням у 25 МБ. Потім він POST-ить файл і обрану
   модель до локальної самопетлі `/v1/audio/transcriptions`, аутентифікованої з
   `resolveSelfLoopBearer()`. Існуючий маршрут транскрипції виконує звичайний
   пошук облікових даних, обробку охолодження/обмеження швидкості та відправку постачальника.
5. Успішні виклики замінюють свої частини на `[Audio N]: <transcript>`. Виклики
   виконуються з `Promise.allSettled`: індивідуальна помилка зберігає ту оригінальну
   аудіо-частину (#4012 контракт). Якщо кожен виклик зазнає невдачі, і ціль
   доведено, що `supportsAudio === false`, частини стають
   `[Audio N]: (недоступно — жодного STT постачальника не підключено)` (#8430 контракт). Для
   невідомої цілі (`null`) результат з усіма невдачами залишається незайманим. Доведена
   ціль лише з текстом без використаної STT облікової інформації отримує той же явний
   шаблон без виконання мережевого виклику.

Успішні транскрипції використовують кеш Modality Bridge з LRU/TTL на рівні процесу. Ключ
поєднує аудіо-референс, стабільну мітку операції `audio-transcription` та обрану STT модель; невдачі
ніколи не кешуються. Аудіо-спроби оновлюють спільні лічильники `bridged`, `cacheHits`, `failures`
та `lastUsedAt`.
Перетворені відповіді несуть
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>`; незаймані
запити не отримують сегмент Audio Bridge.

Налаштування виконання підтримуються базою даних та перевіряються Zod:

| Ключ                          | Значення за замовчуванням | Діапазон        |
| ----------------------------- | ------------------------- | --------------- |
| `modalityBridgeAudioEnabled`  | `true`                    | —               |
| `modalityBridgeAudioModel`    | `""`                      | Auto або STT ID |
| `modalityBridgeAudioTimeout`  | `60000`                   | 1000–300000     |
| `modalityBridgeAudioMaxClips` | `3`                       | 1–10            |

Спільний кеш залишається під контролем `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes` та `modalityBridgeCacheMaxEntries`.

### Video Bridge (`videoBridge.ts`, `videoBridgePipeline.ts`)

Перехоплює верхні частини відео в Chat Completions `messages` та Responses API `input` перед викликом цілі, для якої не відома нативна підтримка відео. Підтримувані формати: `input_video`, `video_url`, `video_source`, HTTPS URL, та `data:video/*;base64,...` data URI. Звичайні імена файлів у тексті не розглядаються як відео.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) відповідає за проходження запиту, перевірку можливостей/політики, агрегацію за запитом та корисне навантаження відповіді. Робота з відео — отримання, кешування всіх результатів, опис послідовності кадрів (яка об'єднує будь-який аудіо транскрипт, оголошений викликом), та метрики/скасування/очищення за спробу — прихована за `processVideoPart` у `videoBridgePipeline.ts`, яка викликається один раз для кожної частини відео в циклі `preCall`. Цей модуль також визначає явні межі портів `VideoMediaBrokerPort` (отримання байтів та витягування зразків кадрів), `VideoAudioTranscriptionPort` (об'єднання аудіо транскрипту, оголошеного викликом, з зразковими підписами) та `VideoDrilldownPort` (спадковий формат сирого зберігання). Продукційний STT та збереження кадрів формуються навколо описового порту через `createVideoSttAdapter` та `createVideoDrilldownAdapter`; останній використовує спільний непрозорий цикл життя.

Публічний шлях запиту `/v1` ніколи не імпортує або викликає підпроцес. Віддалені відео завантажуються з обмеженням у 50 MiB; вбудовані base64 відео мають консервативний ліміт у 36 MiB декодованого розміру на відео, щоб модель/повідомлення/обгортка залишалися в межах публічного ліміту запиту JSON у 50 MiB. Оцінки довжини вбудованих та декодованого розміру перевіряються перед виділенням. HTTPS є обов'язковим для початкового віддаленого URL та кожного перенаправлення, використовуючи існуючий публічний лише вихідний захист з прив'язкою DNS. Байти потім перетинають точну внутрішню межу брокера `POST /api/modality-bridge/video/extract`. Цей маршрут є як `LOCAL_ONLY`, так і `SPAWN_CAPABLE`, приймає лише аутентифікований запит з довіреного зворотного зв'язку за процесом і ніколи не приймає URL, шлях до файлової системи, виконуваний файл або список аргументів. Конвеєр розміру тіла API та інкрементальний читач тіла обробника незалежно забезпечують обмеження на вхід брокера у 50 MiB. Його обмежена черга виконує одне витягування за раз, дозволяє чотири очікуючі завдання та обмежує очікуючий вхід до 100 MiB.

Всередині брокера `ffprobe` читає приватний локальний файл; фіксований формат дозволів виключає плейлисти та формати маніфестів. Для дозволених контейнерів MOV-сімейства зовнішні посилання на дані MOV за замовчуванням залишаються вимкненими, і фіксована команда не підключається до них. Як `ffprobe`, так і `ffmpeg` використовують лише протокол `file` у білому списку, один потік, фіксовані масиви аргументів, без оболонки та виконувані файли, які вирішуються з `PATH`. Потоки з обкладинками з прикріпленими зображеннями не є відтворювальними кандидатами. Усі відтворювальні потоки повинні відповідати обмеженням, і явний стандартний потік віддається перевага перед детермінованим найнижчим індексом резерву. Відео обмежені до 600 секунд, 8192 пікселів за виміром та 33,554,432 пікселів джерела. FFmpeg зразки 1–16 середніх JPEG кадрів, зменшує довгу сторону до максимуму 1024 пікселів без збільшення менших вхідних даних і ніколи не отримує URL. Вибірка є `uniform` за замовчуванням. Додаткові опції `scene_aware` та експериментальна `segment_aware` політики виконують один додатковий фіксований прохід FFmpeg над вже перевіреним локальним потоком, вибирають обмежені `showinfo` часові мітки сцен і детерміновано повертаються до тих же рівномірних середніх точок у разі збою детектора, тайм-ауту, неправильної виходу або порожнього набору кандидатів. Режим, обізнаний про сегменти, виділяє зразки середніх точок пропорційно до перевірених інтервалів сцен; докази, обізнані про сегменти, та поведінка резерву детально описані нижче. Жорстке обмеження у 16 кадрів застосовується після вибору в кожній політиці. Коли запит, обізнаний про сцену, має лише бюджет у один кадр, він використовує рівномірну середню точку активного повного відео або фокусного вікна та повідомляє `policyEffective: uniform`: один вибраний кадр сцени не може зберегти обидва тимчасові кінці. Виклик може за бажанням надати скінченне фокусне вікно (`start`/`end` секунди); межі обмежуються тривалістю медіа, перевернуті або нескінченні вікна відхиляються, і всі політики вибірки виконуються лише всередині нормалізованого інтервалу. Отримане вікно включається в метадані вибірки та в ненадійний префікс опису, щоб подальші моделі могли відрізнити фокусований уривок від повної хронології.

Семантичний фокус підпису є окремим, явним налаштуванням. Режим аналізу за замовчуванням `full` зберігає існуючий запит кадру та ніколи не пересилає текст запиту до моделі підпису. У режимі `focused` місток читає лише останній непорожній текст, написаний користувачем, з того ж контейнера Chat або Responses, нормалізує його до NFC, зменшує контрольні символи та пробіли, і обмежує до 500 кодових точок Unicode. Порожній результат повертається до точного запиту `full`. Використовуваний підказка серіалізується як JSON у спеціальному блоці ненадійного користувача та може лише пріоритизувати спостережувані деталі; вона не може переважити окреме попередження проти дотримання інструкцій, видимих або чутних у медіа. Текстовий фокус ніколи не виводить `start`/`end` або не змінює тимчасовий вибірник.

#### FU-07 структурні сегменти доказів

`segment_aware` використовує один обмежений попередній аналіз над вже перевіреним локальним відеопотоком. Фіксований фільтровий ланцюг спочатку масштабує до максимуму 320 пікселів у ширину, виявляє зміни сцен і заморожені інтервали, а потім зразки з 1 кадру на секунду для розмиття, середньої яскравості та просторової/тимчасової інформації. Прохід обмежений 600 структурними зразками, одним потоком FFmpeg/фільтра, тими ж дозволами протоколу та контейнера `file`-only, обмеженням виходу процесу у 1 MiB та максимум 30 секундами всередині спільного скасування/термінації брокера. Він ніколи не приймає команду, фільтр, шлях або URL з запиту.

Структурні значення є детермінованими доказами вибірки, а не семантичним розумінням відео. Вони не виводять суб'єкти, дії, підписи, мову чи наміри користувача. Межі сцен і заморожування формують сегменти; покриття заморожування, розмиття, експозиція, просторові деталі та тимчасові зміни лише впливають на те, як існуючий бюджет у 1–16 кадрів розподіляється. Повністю заморожений сегмент обмежений одним кадром, тоді як незаморожені сегменти конкурують за залишковий бюджет. Коли межі перевищують кількість кадрів, зберігається рівномірне покриття хронології, тому швидкі ранні різання не можуть приховати довгий сегмент. Межі сцен у межах 1-секундної роздільної здатності аналізу межі заморожування об'єднуються.

Відсутні фільтри, неправильно сформовані/порожні докази, помилка детектора або обмежений тайм-аут попереднього аналізу не проходять відкритими до точної рівномірної політики середини. Відмова виклику або термін брокера не проходять відкритими: це завершує процес, що виконується, запобігає подальшому витягуванню кадрів, а приватне тимчасове дерево видаляється в `finally`.

`scripts/perf/video-bridge-fu07-eval.ts` генерує детерміновані реальні FFmpeg фікстури для економії після дедуплікації підписів, розподілу бюджету щільного руху, доказів розмиття/експозиції/SI-TI, швидких різань з довгим хвостом і помилок поступового зникнення. Він записує час стіни попереднього аналізу і, де доступно `/usr/bin/time`, дитячий CPU та піковий RSS. Його перевірки якості є структурними оракулами. Реальна якість моделі підписів залишається `HOLD`, оскільки цей пристрій не має авторизованої кінцевої точки або замороженого судді. Грошова економія також залишається `HOLD`, якщо `--caption-cost-per-call-usd` не надає явну позитивну оцінку за виклик; скрипт ніколи не вигадує жодного з результатів.

Кожен кадр обмежений 4 MiB, всі сирі кадри разом до 23 MiB, а серіалізований відповідь брокера до 32 MiB. Приватний тимчасовий каталог видаляється в `finally`. OmniRoute не пакує FFmpeg і не приймає користувацький шлях до виконуваного файлу. Перед підписуванням місток застосовує обережний візуальний дедуплікаційний прохід: кожен JPEG зменшується до 16×16 градацій сірого і порівнюється лише з останнім збереженим кадром. Для запитуваного бюджету підписів вище одного кадру, витягування постачає обмежений пул кандидатів до двох бюджетів і ніколи більше 16 кадрів. Запитуваний ліміт застосовується лише після дедуплікації, при цьому перші та останні обрані кандидати зберігаються під час остаточного звуження, коли бюджет становить щонайменше два. Версійна політика `grayscale-16x16-mean-cells-v2` використовує більше з середнього лума дельта та співвідношення клітин ескізів, чий нормалізований дельта становить щонайменше 0.05. Поріг дублікатів є сталою 0.04, обраною для передбачуваності, а не виставленою як налаштування під час виконання. Цей вторинний сигнал з високим контрастом зберігає невеликий рух і зміни видимого тексту, які можуть бути приховані лише порівнянням середнього. Помилки компаратора або декодера проходять відкритими і зберігають покриття. Вихідні метадані розділяють витягнуті кандидати, успішно використані кадри та візуальні дублікатів, які були відкинуті.

Явно позначена частина відео може запитувати таймстампований контактний лист. Місток будує максимум 4-колонну, 16-кадрову JPEG сітку. Кожна клітинка розміром 512 пікселів вбудовує свій таймстамп у висококонтрастну нижню смугу, тоді як ті ж таймстампи залишаються в текстових метаданих для подальшої асоціації та аудиту. Повний JPEG залишається обмеженим до 32 MiB. Якщо `sharp` не може декодувати або скласти сітку, місток повертається до окремих JPEG кадрів; відмова клієнта все ще поширюється через операцію листа.

Докази просування навмисно відокремлені від синтетичного складання мікробенчмарку. `scripts/perf/video-bridge-contact-sheet-eval.ts` визначає схему-версію A/B для реальних моделей зору, сумісних з OpenAI. Він вимірює токени, повідомлені постачальником, затримку стіни від початку до кінця (включаючи складання листа), кількість викликів моделі та збереження фактів, визначених у маніфесті. Сирі відповіді моделі не записуються в звіт; зберігаються лише SHA-256 дайджести та відповідні ID фактів. Пристрій не робить жодного мережевого або платного виклику моделі, якщо не передано `--execute-real` і не налаштовано `--model`, `OMNIROUTE_BASE_URL` та `OMNIROUTE_API_KEY`. Без цього явного реального запуску його машинозчитуваний вердикт залишається `HOLD`; вимірювання синтетичного навантаження/кількості викликів самі по собі не є доказом просування.

Окремий `scripts/perf/video-bridge-promotion-eval.ts` споживає спостереження FU-07 або FU-09. Для прийняття просування потрібні всі вісім синтетичних сценаріїв плюс очищений реальний кліп, щонайменше три виміряні повторення на роль і випадок, всі десять оголошених метрик, дайджести заморожених медіа/підказок/очікуваних фактів/налаштувань, унікальні ID спостережень та перевірений послідовний порядок A/B. Квиток виконання зв'язує дайджест корпусу, точний кандидат SHA та ревізію моделі. Відсутні або недійсні вимірювання залишаються `HOLD`, включаючи CPU понад 30 с, піковий RSS понад 512 MiB або попередній аналіз понад 30 с. Це обмеження на прийняття доказів, а не нова гарантія виконання RSS під час виконання.

FU-07 вимагає щонайменше 98% збереження якості та p95 затримки не більше 1.2x базового рівня, плюс або 0.05 абсолютне покращення середнього відгуку, збалансованого за випадками, при еквівалентних середніх викликах підписів, або щонайменше 10% менше середніх викликів підписів після дедуплікації. FU-09 вимагає щонайменше 0.85 якості, 95% збереження, 20% зменшення p95 затримки та 10% зменшення токенів. Втрата критичних фактів, відповідність ін'єкцій або відсутнє використання заважають просуванню. Одне виконання не може просунути нічого: `--previous-report` підтверджує два різні, неперекриваючі, послідовно допустимі виконання однієї й тієї ж політики/ревізії моделі/кандидата/корпусу. Експеримент вибірки не може підтвердити експеримент контактного листа.

Збирачі повинні оцінювати відповіді в пам'яті та зберігати `responseDigest` разом з метриками та прив'язками спостережень, ніколи не зберігаючи текст відповіді. Споживач також читає старі сирі спостереження, але ніколи не копіює цей текст у свої звіти. Приймається лише один з `responseDigest` або `rawResponseText` для кожного спостереження. Версійний дозволений список залишається порожнім з незмінним значенням за замовчуванням `hold`. Для допустимого запису потрібні його посилання на докази, політику, ревізію моделі, точний SHA кандидата, дайджест маніфесту та два різні ідентифікатори запуску; конфліктуючі контексти відхиляються. Ці метадані є контрактом аудиту, а не доказом того, що посиланий файл містить справжні вимірювання. Перегляньте фактичні квитанції перед додаванням будь-якого запису. Кінцевий пункт статистики управління та панель відео демонструють консервативну готовність. Конфігурований псевдонім моделі сам по собі не встановлює її ревізію або SHA працюючого кандидата, тому поточна панель звітує `HOLD`, а не повторно використовує допустимість з іншого контексту виконання. Явний експериментальний вибір залишається окремим від просування; жодне значення за замовчуванням автоматично не змінюється.

Викликачі можуть прикріпити необов'язковий масив `transcript.cues` до підтримуваної частини відео, коли вони вже мають узгоджений текст. Кожен сигнал повинен містити `text`, скінченний інтервал `start`/`end` всередині перевіреної тривалості та дозволене `source` (`client`, `embedded` або `audio-bridge`); `confidence` за замовчуванням дорівнює `1` і повинен залишатися між `0` та `1`. Точні дублікати сигналів об'єднуються. OmniRoute ніколи не починає транскрипцію з цих метаданих: перевірені сигнали копіюються у описаний результат з джерелом, впевненістю та інтервалом і відображаються як ненадійні спостереження поряд з підписами кадрів. Неправильний, поза межами або безпосередньо отриманий текст відхиляється, а не змішується в потік підписів. Обидва канали транскрипції тіла запиту нормалізують надане походження до `client`, включаючи самостійно заявлені мітки `embedded` або `audio-bridge`. Тільки адаптер, що належить серверу, може призначити ці надійні мітки через аргумент `trustedSource`, що містить лише код; поле JSON запиту не може досягти цього аргументу. Текст транскрипції залишається ненадійним медіа-отриманим контентом, незалежно від його походження, і ніколи не повинен визначати авторизацію.

Розширений викликач може надати трек `audioTranscript` для того ж відео; він розглядається як текст, наданий клієнтом, а не доказ транскрипції сервера. Шов злиття запускає візуальні та аудіоспостереження під одним терміном і сигналом про скасування, розташовує їх на спільній часовій шкалі, об'єднує точні дублікати та звітує про частковий результат, коли лише одна сторона успішна. Неправильний `audioTranscript` знижується до цього часткового результату — візуальний опис зберігається, а аудіогілка записує очищений код помилки — замість того, щоб провалити все відео. Доступність за гілками, частковий прапорець та очищені коди помилок зберігаються в описаному результаті, у метаданих захисних бар'єрів (`audioFusionRuns`/`audioFusionPartials`/`audioFusionFailureCodes`), у метаданих кешу результатів та у лічильниках злиття моста. Шлях за замовчуванням Video Bridge не викликає перетворення мови в текст або не завантажує другу копію медіа; без цього явного треку він залишається лише відео.

**Збереження транскрипції (#12150 P1).** Це застосовується автоматично щоразу, коли Video Bridge (сам по собі за бажанням) відображає сигнал транскрипції — немає окремого прапорця збереження. Коли запит відображає будь-який сигнал транскрипції (оголошений викликачем `transcript` або злитий `audioTranscript`), захисний бар'єр позначає його як `videoBridgeObserved` і створює редаговану тінь відеоопису — ідентичне відображення, в якому кожен сигнал вільного тексту замінюється на `[redacted-video-transcript]`, створене шляхом заміни структурованого поля сигналу перед складанням рядка (ніколи не шляхом парсингу сплющеного тексту, тому жоден вміст сигналу — ворожий чи звичайний, включаючи тіла, що містять `]`, такі як `[inaudible]`/`[music]` — не може вижити). Збережене тіло запиту журналу викликів замінює кожну частину тексту, отриману з відео, на цю редаговану тінь, відповідно до рівності вмісту; якорь `fullText` знову читається з завершеного вантажу захисного бар'єра перед викликом, тому збіг все ще успішний після пізніших захисних бар'єрів (маскувальники PII та облікових даних, пріоритети 10/95) переписують текст опису на місці і після системного запиту/передачі/ін'єкції пам'яті формують масив повідомлень. Тіло, надіслане вгору до моделі, залишається незмінним. Спостережуваний запит також не заповнює жодної постійної пам'яті (обидва витягування, отримані з запиту та відповіді, пропускаються), тому відповідь моделі не може повторити текст транскрипції в пам'яті.

**Сирі відеополя (#12430).** Коли місток увімкнено, а підтримка рідного відео невідома або відсутня, визначені поля `transcript`/`audioTranscript` також активують `videoBridgeObserved`, навіть після невдачі опису або обмеження `maxVideos`. `null` та порожні рядки враховуються; відсутні поля та невідеометадані не враховуються. Збережені копії редагують ці поля або пропускають запит, а кеші/пам'ять обходяться. Вантаж постачальника залишається незмінним.

Додаткові збережені копії використовують той же сигнал спостережуваного запиту. Сирий знімок запиту клієнта перед захисним бар'єром, запит, що чекає в пам'яті, та журнал раніше відхиленого запиту структурно замінюють поля транскрипції у відеочастинах; рядкові запити, синтезовані етапами конвеєра та передачею контексту, редагуються на місці збереженого тіла запиту. Збережений маркер `video_content_removed` змушує продовження `previous_response_id` завершитися закритим, а не відновлювати текст, який був навмисно відкинутий. Якщо спостережуваний запит втрачає свою тінь редагування перед журналом, або навіть один з кількох відео-тіней не відповідає після пізніших мутацій запиту, збережене тіло запиту повністю пропускається замість того, щоб зберігати частково редаговану транскрипцію.

Для спостереженого запиту відповідь моделі може цитувати будь-яку частину транскрипту без структурної межі підказки. Тому його збережений журнал викликів `responseBody` замінюється маркером пропуску; детальний артефакт конвеєра (який може включати в себе тіла upstream/клієнта та частини потоку) не зберігається. Семантичні, ідемпотентні та кеші повторного розуміння обходять читання та запис для цього запиту. Запит постачальника та видима клієнтом відповідь залишаються незмінними. Ранні байти keepalive видаляються з тимчасового буфера, коли детальний артефакт пропускається. Попередження Kiro про неправильно сформований EventStream повідомляє лише про кількість байтів корисного навантаження, ніколи не про його вміст або сирий помилку парсера JSON. Це не стверджує, що кожна не пов'язана діагностика постачальника/плагіна була перевірена; ширший моніторинг збережених зливів відстежується в #11658.

Внутрішній життєвий цикл `/api/modality-bridge/video/drilldown` є окремим, замкнутим/токен-аутентифікованим кешем. Кожна операція також вимагає канонічного непрозорого ідентифікатора принципала. Перед тим, як виклик виробництва буде активовано, він повинен отримати цей ідентифікатор з аутентифікованого орендаря і ніколи не повинен пересилати значення, вибране клієнтом. Ключі кешу пов'язують цього принципала з канонічними ідентифікаторами сесії та відео, зберігають лише їх ключі, отримані з SHA-256, і обмежують як читання, так і видалення до одного й того ж принципала. Кеш зберігає не більше 16 отриманих JPEG кадрів на запис, термін дії яких закінчується через десять хвилин, і підтримує обмежені читання `start`/`end` або явне видалення сесії.

Кожен принципал обмежений 16 записами та 64 MiB канонічних JPEG даних. Ці обмеження незалежні від глобального ліміту в 64 записи/256 MiB: тиск на квоту принципала видаляє лише найменш використовувані записи цього принципала перед тим, як розглядати глобальне видалення LRU. Прострочені записи видаляються як з обліку принципала, так і з глобального обліку під час активності кешу, тоді як скасування та невдача валідації не фіксують часткову заміну.

Кеш відхиляє неконанічний Base64, надмірне заповнення, не-JPEG медіа, неправильно сформовані або обрізані JPEG, а також JPEG, які викликають попередження під час обмеженого повного зображення `sharp` декодування. Він повторно кодує кожне прийняте зображення як канонічний JPEG, отримує ширину та висоту з декодованих байтів замість того, щоб довіряти полям виклику, і відкидає будь-які залишкові байти поліглота, а не зберігає їх. Лише обмежений канонічний стиснутий буфер зараховується до обох квот. Ліміт JSON по проводах включає накладні витрати Base64 для стелі декодованого вводу в 32 MiB. Кожне збережене похідне записує свій перевірений формат/роздільну здатність JPEG, політику вибірки, версію похідного, час створення, хеш вмісту, обчислений сервером, та хеш батьківського посилання плюс хеш вмісту батьківського виклику. Скасування перевіряється між асинхронними фазами декодування/хешування перед атомарним комітом кешу.

Виробник продукції повторно використовує вже отримані кадри брокера лише після успішного візуального аналізу, без повторного завантаження/екстракції відео. Він вимагає оператора `modalityBridgeVideoDrilldownEnabled=true`, строгого перетворення `drilldown: true` для кожної частини та аутентифікованого запису ID API-ключа. Значення принципала/сесії, оголошені клієнтом, ніколи не встановлюють право власності. Без усіх трьох умов він не хешує, не змінює розмір або не зберігає додаткові кадри. Невдача збереження зберігає придатну візуальну відповідь. Запити з дозволом обходять кеш результатів всього відео, тому кешовані результати ніколи не повторюють обробники.

Успішні відповіді JSON та SSE відкривають не більше чотирьох непрозорих обробників у обмеженому заголовку `x-omniroute-video-drilldown`. Авторизовані браузерні джерела можуть читати цей заголовок без розширення політики CORS. Нові обробники використовують `v1.<32-byte random base64url token>`, а реєстр зберігає лише їх SHA-256 хеші. Читач/парсер заголовків також приймає старі 64-шестигранні токени. Аутентифікований публічний споживач — це `GET /api/v1/video-bridge/drilldown?handle=...`, незалежно контролюється `modalityBridgeVideoDrilldownRemoteEnabled=true`. Явне збережене значення false відкликає доступ, навіть коли активовано спадкове значення `OMNIROUTE_VIDEO_BRIDGE_DRILLDOWN_REMOTE_ENABLED`. Збереження продукції має аналогічне спадкове значення `OMNIROUTE_VIDEO_BRIDGE_DRILLDOWN_ENABLED`. Обидва спадкові значення за замовчуванням вимкнені.

Споживач отримує право власності з аутентифікованого ключа, застосовує політику ключа та повертає однаковий 404 для невідомих, прострочених та обробників іншого ключа. Він приймає `variant=preview|standard|detail` (максимальний розмір JPEG 320/640/1280, ніколи не збільшується), `limit=1..8` (або спадковий псевдонім `frames`, ніколи не обидва), нульовий `page` та необов'язкові `start`/`end` фокус-секунди. Дублікати ключів запиту та перевернуті фокусні вікна відхиляються. Кожен повернений варіант має хеш свого фактичного вмісту та метадані фактичної роздільної здатності, пов'язані з збереженим джерелом. Варіанти отримуються під час читання, а не зберігаються як додаткові збережені копії. Відповідь JSON, включаючи Base64/конверт, обмежена 32 MiB; надмірна сторінка повертає 413, і клієнт повинен запитати менше кадрів. Читання перевіряє скасування навколо кожного зміни розміру та повторно перевіряє дійсність обробника перед поверненням. `DELETE` власником є ідемпотентним; видалення або закінчення терміну дії звільняє збережене джерело та облік використання.

Спільне сховище є локальним для процесу: обробники закінчуються при перезапуску і не можуть бути передані між незалежними процесами OmniRoute. Статистика управління відкриває ефективну політику збереження/віддаленого доступу та агрегує лише збережені записи/байти, ніколи медіа, посилання, ідентифікатори принципалів або обробники. Панель налаштувань відео показує ці значення і може зберігати обидва перемикачі згоди. Ця документація з реалізації не є доказом живого розгортання або просування; прийняття реальної моделі відстежується окремо.

Фрейми підписуються послідовно з налаштованою моделлю Відео. Порожнє
перевизначення Відео успадковує налаштування Зору; якщо обидва порожні, автоматичний маршрутизатор Зору вибирає ефективну модель, що підтримує зір. Успішні підписи замінюють оригінальну частину стабільним префіксом `[Video description:`, який також позначає текст як ненадійне спостереження, отримане з медіа, і вказує подальшим моделям не слідувати інструкціям, знайденим у медіа. Ключі кешу підписів фреймів включають байти JPEG, запит, мітку часу та ефективну модель; лише успішні підписи кешуються. Записи кешу зберігають фактичну успішну модель виробника, включаючи резервну модель; місток повідомляє `mixed`, коли різні фрейми були створені різними моделями. Успішний кеш повторно використовує цю ідентичність виробника замість того, щоб переназивати її як запланований маршрут. Кеш результатів для всього відео ключується на кожному вході, який змінює вихід — запит, ефективну модель, політику вибірки, кількість фреймів, режим семантичного аналізу, SHA-256 відбиток нормалізованого підказки фокусу, вікно фокусу, `transcript`,
`audioTranscript` та прапорець контактної таблиці — тому зміна будь-якого з цих вимірів є промахом кешу, ніколи не є застарілим повторним використанням. Версія політики візуального дублікату, поріг та обмежена кількість кандидатних фреймів також є явними в ключі кешу результатів та метаданих; зміна політики, отже, не може повторно використовувати застарілий опис всього відео. Метадані кешу результатів v4 зберігають режим та відбиток, ніколи не сировинне завдання користувача. Метадані захисних бар'єрів повідомляють як запитувані, так і ефективні режими аналізу; запитуваний режим `focused` без придатного тексту користувача повідомляється як ефективно `full`.

Захисний бар'єр витягує кожну підтримувану частину відео, але описує не більше ніж `modalityBridgeVideoMaxVideos`. Для цілі, доведеної до того, що `supportsVideo === false`, невдалі та надмірні відео стають явними безпечними текстовими маркерами, тому жодне сировинне відео не зберігається. Коли можливості невідомі, ці частини залишаються недоторканими. Цілі з `supportsVideo === true` обходять місток. Сигнал скасування запиту клієнта поширюється через завантаження, чергу брокера, підпроцеси та виклики підписів; скасування зупиняється між відео і ніколи не відкривається для сировинних медіа.

Налаштування часу виконання підтримуються базою даних та перевіряються Zod:

| Ключ                                | За замовчуванням | Діапазон / поведінка                                                                                           |
| ----------------------------------- | ---------------- | -------------------------------------------------------------------------------------------------------------- |
| `modalityBridgeVideoEnabled`        | `false`          | Додатковий час виконання, за бажанням                                                                          |
| `modalityBridgeVideoAnalysisMode`   | `"full"`         | `full` зберігає загальні підписи; `focused` використовує обмежений, ненадійний контекст останнього користувача |
| `modalityBridgeVideoModel`          | `""`             | Успадковує модель Мосту Зору                                                                                   |
| `modalityBridgeVideoFrameCount`     | `8`              | 1–16                                                                                                           |
| `modalityBridgeVideoSamplingPolicy` | `"uniform"`      | `uniform`, `scene_aware` або пропорційний `segment_aware`; збій детектора повертається до `uniform`            |
| `modalityBridgeVideoMaxVideos`      | `1`              | 1–4                                                                                                            |
| `modalityBridgeVideoTimeout`        | `120000`         | 1000–120000 мс                                                                                                 |

Значення тайм-ауту для застарілого Відео, що перевищують 120 секунд, обмежуються термінами брокера; нові записи вище цього ліміту відхиляються. `GET /api/modality-bridge/video/runtime` вимагає довіреного штампованого локального зворотного зв'язку перед аутентифікацією або перевіркою часу виконання, а потім вимагає управлінської аутентифікації. Він повертає лише `available`, очищені версії FFmpeg/ffprobe та фіксовану причину, коли час виконання недоступний. Внутрішня точка витягання не є публічним API для завантаження: насичення черги повертає `503` плюс `Retry-After`, відключення виклику повертає `499`, а фіксований термін брокера повертає `504`. Перетворені відповіді додають
`video->text;model=<visionModel>;parts=<videos>` до центрального
`x-omniroute-modality-bridge` заголовка без видалення сегментів Зору або Аудіо.

### Маскувальник PII (`piiMasker.ts`)

Запускається на **обох** етапах.

- **`preCall`** клонує навантаження, проходить через `system`, `messages`, `input` та
  `prompt` (включаючи прості рядкові елементи) та застосовує `processPII()` (з
  `@/shared/utils/inputSanitizer`) до рядкових полів `content`/`text`. Коли
  `PII_REDACTION_ENABLED=true`, виявлені PII редагуються в вихідному
  навантаженні. Це незалежно від `INPUT_SANITIZER_MODE` (який лише контролює
  політику ін'єкції запиту). Коли редагування вимкнено, виклик записує кількість виявлень без переписування вмісту.
- **`postCall`** глибоко клонує відповідь, запускає `sanitizePIIResponse()` плюс
  маскувальник форми API Відповідей (`maskResponsesOutput` — охоплює
  `output_text` та `output[].content[].text`). Якщо відбувається будь-яке редагування, змінена відповідь замінює оригінал.

Захисний бар'єр ніколи не блокує; він лише анотує (`meta.detections`,
`meta.redacted`) або переписує.

### Ін'єкція запиту (`promptInjection.ts`)

Виявляє ворожі структури у вмісті, наданому користувачем, і забезпечує
налаштовану політику. Поведінка керується змінними середовища та параметрами конструктора:

| Налаштування     | Змінна середовища                                                                                        | За замовчуванням | Ефект                                                                                                                                                                                      |
| ---------------- | -------------------------------------------------------------------------------------------------------- | ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Увімкнено        | `INPUT_SANITIZER_ENABLED`                                                                                | `true`           | Коли `false`, охоронна система короткочасно відключається.                                                                                                                                 |
| Режим            | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                          | `warn`           | Політика ін'єкцій: `block`, `warn` або `log`. (`redact` приймається для зворотної сумісності, але **не** видаляє текст ін'єкції; переписування PII контролюється `PII_REDACTION_ENABLED`.) |
| Поріг блокування | `blockThreshold` опція / `INPUT_SANITIZER_BLOCK_THRESHOLD` (псевдонім `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`           | Мінімальна серйозність, необхідна для блокування. Середня серйозність є лише для спостереження за замовчуванням.                                                                           |

**Пріоритет режиму** (`getMode`): виклик `options.mode` →
`INJECTION_GUARD_MODE` **перевизначення функціонального прапора БД** (Панель управління → Налаштування →
Функціональні прапори) → `INJECTION_GUARD_MODE` змінна середовища → `INPUT_SANITIZER_MODE` змінна середовища →
`warn`. Отже, перевизначення на панелі управління переважає над змінними середовища, тому UI функціональних прапорів контролює роботу охоронної системи в реальному часі (без перезапуску). Читання з БД є безпечним:
якщо виникає помилка, охоронна система повертається до поведінки на основі змінних середовища, а коли жодне
перевизначення не встановлено, поведінка є ідентичною лише резолюції на основі змінних середовища.

Джерела виявлення:

1. `sanitizeRequest()` з `@/shared/utils/inputSanitizer` (спільний детектор
   набір, що використовується в інших місцях конвеєра).
2. Вбудовані `DEFAULT_GUARD_PATTERNS` (в даний час `system_override_inline` та
   `markdown_system_block`, обидва з серйозністю `high`).
3. Додаткові `customPatterns`, передані через параметри конструктора (рядки, регулярні вирази,
   або `{ name, pattern, severity }` записи).

Коли `mode === "block"` **і** принаймні одне виявлення відповідає порогу
серйозності, `preCall` повертає `{ block: true, message: "Запит відхилено:
виявлено підозрілий контент" }`. У режимах `warn`/`log` охоронна система веде журнал, але
дозволяє виклик. Спільний допоміжний метод `evaluatePromptInjection()` також експортується
для викликів, які потребують оцінки запитів без проходження через реєстр.

**Обмеження сканування (v3.8.20):** детектор перевіряє лише **перші 16 КБ**
об'єднаного тексту запиту — `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 байти) в
`src/shared/utils/inputSanitizer.ts`. Як `detectInjection()`, так і
`evaluatePromptInjection()` `slice(0, MAX_INJECTION_SCAN_BYTES)` перед виконанням
циклу шаблонів. Директиви ін'єкції розташовані близько до початку введення, тому це
обмежує використання процесора/GC для навантажень у кілька сотень КБ без послаблення виявлення (порівняйте
#3932, #4041).

### Маскувальник облікових даних (`credentialMasker.ts`)

Працює на **обох** етапах, останній у стандартному ланцюгу (пріоритет `95`). Видаляє
відомі шаблони API-ключів / секретних токенів з вихідного навантаження (вміст повідомлення,
аргументи виклику інструментів, результати інструментів) **і** відповіді постачальника, тому
облікові дані, вставлені в запит (або повернуті назад результатом інструменту), не потрапляють
до постачальника або назад до клієнта.

- **Тільки за бажанням**, та ж сама конвенція, що й видалення PII (Жорстке правило #20-сусіднє):
  вимкнено, якщо `settings.credentialRedactionEnabled === true` **або**
  `CREDENTIAL_REDACTION_ENABLED=true`. Коли це вимкнено, охоронна система не виконує жодних дій —
  вона ніколи не блокує і ніколи не переписує.
- `redactCredentials()` обходить все дерево навантаження/відповіді (`walkValue()`,
  безпечно для забруднення прототипу, безпечно для циклів через `WeakSet`) і замінює збіги на
  заповнювач `[REDACTED:<type>]`, клонує лише гілки, які насправді
  змінилися.
- `CREDENTIAL_PATTERNS` охоплює ключі постачальників LLM (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), токени VCS/SaaS (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), платіжні ключі (Stripe, Square), ключі хмари
  (ключ доступу AWS, Twilio, SendGrid, Mailgun), приватні ключі / JWT,
  рядки підключення з обліковими даними (`mongodb://user:pass@...` тощо) та
  загальний шаблон заголовка `Authorization`/`x-api-key`/`api-key`/`apikey`.
  Ключі у формі заголовка (`authorization`, `x-api-key`, `api-key`,
  `apikey`) видаляються структурно (тільки значення, префікс схеми, як
  `Bearer `/`Basic ` зберігається) замість використання загального текстового регулярного виразу.
- Охоронна система ніколи не блокує; вона лише переписує (`modifiedPayload` /
  `modifiedResponse`) і анотує (`meta.credentialsRedacted`, `meta.count`).

Охорона від регресії: `tests/unit/credential-masker-guardrail.test.ts`.

## Базовий контракт (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(
    payload: unknown,
    context: GuardrailContext,
  ): Promise<GuardrailResult | void>;

  async postCall(
    response: unknown,
    context: GuardrailContext,
  ): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true коротко перериває ланцюг
  message?: string; // з'являється при блокуванні
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // повертається preCall для переписування запиту
  modifiedResponse?: TValue; // повертається postCall для переписування відповіді
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

Гардурал сигналізує "без змін", повертаючи або `void`, `{}`, або
`{ block: false }`. Повернення `modifiedPayload`/`modifiedResponse` замінює
значення, що проходить через ланцюг для наступних гардуралів.
`signal?: AbortSignal` переносить життєвий цикл виклику в гардурали. Відміна запиту є навмисним винятком fail-open: медіа мости припиняють роботу та очищуються без відновлення сирого медіа до цілі, яка відома як така, що не підтримує його.

## Реєстр (`registry.ts`)

Синглтон `guardrailRegistry` надає:

- `register(guardrail)` — додає (або замінює за нормалізованим ім'ям) захисний механізм та пересортовує за зростанням `priority`.
- `clear()` / `list()` — допоміжні функції адміністрування.
- `runPreCallHooks(payload, context)` — ітерує активні захисні механізми, пропускає `payload` через `modifiedPayload` і зупиняється на першому `block: true`.
- `runPostCallHooks(response, context)` — той самий потік на стороні відповіді.
- `resetGuardrailsForTests({ registerDefaults })` — очищає стан та, за бажанням, повторно реєструє значення за замовчуванням для чистої ізоляції тестів.

Обидва виконавці повертають `{ blocked, payload|response, results, guardrail?, message? }`, де `results` — це масив записів `GuardrailExecutionResult`, що містять поля `blocked`, `skipped`, `modified`, `error` та `meta` для кожного захисного механізму, корисні для трасування.

### Вимкнення захисних механізмів для кожного запиту

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` агрегує дедуплікований список імен захисних механізмів, які слід пропустити для поточного запиту. Джерела (всі необов'язкові, всі об'єднані):

- `apiKeyInfo.disabledGuardrails`
- Тіло запиту `disabledGuardrails` (верхнього рівня)
- Тіло запиту `metadata.disabledGuardrails`
- Заголовок `x-omniroute-disabled-guardrails` (або застарілий `x-disabled-guardrails`)

Значення можуть бути масивами рядків або рядком, розділеним комами; імена нормалізуються до нижнього регістру в kebab-case (`pii_masker` → `pii-masker`). Результат передається через `context.disabledGuardrails` до реєстру, який пропускає відповідні захисні механізми (`skipped: true` у `results`).

## Порядок виконання

Для кожного запиту, що проходить через `src/sse/handlers/chat.ts` та
`open-sse/handlers/chatCore.ts`:

1.  `resolveDisabledGuardrails(...)` створює список винятків з ключа API, тіла запиту
    та заголовків.
2.  `guardrailRegistry.runPreCallHooks(body, ctx)` запускає захисні механізми у порядку
    зростання пріоритету:
    - Вимкнені захисні механізми записуються як `skipped`.
    - `preCall` кожного захисного механізму може переписати корисне навантаження
      через `modifiedPayload`.
    - Перший `block: true` перериває ланцюжок, і обробник повертає
      відповідь про відхилення захисним механізмом.
3.  (Потенційно переписане) корисне навантаження надходить до комбінованої маршрутизації
    та вихідної диспетчеризації.
4.  Після формування відповіді `guardrailRegistry.runPostCallHooks(...)`
    запускає той самий ланцюжок на відповіді. `block: true` тут відкидає
    вихідну відповідь.

Захисні механізми, які викликають помилку, записуються з `error: <message>` та
реєструються через `logger.warn`, але ланцюжок продовжується — за задумом,
система працює за принципом "відмова-відкриття".

## Конфігурація

Змінні середовища, які читаються вбудованими захисними механізмами:

| Змінна                                | Використовується               | Ефект                                                                                                          |
| :------------------------------------ | :----------------------------- | :------------------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`             | Встановіть `false`, щоб повністю вимкнути виявлення.                                                           |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`             | Політика ін'єкцій: `warn`, `block` або `log`. Застаріле значення `redact` не переписує текст ін'єкції.         |
| `INJECTION_GUARD_MODE`                | `prompt-injection`             | Режим для захисту від ін'єкцій; також прапорець функції БД, який **перевизначає** змінні середовища (БД > ЗМ). |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`             | Мінімальна серйозність, при якій `MODE=block` відхиляє: `high` (за замовчуванням), `medium` або `low`.         |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`             | Застарілий псевдонім для `INPUT_SANITIZER_BLOCK_THRESHOLD`.                                                    |
| `PII_REDACTION_ENABLED`               | `pii-masker`                   | Якщо `true`, PII запиту редагується (незалежно від режиму ін'єкції).                                           |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (нижче за течією) | Контролює поведінку маскувальника на стороні відповіді.                                                        |

Захисні механізми Modality Bridge читають конфігурацію часу виконання зі сховища
налаштувань на основі БД (`getSettings()`), а не зі змінних середовища.
Основними ключами Vision є `modalityBridgeVisionEnabled`,
`modalityBridgeVisionMode`, `modalityBridgeVisionModel`,
`modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`,
`modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`,
`modalityBridgeVisionMaxChars`, `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes` та `modalityBridgeCacheMaxEntries`.
Застарілі ключі `visionBridge*` приймаються лише як задокументований
одноцикловий резервний варіант читання; записи на панелі керування
використовують основні ключі. Значення за замовчуванням та резервний
розв'язувач знаходяться в `src/shared/constants/modalityBridgeDefaults.ts`,
а застарілі константи зберігаються в
`src/shared/constants/visionBridgeDefaults.ts`.

Аудіо використовує `modalityBridgeAudioEnabled`, `modalityBridgeAudioModel`,
`modalityBridgeAudioTimeout` та `modalityBridgeAudioMaxClips`, а також спільні
налаштування `modalityBridgeCache*`. Аудіо не має резервного варіанту
застарілих ключів, оскільки ці ключі були введені зі схемою Modality Bridge.

Відео використовує `modalityBridgeVideoEnabled`, `modalityBridgeVideoAnalysisMode`,
`modalityBridgeVideoModel`, `modalityBridgeVideoFrameCount`,
`modalityBridgeVideoSamplingPolicy`, `modalityBridgeVideoMaxVideos` та
`modalityBridgeVideoTimeout`, а також спільні налаштування `modalityBridgeCache*`.
Він вимкнений за замовчуванням, оскільки FFmpeg/ffprobe є необов'язковими
операційними залежностями, а створення субтитрів кадрів додає затримку та
витрати на модель.

## Користувацькі обмежувачі (Guardrails)

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

Кроки:

1.  Створіть `src/lib/guardrails/myGuardrail.ts`, розширюючи `BaseGuardrail`.
2.  Реалізуйте `preCall` та/або `postCall`.
3.  Зареєструйте під час імпорту (виштовхніть з `registerDefaultGuardrails`) або
    викличте `guardrailRegistry.register(...)` під час виконання — реєстр замінює
    будь-який попередній обмежувач з тим самим нормалізованим ім'ям.
4.  Додайте тести до `tests/unit/` (існуючі приклади:
    `tests/unit/guardrails-registry.test.ts`,
    `tests/unit/prompt-injection-guard.test.ts`,
    `tests/unit/guardrails/visionBridge.test.ts`).

## Тестування

Використовуйте `resetGuardrailsForTests()` між тестами, щоб почати з відомого стану.
Передайте `{ registerDefaults: false }`, щоб почати з порожнього реєстру та
зареєструвати лише обмежувачі, що тестуються. Vision Bridge приймає впровадження
залежностей (`deps.getSettings`, `deps.callVisionModel`); Audio Bridge надає
еквівалентні точки для налаштувань, можливостей, вибору моделі STT, перевірок
облікових даних та транскрипції. Таким чином, тести можуть перевіряти обидва
потоки без доступу до БД або мережі.

## Покриття маршрутів захисту від ін'єкцій та червона команда (Фаза 8 · Блок D)

Захист від ін'єкцій (`createInjectionGuard` / `withInjectionGuard`) охоплює всі маршрути,
які приймають підказки користувача. Він враховує `INJECTION_GUARD_MODE` (за замовчуванням `warn` = лише логування;
`block` = повертає HTTP 400 `SECURITY_001`).

| Тип              | Маршрути                                                                                                                                             | Режим за замовчуванням |
| :--------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------- | :--------------------- |
| Текст (існуючий) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn                   |
| Генеративний     | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn                   |
| Дані             | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn                   |

Вилучення тексту (`extractMessageContents`) охоплює `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`.

**Червона команда (нічна, `nightly-llm-security.yml`):** promptfoo перевіряє, що кожен маршрут блокує
корпус OWASP-LLM у режимі `INJECTION_GUARD_MODE=block`; garak запускає зонди (пропускає без секрету).
`moderations` включено для послідовності — оператори в режимі блокування можуть виключити його через
`resolveDisabledGuardrails`.

Нічний робочий процес (`.github/workflows/nightly-llm-security.yml`, cron + ручний
запуск) має два завдання:

- **`promptfoo-guard` (блокування)** — запускає `promptfoo eval -c promptfooconfig.yaml`
  з `INJECTION_GUARD_MODE=block`. Кожен ворожий випадок (наприклад, "ігнорувати всі
  попередні інструкції...", "jailbreaks" у стилі DAN) стверджує, що відповідь містить
  `error.code === "SECURITY_001"`, тобто обмежувач фактично відхилив запит.
- **`garak` (консультативний)** — запускає garak `--probes promptinject,dan,leakreplay`
  проти локального екземпляра OmniRoute (`http://localhost:20128/v1`). Залежить від
  секрету провайдера (`PROMPTFOO_PROVIDER_KEY`); пропускається без помилок і має суфікс
  `|| true`, тому він звітує без збою CI.

Покриття допоміжного обмежувача (`createInjectionGuard` / `withInjectionGuard`)
охоплює кожен маршрут `/v1`, що містить підказки; текст підказки витягується з
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` за допомогою
`extractMessageContents()` у `src/shared/utils/inputSanitizer.ts`.
